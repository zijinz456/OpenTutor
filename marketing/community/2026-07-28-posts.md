## a) Hacker News — Show HN

**Title:** `Show HN: OpenTutor – Bayesian Knowledge Tracing + ZPD difficulty selection in a local AI tutor`

---

Most adaptive learning products use "difficulty levels" that are really just hand-labeled question tiers. The student picks easy/medium/hard from a dropdown, or the system rotates through them evenly. Neither approach is actually adaptive — they don't model what the student knows.

OpenTutor uses Bayesian Knowledge Tracing (BKT) to estimate per-concept mastery P(L_n) from the student's answer sequence, then maps that estimate to a difficulty layer using Vygotsky's Zone of Proximal Development. The implementation is in `apps/api/services/learning_science/knowledge_tracer.py` (197 lines). The math is straightforward: four parameters per concept (P(L0) = prior mastery, P(T) = learning rate per attempt, P(G) = guess rate, P(S) = slip rate), updated with Bayes' rule after each answer. The standard Corbett & Anderson (1994) formulation.

The part worth discussing is how we estimate those four parameters without manual tuning. For a new concept, we initialize from the student's answer history: P(L0) = 0.30 if first attempt correct, 0.05 otherwise; P(G) by question type (0.50 for true/false, 0.25 for MC, 0.05 for short answer); P(T) from wrong→correct transition frequency; P(S) from correct→wrong slippage rate. With ≥15 observations per concept, it upgrades to EM-fitted parameters via pyBKT (`bkt_trainer.py`, 296 lines) — a weekly background job trains per-student, per-concept parameters and caches them. The adaptive path uses the trained params when available, heuristic estimates otherwise, transparently.

The difficulty selector (`difficulty_selector.py`, 165 lines) maps mastery to a three-layer system: P(L) < 0.4 → Layer 1 (fundamental recall, 70/30/0 distribution); 0.4–0.7 → Layer 2 (application, 20/50/30); ≥0.7 → Layer 3 (trap/edge case, 10/30/60). Gap type overrides apply: a detected `fundamental_gap` forces Layer 1 regardless of measured mastery. This is the part that makes the ZPD framing meaningful — questions are always calibrated just above what the student can currently do.

65 test files, 996 pytest functions. MIT. `docker compose up -d --build`.

## b) r/LocalLLaMA

**Title:** `What actually runs on llama3.2:3b in my AI tutor — and what requires something bigger`

---

OpenTutor is a self-hosted learning platform that defaults to Ollama + llama3.2:3b. After a few months of building with it, I wanted to document which parts of the stack llama3.2:3b handles well and where I had to accept a quality ceiling or route to something bigger.

**What llama3.2:3b handles fine**

Content ingestion routing. When you upload a PDF, the pipeline (`ingestion/pipeline.py`, 410 lines) extracts text, splits into semantic chunks, and classifies each chunk by content type (concept, example, definition, exercise). Classification is done via a short structured prompt — typically < 200 tokens context, expects a JSON enum response. llama3.2:3b is accurate here and fast enough that it doesn't noticeably slow ingestion.

Flashcard generation from chunked notes. The prompt is bounded (one chunk at a time), the output is structured (front/back pairs), and 3b handles the instruction-following reliably. Generated quality is noticeably lower than 8b+ on abstract or math-heavy content, but acceptable for factual recall cards.

Cognitive load signals. The app runs NLP-based affect analysis (`compute_cognitive_load()`) every 3 messages to detect frustration and confusion in the student's message. The prompt is short, the output is two floats. 3b works fine.

**Where it falls short**

Multi-step study plan generation. The planning agent needs to reason across a full course structure (all topics, their prerequisites, the student's mastery state, a deadline), produce a week-by-week schedule with rationale, and make it actually coherent. 3b consistently produces plans that ignore prerequisite ordering or assign the wrong number of sessions per concept. I route planning to a frontier tier (or llama3.1:70b if you have it) — 3b plan quality isn't usable.

Socratic questioning. The tutor is supposed to ask follow-up questions rather than just explain. 3b reliably defaults to direct explanation even when the prompt says otherwise. This isn't a prompt engineering problem I've been able to solve.

**Setup**

```bash
LLM_PROVIDER=ollama
LLM_MODEL=llama3.2:3b          # fast tier + ingestion
LLM_FALLBACK_PROVIDER=deepseek
DEEPSEEK_API_KEY=sk-...        # frontier tier fallback
```

llama3.2:3b RAM at 4-bit quant: ~2.0 GB on an M2 Pro. Response latency for ingestion classification: 0.3–0.8s per chunk warm. For a 30-page PDF, ingestion takes about 40–60s total. MIT licensed.

## c) r/Anki

**Title:** `FSRS has a "forgetting cost" calculation I hadn't seen discussed — here's how it works`

---

I've been building an FSRS-based flashcard scheduler for OpenTutor and came across a scheduling concept that I don't see discussed in the Anki community: **forgetting cost estimation**. Anki's scheduler tells you what's due; it doesn't tell you how much knowledge you're currently losing by not reviewing.

Here's the idea. For each overdue card, you can compute the current retrievability R(t) = (1 + t / (9 × S))^−1, where t is days since scheduled due date and S is stability. 1 − R(t) is the probability that card is already forgotten. Sum that across all overdue cards:

```
forgetting_cost = Σ (1 - R(t_i, S_i))   for each overdue card i
```

The result is an expected number of forgotten cards — a float, not a card count. From `apps/api/services/spaced_repetition/fsrs.py` (304 lines):

```python
def estimate_forgetting_cost(cards, now=None):
    now = _as_utc(now or datetime.now(timezone.utc))
    total_expected_forgotten = 0.0
    for card in cards:
        if card.due is None or card.stability <= 0:
            continue
        due = _as_utc(card.due)
        if due > now:
            continue
        elapsed = max((now - due).total_seconds() / 86400, 0)
        scheduled_interval = max(card.stability, 1.0)
        total_elapsed = elapsed + scheduled_interval
        recall_prob = _retrievability(total_elapsed, card.stability)
        total_expected_forgotten += (1.0 - recall_prob)
    return round(total_expected_forgotten, 2)
```

This feeds into `estimate_session_urgency()`, which maps the cost to urgency levels:

- cost ≥ 5.0 → "critical" (immediate review needed)
- cost ≥ 2.0 → "high"
- ≥10 due cards → "normal"
- ≥3 due cards → "low"
- otherwise → "none"

The 90% retention threshold (stability S = days until R drops to 0.90) maps to `t = 9 × S × (1/0.90 − 1) ≈ 1.0 × S` — roughly one stability-length of delay before a card crosses the threshold. So a card with stability 10 days is expected to be forgotten about 10 days after its due date if unreviewed. The forgetting cost formula makes this operational: you can surface a "review now" nudge based on expected knowledge loss, not just raw due count.

This is distinct from Anki's due-count-based scheduling and from load-balancing approaches (like the "max due per day" setting). It answers a different question: not "how many cards are due?" but "how much are you forgetting by waiting?"

We also added a forgetting forecast (`forgetting_forecast.py`, 137 lines) that projects when each knowledge point will drop below threshold and assigns urgency tags ("ok", "warning", "urgent", "overdue") — displayed in the workspace as a proactive review schedule.

MIT licensed. GitHub: https://github.com/zijinz456/OpenTutor

## d) r/GetStudying / r/medicalschool

**Title:** `I started mapping what I don't know before deciding what to study next — changed everything`

---

Most of my studying used to be linear. Read chapter, do questions, move to next chapter. The problem: I kept rediscovering that I didn't actually understand something three chapters back, usually right before an exam when there wasn't time to fix it.

The shift that helped most was stopping at the end of each study block and asking a different question: **not "what did I just cover?" but "what do I currently not know that would block me if it came up tomorrow?"**

This forced me to think about prerequisites, not just topics. For a lot of subjects — pharmacology, biochemistry, physiology — concepts have hard dependencies. If you don't actually understand receptor binding kinetics, you can memorize competitive vs. non-competitive inhibition and still not be able to apply it on a novel question. The knowledge is there as a fact but not as a tool.

The exercise I do:

1. After finishing a topic, write down the three concepts from it that I feel least solid on.
2. For each, ask: "Is there something earlier I'd need to understand this properly?"
3. If yes — go back. Don't move forward until the prerequisite is actually solid, not just reviewed.
4. If no — add it to the flashcard queue with a note: "I know this but it feels fragile."

The "fragile" tag matters. Stuff that feels fragile tends to be partially encoded — you can recognize it in a multiple-choice stem but can't produce it cold. Identifying fragile knowledge is different from identifying gaps; it's a separate category that standard review scheduling misses.

The other thing: I started treating concept relationships as more important than concept counts. Knowing 200 drug names is less useful than understanding 5 mechanism families well enough to reason from mechanism to effect. Studying toward relationships — "how do these two concepts connect?" — changes what questions you ask during review.

The tool I've been building (OpenTutor) tries to automate the prerequisite-mapping part with a knowledge graph, but the core habit — explicitly asking "what else do I need to know for this to make sense?" after every topic — is something you can do with a piece of paper. The tool just makes the gap more visible.

What's your method for deciding what to study next when everything feels incomplete?

## e) Dev.to / Hashnode — Technical Article

**Title:** How I implemented Bayesian Knowledge Tracing to track per-concept mastery in my AI tutor

---

Most educational software has one of two problems: it doesn't track what students know at all (just tracks time or content completed), or it tracks it with something too heavy to run locally (adaptive testing models that require thousands of response calibrations). I wanted something between those — a lightweight probabilistic model of student knowledge that updates in real time, runs with no external service, and plugs into difficulty selection.

The answer was Bayesian Knowledge Tracing (BKT), introduced by Corbett and Anderson in 1994. It's old, well-understood, and surprisingly effective. Here's what I built in OpenTutor.

### What BKT models

BKT estimates a single latent variable per student per concept: P(L_n), the probability the student has learned the concept after n observations. It has four parameters:

- **P(L0)**: Prior probability — does the student already know this?
- **P(T)**: Learning rate — probability of learning on each practice opportunity
- **P(G)**: Guess rate — probability of answering correctly without knowing
- **P(S)**: Slip rate — probability of answering incorrectly despite knowing

The update rule after each observation applies Bayes' theorem:

```python
def update_mastery(state: BKTState, is_correct: bool, params: BKTParams) -> BKTState:
    p_l = state.p_mastery

    if is_correct:
        p_correct = p_l * (1 - params.p_s) + (1 - p_l) * params.p_g
        p_l_given_obs = (p_l * (1 - params.p_s)) / max(p_correct, 1e-9)
    else:
        p_wrong = p_l * params.p_s + (1 - p_l) * (1 - params.p_g)
        p_l_given_obs = (p_l * params.p_s) / max(p_wrong, 1e-9)

    # Incorporate learning opportunity
    p_l_new = p_l_given_obs + (1 - p_l_given_obs) * params.p_t
    return BKTState(p_mastery=max(0.0, min(1.0, p_l_new)), observations=state.observations + 1)
```

The posterior step updates our estimate based on whether the answer was correct, accounting for guessing and slipping. The learning step then shifts the estimate upward by P(T) regardless — the student had an opportunity to learn, whether or not they got it right.

### The parameter estimation problem

Standard BKT assumes you have population-level parameters pre-fitted on historical data. I don't — OpenTutor is single-user, local-first, and can't pool data across students. I needed parameters that personalize from the individual's answer history.

The solution is in `knowledge_tracer.py` (197 lines):

```python
def estimate_params(results: list[bool], question_type: str | None = None) -> BKTParams:
    # P(G) — by question type
    p_g = 0.25  # default MC
    if question_type in ("tf", "true_false"):
        p_g = 0.50
    elif question_type in ("short_answer", "fill_blank"):
        p_g = 0.05

    # P(L0) — from first attempt
    p_l0 = 0.30 if results[0] else 0.05

    # P(T) — from wrong→correct transitions
    transitions = sum(
        1 for i in range(1, len(results))
        if not results[i-1] and results[i]
    )
    opportunities = sum(1 for i in range(1, len(results)) if not results[i-1])
    p_t = transitions / max(opportunities, 1) if opportunities > 0 else 0.20
    p_t = max(0.05, min(p_t, 0.5))

    # P(S) — from correct→wrong transitions
    slips = sum(1 for i in range(1, len(results)) if results[i-1] and not results[i])
    slip_opps = sum(1 for i in range(1, len(results)) if results[i-1])
    p_s = slips / max(slip_opps, 1) if slip_opps > 0 else 0.10
    p_s = max(0.02, min(p_s, 0.3))

    return BKTParams(p_l0=p_l0, p_t=p_t, p_g=p_g, p_s=p_s)
```

This heuristic is good enough for < 15 observations. With ≥15 observations per concept, the system upgrades to EM-fitted parameters via `bkt_trainer.py` (296 lines, uses the pyBKT library). A weekly background job runs the EM fitting across all concepts and caches results with an 8-day TTL. The main mastery path calls `compute_mastery_adaptive()`, which silently uses trained params when available and falls back to heuristic otherwise.

### Connecting mastery to difficulty

BKT alone gives you a probability estimate. The useful part is what you do with it. I mapped mastery to Vygotsky's Zone of Proximal Development — questions should be just above the student's current ability.

```python
# difficulty_selector.py (165 lines)
MASTERY_LOW_THRESHOLD = 0.4   # Below → Layer 1 (fundamental recall)
MASTERY_HIGH_THRESHOLD = 0.7  # Above → Layer 3 (traps / edge cases)

DIST_LOW_MASTERY  = {1: 0.6, 2: 0.3, 3: 0.1}
DIST_MID_MASTERY  = {1: 0.2, 2: 0.5, 3: 0.3}
DIST_HIGH_MASTERY = {1: 0.1, 2: 0.3, 3: 0.6}
```

The function returns both a `primary_layer` and a `layer_distribution` (mix of question difficulties), so the quiz generator can produce a set of questions at the right average difficulty rather than picking a single tier. There are also gap type overrides: a detected `fundamental_gap` forces Layer 1 regardless of measured mastery (the student might score well on application questions while missing a core concept).

### What the knowledge graph adds

Mastery is per-concept, but concepts have prerequisites. The LOOM graph (`loom_graph.py`, 428 lines) maps concept relationships — prerequisites, related concepts, co-occurrence in wrong answers. When the gap detector finds a weak concept, it walks the prerequisite graph to find the root cause. A student who consistently misses cardiac output questions might have an unmeasured gap in stroke volume fundamentals — the graph surfaces that.

Mastery in the graph is also FSRS-decayed. A concept the student aced three months ago has lower current mastery than one they reviewed last week, even with the same P(L_n) at time of last practice. The workspace's knowledge graph visualization shows time-decayed mastery by applying `_retrievability(elapsed_days, stability_days)` to each node before rendering.
