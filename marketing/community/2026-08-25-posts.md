## a) Hacker News — Show HN

**Title:** `Show HN: OpenTutor – maps BKT mastery to Vygotsky's ZPD for question difficulty`

---

Most AI tutors generate questions at a fixed difficulty or let the user pick "easy/medium/hard." Both are wrong in the same way: they ignore what the student actually knows right now. Vygotsky's Zone of Proximal Development says learning happens fastest when tasks sit just above current ability — not below (no challenge, no encoding), not far above (too much cognitive load, nothing sticks). The problem is implementing that precisely without a heavy inference call on every question.

OpenTutor maps BKT mastery scores to three question difficulty tiers without an LLM call. Bayesian Knowledge Tracing runs per concept and gives a mastery probability P(L) between 0 and 1. Below 0.4, the student gets Layer 1 questions — recall and recognition, "what is X." Between 0.4 and 0.7, Layer 2 — application and transfer, "use X to solve Y." Above 0.7, Layer 3 — traps and edge cases, "why does X fail when Z." Each session gets a layer distribution (not a hard cutoff) so there's always some mixing: at mid-mastery the distribution is `{1: 20%, 2: 50%, 3: 30%}`. Gap type overrides mastery entirely: a `fundamental_gap` detected from error patterns forces Layer 1 regardless of P(L), because the student's overall mastery number is misleading when a foundation concept is missing.

The implementation is `services/learning_science/difficulty_selector.py` (165 lines). BKT parameter estimation is per-student from answer history (`knowledge_tracer.py`, 197 lines) — P(G) varies by question type (0.5 for true/false, 0.25 for MCQ, 0.05 for short answer), and P(L0) is seeded from first-attempt correctness rather than a global prior. The layer recommendation gets formatted as text and injected into the question-generation agent's system prompt. This composable approach means any agent that generates practice content gets ZPD-aware difficulty for free by pulling the recommendation from DB. FastAPI + Next.js 16 + SQLite, Docker Compose, MIT, 65 test files, 996 test functions. GitHub: https://github.com/zijinz456/OpenTutor

## b) r/LocalLLaMA

**Title:** `How I route llama3.2:3b vs larger models per-request using heuristic complexity scoring (no LLM call)`

---

If you run multiple models locally, the obvious approach is: small model for simple stuff, large model for complex stuff. The non-obvious part is figuring out which is which without asking an LLM to classify the request (that defeats the point).

OpenTutor's complexity router scores each incoming request on five heuristics — no inference needed — and routes to one of three model tiers: `fast`, `standard`, or `frontier`. The implementation is in `services/llm/complexity.py`:

```python
def score_complexity(
    message: str,
    intent: str = "general",
    scene: str = "study_session",
    history_length: int = 0,
    has_rag_context: bool = False,
) -> int:
    score = 0
    score += _score_message_length(message)    # 0-150
    score += _score_intent(intent)             # 0-300
    score += _score_scene(scene)               # 0-100
    score += _score_conversation_depth(history_length)  # 0-80
    score += _score_complexity_markers(message)         # 0-100, capped
    if has_rag_context:
        score += 50   # RAG synthesis needs more capable model
    return score

# score < 150 → fast tier
# 150 <= score < 500 → standard
# score >= 500 → frontier
```

Complexity markers catch domain-specific phrasing: "prove", "derive", "step-by-step" add 40-50 points; "compare", "analyze", "explain why" add 25-30. The intent score carries the most weight — a preference change is 30, a lesson is 150, a curriculum plan is 250. Scene adds context: `exam_prep` gets +80, plain `study_session` adds nothing.

On top of the score, each agent type has a minimum tier floor:

```python
AGENT_MIN_TIERS: dict[str, ModelTier] = {
    "preference": ModelTier.FAST,     # Simple preference lookups
    "scene": ModelTier.FAST,
    "teaching": ModelTier.STANDARD,   # Teaching needs reasoning
    "exercise": ModelTier.STANDARD,
    "planning": ModelTier.FRONTIER,   # Multi-step planning
    "code_execution": ModelTier.FRONTIER,
}
```

The router returns `max(scored_tier, agent_min_tier)`. A preference update that scores high (long message asking about preferences) still runs fast. A planning agent that scores low still runs frontier — you can't write a curriculum plan on llama3.2:3b and expect coherent output.

Real numbers on a 16GB Mac: fast-tier calls with llama3.2:3b average 340ms, standard-tier with llama3.1:8b average 1.2s. Frontier-tier routes to a cloud fallback if configured. About 40% of requests in a typical study session score below 150 (fast tier) — greetings, preference changes, short factual lookups. The remaining 60% split roughly evenly between standard and frontier. Without routing, everything would hit the 8b model; with it, average latency drops by about a third.

## c) r/Anki

**Title:** `Anki uses global BKT defaults. I estimate them per student from answer history — here's why it matters`

---

Anki's FSRS uses global parameters optimized across millions of reviews. That's the right tradeoff for Anki — it's a general-purpose tool, and person-specific parameter estimation requires enough review data that global defaults are better for most new users. But it's a deliberate tradeoff, not the ceiling.

OpenTutor estimates BKT parameters per student from their actual answer history. The four parameters — P(L0): prior mastery, P(T): learning rate, P(G): guess probability, P(S): slip rate — start from educated defaults but update as the student practices:

- **P(G)** adjusts by question type immediately: 0.50 for true/false (you can guess your way through), 0.25 for 4-option MCQ, 0.05 for short answer and free response. This matters: the same wrong answer means something very different on a true/false card versus a fill-in-blank card. A wrong true/false answer is weak evidence of not knowing; a wrong free-response answer is strong evidence.

- **P(L0)** seeds from first-attempt performance. If a student gets the first question on a concept right, the prior starts at 0.30 (probably already had some knowledge). First attempt wrong, prior starts at 0.05. This avoids the problem where a student who already knows the material gets served a full recall-from-zero sequence.

- **P(T)** estimates from `wrong → correct` transitions in the answer sequence. Frequent transitions signal fast learning; slow transitions signal a concept that's hard to acquire. The estimator runs over the last 20 answers, not the full history, so it's responsive to recent sessions.

The practical effect: two students with the same overall card performance but different patterns get different question sequences. The student who gets things right on the first attempt but slips occasionally gets a different slip rate (P(S)) from the student who struggles at first but then nails it — and their FSRS stability growth is calibrated differently as a result.

This composable with the LECTOR review layer: once per-student BKT mastery is estimated, LECTOR uses it to order prerequisites before dependents and cluster related concepts. Anki doesn't have the prerequisite graph — that's structural, not a parameter thing — but the per-student parameters do make the review queue more individually tuned.

OpenTutor is MIT, self-hosted, runs locally with Ollama. GitHub: https://github.com/zijinz456/OpenTutor

## d) r/GetStudying / r/medicalschool

**Title:** `The problem with doing "hard" practice: most of it's probably not at the right level`

---

Something I used to get wrong about studying: I'd find a hard problem set, grind it, feel productive. Then I'd take a test and realize I was missing foundational things I thought I knew.

The issue wasn't that I was practicing hard material. The issue was that "hard" is relative to what you actually know right now — and I was bad at estimating that.

There's a concept from educational psychology called the Zone of Proximal Development. The version I find useful: learning encodes best when tasks sit just above your current ability level. Too far below (things you already know cold) and you're just doing recall with no new encoding. Too far above (things you have no framework for) and you're guessing without any mental hooks to attach the answer to. The sweet spot is the zone where you genuinely have to work for it but the answer is reachable given what you already know.

The practical implication: **which concepts you practice matters less than whether you're practicing them at the right level.** A student who hammers hard pharmacokinetics problems when they've never really nailed first-order vs zero-order elimination is doing Layer 3 practice without completing Layer 1. They'll score unpredictably and not understand why.

What actually helped me: before starting a new topic section in practice, explicitly locate my weakest prerequisite within that section. Not the hardest concept — the foundation concept I'd been assuming I understood because I could recognize the answer when I saw it. Recognition and recall are different skills. Recognition is the feeling of familiarity with an answer when it's in front of you. Recall is generating the answer from nothing. Most studying builds recognition without testing recall.

The quick diagnostic: close your notes and explain the concept from scratch in one paragraph. If you can't do it fluently, you have a recall gap. That's the thing to fix before progressing to application problems.

I built this into OpenTutor (the tool I'm working on — open source, runs locally with Ollama). It tracks a mastery probability per concept and adjusts question difficulty accordingly: recall questions when mastery is low, application problems as it builds, edge-case traps when you're actually solid. But the manual version — consciously asking "am I practicing at the right level for this concept right now?" — is a habit worth building regardless of what tool you use.

## e) Dev.to / Hashnode — Technical Article

**Title:** How I implemented Vygotsky's Zone of Proximal Development in my AI tutor's question generator

---

Every question-generation pipeline I've seen has the same implicit assumption: difficulty is a prompt parameter. You tell the model "generate an easy question" or "generate a hard question" and it does its best. The problem is that "hard" is not an intrinsic property of a question — it's a relationship between the question and the student's current knowledge state. A question about mitochondria is trivially easy for a biology PhD and genuinely hard for a high school sophomore. Passing "difficulty: hard" to an LLM ignores that relationship entirely.

Vygotsky's Zone of Proximal Development (ZPD) is the relevant theoretical frame. The ZPD is the region between what a student can do independently and what they can do with guidance. Vygotsky's insight — and the experimental literature backs it — is that tasks in this zone produce better learning outcomes than tasks below it (no challenge, no encoding) or above it (cognitive overload, the student guesses rather than learns). The implementation challenge is: how do you measure "current ability" precisely enough to place the difficulty target in the right zone?

In OpenTutor, the answer is Bayesian Knowledge Tracing (BKT) per concept, feeding into a three-tier difficulty system. Here's how it works end to end.

### Step 1: Estimate per-student BKT parameters from answer history

BKT has four parameters: P(L0) — prior mastery, P(T) — learning rate, P(G) — guess probability, P(S) — slip rate. Standard educational software uses global defaults. OpenTutor estimates them per student from their actual answer history:

```python
def estimate_params(
    results: list[bool],
    question_type: str | None = None,
) -> BKTParams:
    # P(G) adjusts by question type — guessing matters very differently
    # across formats
    p_g = _DEFAULT_P_G
    if question_type:
        qt = question_type.lower()
        if qt in ("tf", "true_false"):
            p_g = 0.50   # Can guess your way through true/false
        elif qt in ("mc", "multiple_choice"):
            p_g = 0.25   # Standard 4-option MCQ
        elif qt in ("short_answer", "fill_blank", "free_response"):
            p_g = 0.05   # Hard to guess a free-response answer

    # P(L0) seeds from first-attempt: if they got it right immediately,
    # they probably had some prior knowledge
    p_l0 = 0.30 if results[0] else 0.05

    # P(T) estimates from wrong → correct transitions
    transitions = 0
    opportunities = 0
    for i in range(1, len(results)):
        if not results[i-1] and results[i]:
            transitions += 1
        opportunities += 1
    p_t = min(0.5, transitions / max(opportunities, 1) * 1.5) if opportunities else _DEFAULT_P_T

    return BKTParams(p_l0=p_l0, p_t=p_t, p_g=p_g, p_s=_DEFAULT_P_S)
```

Why P(G) by question type matters: a wrong answer on a true/false question is weak evidence of not knowing (50% chance they'd be wrong even if guessing). A wrong short-answer is near-proof of a gap. Running them through the same BKT formula with the same P(G) produces systematically miscalibrated mastery estimates — true/false wrong answers look more informative than they are, free-response correct answers look less informative.

### Step 2: Map mastery probability to a difficulty tier

Once BKT gives a mastery probability P(L) per concept, `difficulty_selector.py` maps it to a three-tier system based on ZPD:

```python
MASTERY_LOW_THRESHOLD = 0.4     # Below → Layer 1 (recall)
MASTERY_HIGH_THRESHOLD = 0.7    # Above → Layer 3 (traps)

DIST_LOW_MASTERY  = {1: 0.6, 2: 0.3, 3: 0.1}
DIST_MID_MASTERY  = {1: 0.2, 2: 0.5, 3: 0.3}
DIST_HIGH_MASTERY = {1: 0.1, 2: 0.3, 3: 0.6}

def recommend_difficulty(
    mastery_score: float,
    gap_type: str | None = None,
    fsrs_state: str | None = None,
) -> DifficultyRecommendation:
    # Gap type overrides mastery — when there's a diagnosed gap,
    # trust the gap classifier over the aggregate score
    if gap_type == "fundamental_gap":
        return DifficultyRecommendation(
            primary_layer=1,
            layer_distribution={1: 0.7, 2: 0.3, 3: 0.0},
            rationale="Fundamental gap detected — core recall before advancing.",
            ...
        )
    if gap_type == "transfer_gap":
        return DifficultyRecommendation(
            primary_layer=2,
            layer_distribution={1: 0.2, 2: 0.6, 3: 0.2},
            rationale="Transfer gap — knows concept, struggles with application.",
            ...
        )

    # Mastery-based selection for non-override cases
    if mastery_score < MASTERY_LOW_THRESHOLD:
        return DifficultyRecommendation(primary_layer=1, layer_distribution=DIST_LOW_MASTERY, ...)
    if mastery_score < MASTERY_HIGH_THRESHOLD:
        return DifficultyRecommendation(primary_layer=2, layer_distribution=DIST_MID_MASTERY, ...)
    return DifficultyRecommendation(primary_layer=3, layer_distribution=DIST_HIGH_MASTERY, ...)
```

The distribution (not a hard cutoff) is important. At mid-mastery, the session gets 20% Layer 1, 50% Layer 2, 30% Layer 3. You still see some easy questions (reinforcement) and some hard ones (stretch). Pure Layer 2 would leave the student with nothing to anchor new knowledge against and no challenge to reveal their ceiling.

Gap type overrides mastery entirely. A student might have 0.65 aggregate mastery on a topic but a `fundamental_gap` in a specific prerequisite concept — the classifier detects this from error clustering patterns. When that override fires, they get Layer 1 regardless of the 0.65 score, because the aggregate number is misleading.

### Step 3: Inject the recommendation into the generation agent prompt

The recommendation formats itself for injection into the question-generation agent's system prompt:

```python
def format_for_prompt(rec: DifficultyRecommendation) -> str:
    dist_str = ", ".join(
        f"Layer {k}: {v:.0%}" for k, v in sorted(rec.layer_distribution.items())
    )
    return (
        f"\n[ADAPTIVE DIFFICULTY GUIDANCE]\n"
        f"Recommended primary layer: {rec.primary_layer}\n"
        f"Distribution: {dist_str}\n"
        f"Rationale: {rec.rationale}\n"
        f"Note: This is a recommendation based on the student's knowledge state. "
        f"You may adjust if the student explicitly requests a different difficulty.\n"
    )
```

Any agent that generates practice content — quiz generator, flashcard reviewer, exercise planner — calls `get_recommendation_for_node()` from the DB and prepends this block to its system prompt. This means ZPD-aware difficulty is automatic for every generation path without each agent needing to reimplement the mastery logic.

### What this doesn't solve

Two things are still hard. First, the BKT estimator needs enough data to be useful — with fewer than five answers on a concept, the parameter estimates are noisy and the system falls back to conservative defaults. New topics always start with a few calibration questions that are intentionally mixed in difficulty. Second, the gap classifier that triggers overrides (fundamental vs. transfer vs. trap vulnerability) is still heuristic-based. It looks at error patterns from the last 10 answers and applies rules. It gets wrong answers confused with transfer gaps fairly often. A better classifier here would require more training data than we have.
