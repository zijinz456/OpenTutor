## a) Hacker News — Show HN

**Title:** `Show HN: OpenTutor – routes LLM calls by complexity score, no extra inference needed`

---

We're building an open-source local-first AI learning platform (MIT, Docker Compose one-liner, Ollama by default) and wanted to share the approach we took to avoid a common failure mode in AI apps: sending every request—including "ok thanks" and "what's next?"—to the frontier model.

The solution is a heuristic complexity scorer in `services/llm/complexity.py` (196 lines) that runs synchronously before each LLM call with zero extra inference overhead. It produces a score on a 0-780 scale across five dimensions: message length (0-150 pts), classified intent (0-300 pts), active learning scene (0-100 pts), conversation depth (0-80 pts), and complexity-marker regex patterns (0-100 pts, capped). The markers include 14 patterns for English ("prove", "derive", "step-by-step", "optimize") and 4 for Chinese (证明, 比较, etc.) since we support bilingual sessions. Scores below 150 go to the fast tier, 150-499 to standard, 500+ to frontier. A simple preference change ("switch to dark mode") scores ~50 and never touches the frontier model. A multi-step proof request in an exam-prep scene with a long question and "prove" in the text can easily hit 500+.

On top of the complexity router, each provider has a circuit breaker (`services/llm/circuit_breaker.py`, 83 lines) with progressive cooldown steps of [5, 10, 20, 60] seconds and auto-opens after 3 consecutive failures, resetting after 120 seconds. The `ProviderRegistry` walks a typed fallback chain: model variant hints (large/small/fast) first, then primary, then ordered fallback. The registry also runs a background health probe loop every 30 seconds, caching latency-annotated results, so the fallback decision uses recent probe data rather than stale failure flags. Stack: FastAPI + Next.js 16 + SQLite, 65 test files, 961 pytest passing. MIT. https://github.com/zijinz456/OpenTutor

## b) r/LocalLLaMA

**Title:** `How we handle provider fallback + circuit breaker for a local AI tutor (Ollama-first, MIT)`

---

Been building OpenTutor, an open-source local AI tutor that runs with Ollama by default, and wanted to share the multi-provider routing layer since I haven't seen this pattern in many local LLM projects.

The core problem: local Ollama is great but occasionally drops requests when loading a model cold, running on constrained hardware, or hitting memory limits mid-session. When that happens mid-tutoring-session, the app needs to either retry gracefully or fall back to a cloud provider without the user noticing.

The `CircuitBreakerMixin` in `circuit_breaker.py` (83 lines) tracks health per provider. On failure it applies progressive cooldown: first failure = 5s cooldown, second = 10s, third = 20s, fourth+ = 60s. After 3 consecutive failures it opens the circuit and refuses to route to that provider for 120 seconds, then auto-resets with a single probe. Here's the mark_unhealthy logic:

```python
COOLDOWN_STEPS = [5, 10, 20, 60]
CIRCUIT_OPEN_THRESHOLD = 3
CIRCUIT_RESET_TIMEOUT = 120  # seconds

def mark_unhealthy(self, error: str):
    self._healthy = False
    self._consecutive_failures += 1

    if self._consecutive_failures >= CIRCUIT_OPEN_THRESHOLD:
        self._circuit_open = True
        self._circuit_open_time = time.time()
        return

    idx = min(self._consecutive_failures - 1, len(COOLDOWN_STEPS) - 1)
    cooldown = COOLDOWN_STEPS[idx]
    self._cooldown_until = time.time() + cooldown
```

The `ProviderRegistry` in `router.py` (399 lines) layers on top: it tries model variant hints first (register a "fast" variant pointing to `llama3.2:3b` and a "standard" pointing to `llama3.1:8b`), then the configured primary, then walks the fallback chain. A background async probe loop runs every 30s and caches latency-annotated health results so the fallback decision doesn't rely on stale in-memory failure flags.

In practice: Ollama + `llama3.2:3b` is the default with no API key needed. RAM usage for 3b is typically 2-3GB depending on quant. If you want better quality for complex content, swap to `llama3.1:8b` for ~5-6GB. Cloud fallback to DeepSeek or OpenAI only kicks in if you configure those keys AND Ollama is circuit-open. Everything runs locally by default. Docker Compose one-liner, MIT. https://github.com/zijinz456/OpenTutor

## c) r/Anki

**Title:** `We upgraded from FSRS-4.5 to FSRS-5/6 (21 params) and the difference is subtle but real`

---

OpenTutor is an open-source local AI learning platform with a built-in spaced repetition system. When we first implemented FSRS, we used the FSRS-4.5 defaults (17 parameters). We've since upgraded to the FSRS-5/6 formulation (21 parameters), and I want to document what actually changed and why it matters for an AI tutoring context.

**What changed from 4.5 to 5/6:**

The retrievability formula is the most user-visible change. FSRS-4.5 uses: `R(t) = 0.9^(t/S)` — a fixed exponential with a hardcoded 90% recall target. FSRS-5/6 uses: `R(t) = (1 + factor·t/S)^(-decay)` where `decay = w[20]` is now a trainable parameter (default 1.0 for backward compatibility). At decay=1.0 you get the same behavior as 4.5, but once you have per-user data, decay can be fit per student — a student with steeper forgetting curves gets a lower decay, compressing the scheduled intervals to compensate.

```python
def _retrievability(elapsed_days: float, stability: float, w: list[float] = DEFAULT_W) -> float:
    if stability <= 0:
        return 0.0
    decay = w[20] if len(w) > 20 else 1.0
    factor = 9 * decay
    return pow(1 + elapsed_days / (factor * stability), -decay)
```

The second meaningful change is same-day review handling. FSRS-4.5 has no concept of intra-day reviews — if you review a card three times in the same morning, the stability formula treats each like a scheduled interval review, which inflates stability unrealistically. FSRS-5/6 adds w[17-19] and a separate `_same_day_stability` path: `S' = S * exp(w17 * (G - 3 + w18)) * S^(-w19)`. The `-w19` exponent means high-stability cards gain much less from repeated same-day reviews than low-stability cards — appropriate because high-stability cards don't need cramming.

Difficulty initialization also changed. FSRS-4.5: `D0 = w4 - (G - 3) * w5` (linear in rating). FSRS-5/6: `D0 = w4 - exp(w5 * (G - 1)) + 1` (exponential). The exponential form means a "Hard" initial rating (G=2) starts significantly easier than a "Good" (G=3) but not by a fixed linear offset — the difference widens for lower ratings.

How does this compare to Anki's SM-2? SM-2 uses a fixed ease factor starting at 2.5 and adjusts by ±0.15 per review, with no retrievability model at all — just interval multipliers. FSRS at any version is categorically different in that it tracks a continuous probability of recall rather than a step-function ease. In practice, FSRS-4.5 already outperforms SM-2 significantly (~30%+ better recall per study time according to the fsrs4.5 paper). FSRS-5/6 adds the trainable decay parameter, same-day handling, and exponential difficulty init — the gains are incremental on top of that already large gap vs SM-2.

Our full FSRS implementation is in `apps/api/services/spaced_repetition/fsrs.py` (304 lines). MIT, runs locally. https://github.com/zijinz456/OpenTutor

**Title:** `I kept scoring 60s on my USMLE Step 1 practice blocks even though I'd read everything — here's the actual problem`

---

Third-year med student here. I was doing everything "right": I read First Aid cover to cover, watched all the Sketchy videos, did 20 UWorld questions a day. My practice block scores were stuck at 62-65%. I was putting in 8 hours a day and going nowhere.

The actual problem wasn't the content — it was the order. I kept reviewing cardiology pharm before I had a solid grip on basic receptor pharmacology. I'd get the mechanism of beta-blockers wrong on a question, then realize I'd never actually solidified G-protein coupled receptor signaling. The knowledge had gaps shaped like prerequisites.

I switched to using OpenTutor (open-source, runs locally, free) for my weak areas. The thing that helped most wasn't the flashcards — it was the knowledge graph. After uploading my annotated First Aid PDFs and Pathoma notes, the system built a concept dependency map: "beta-1 adrenergic receptor" → "chronotropy and inotropy" → "metoprolol mechanism" → "heart failure pharm". When I got a beta-blocker question wrong, the graph didn't just schedule that card for re-review — it surfaced the prerequisite concepts first.

Three things that actually moved my score:

**1. Upload your weak-area annotated notes, not the whole textbook.** I got better results from 40 pages of dense personal annotations than from 800-page PDFs. The AI tutor cites specific passages, and if your source is focused, so is the tutor.

**2. Do timed 10-question blocks, not open-ended question sessions.** The quiz block adapts difficulty in real time based on your error patterns, but it needs a clean signal. Stopping after 40 minutes of distracted studying poisons your difficulty calibration.

**3. Use the wrong-answer block, not your performance summary.** The wrong-answer tracker shows diagnostic feedback for each miss with the specific concept the question was testing. I reviewed that list before every new Qbank session instead of looking at broad category percentages. Much more actionable.

Eight weeks later I'm consistently scoring 72-76% on NBME practice forms. Not claiming causality — I also changed my sleep schedule and dropped down to 6 hours of studying instead of 8. But the prerequisite-first review ordering was the structural change that made everything else click.

OpenTutor is free, MIT licensed, runs on your laptop with Ollama (no subscription, no data leaving your machine): https://github.com/zijinz456/OpenTutor

## e) Dev.to / Hashnode — Technical Article

**Title:** `How I built a behavior-driven feature unlock system for my AI tutor (and why it's just 74 lines of TypeScript)`

---

One of the more interesting design decisions in building OpenTutor — an open-source local-first AI learning platform — was how to handle feature progressive disclosure. The workspace has 12 block types: notes, quiz, flashcards, knowledge graph, study plan, analytics, wrong-answer tracker, forecast, and more. Not all of them should be visible on day one.

Here's the problem with the conventional approach: most apps gate features behind subscriptions or onboarding steps. We wanted to gate them behind *actual learning behavior* — don't show the knowledge graph until you have enough source material to make it meaningful; don't show the forgetting forecast until you have enough practice history for the model to be accurate.

### The unlock conditions

Each block has a specific unlock condition derived from the product spec:

```typescript
const ALWAYS_AVAILABLE: BlockType[] = [
  "notes", "quiz", "flashcards", "chapter_list", "review",
];

export function isBlockUnlocked(
  type: BlockType,
  ctx: UnlockContext,
): { unlocked: boolean; reason?: string; unlockHint?: string } {
  if (ALWAYS_AVAILABLE.includes(type)) {
    return { unlocked: true };
  }

  switch (type) {
    case "knowledge_graph":
      return ctx.sourceDocCount >= 3
        ? { unlocked: true }
        : { unlocked: false, reason: "Unlocks after uploading 3+ source documents",
            unlockHint: `${ctx.sourceDocCount}/3 documents` };

    case "forecast":
      return ctx.practiceAttempts >= 50
        ? { unlocked: true }
        : { unlocked: false, reason: "Unlocks after 50+ practice attempts",
            unlockHint: `${ctx.practiceAttempts}/50 attempts` };

    case "wrong_answers":
      return ctx.hasWrongAnswer
        ? { unlocked: true }
        : { unlocked: false, reason: "Unlocks after your first incorrect answer",
            unlockHint: "Answer a question incorrectly to unlock" };

    case "agent_insight":
      return ctx.sessionCount >= 3
        ? { unlocked: true }
        : { unlocked: false, reason: "Unlocks after 3+ learning sessions",
            unlockHint: `${ctx.sessionCount}/3 sessions` };
    // ...
  }
}
```

The full file is 74 lines (`apps/web/src/lib/block-system/feature-unlock.ts`). The `unlockHint` field is what the UI renders in the locked block overlay — a progress indicator like "2/3 documents" instead of a generic "locked" message. The reason field shows on hover. This means users always know *exactly* what they need to do to unlock the next capability, which dramatically reduces the friction of progressive disclosure.

### Why the thresholds are what they are

The knowledge graph threshold (3 documents) is based on graph density. With 1-2 documents the concept graph is too sparse to show meaningful prerequisite relationships — you get 20 nodes with 5 edges and the visualization is essentially useless. At 3+ documents the graph becomes dense enough that the LOOM extraction produces actionable concept clusters.

The forecast threshold (50 practice attempts) is an FSRS data quality constraint. The forgetting forecast uses `estimate_forgetting_cost` from `fsrs.py`, which sums `(1 - retrievability)` across overdue cards. With fewer than 50 attempts, you don't have enough card stability estimates for the forecast to be meaningful — the numbers just oscillate based on 3-4 cards. At 50+ attempts you have stable per-card difficulty and stability parameters that make the "expected cards forgotten today" number trustworthy.

### Routing complexity to the right model tier

One thing that took longer to get right was not serving every tutor request from the same model. The complexity scorer in `services/llm/complexity.py` routes without an extra inference call:

```python
_COMPLEXITY_PATTERNS = [
    (re.compile(r"\bprove\b", re.IGNORECASE), 50),
    (re.compile(r"\bderive\b", re.IGNORECASE), 40),
    (re.compile(r"\bstep[- ]by[- ]step\b", re.IGNORECASE), 40),
    (re.compile(r"\banalyze\b|\banalyse\b", re.IGNORECASE), 30),
    # ... 10 more patterns + CJK equivalents
]

FAST_THRESHOLD = 150       # "ok", "next", "what time should I study?"
FRONTIER_THRESHOLD = 500   # "prove that the chain rule holds for..."
# 150 <= score < 500 → standard
```

The fast tier (score < 150) handles preference changes, greetings, and navigation — things like "switch to dark mode" or "what's the next topic?" The frontier tier (score ≥ 500) handles multi-step proofs, complex curriculum planning, and code execution. Everything else — the 80% of tutoring interactions — goes to the standard tier, which for local setups is typically `llama3.1:8b` while the fast tier uses `llama3.2:3b`.

### What I'd do differently

The unlock conditions are currently hardcoded in a switch statement. This works fine for 12 block types but doesn't scale if we add a plugin system for custom blocks. The right abstraction is a config object: `{ threshold: 3, field: 'sourceDocCount', operator: 'gte' }` that gets evaluated generically. We haven't needed it yet, so the switch statement stays — but it's the first thing I'd refactor if we hit 20+ block types.

The behavior tracking (`UnlockContext`) also currently lives in localStorage, which means it's per-browser. If you use OpenTutor on two machines, your unlock state doesn't sync. This is a deliberate local-first trade-off for the beta — the backend has the real data, but we haven't plumbed the context fetch yet for non-blocking UI reasons.
