## a) Hacker News — Show HN

**Title:** `Show HN: OpenTutor – token-aware session compaction for long-running AI tutor sessions`

---

Most AI chat products treat context management as an afterthought until they hit the wall. For a tutoring tool the problem is worse than usual: study sessions are long, the conversation history is semantically dense (concepts build on each other), and losing context mid-session actively degrades the tutoring quality. A naive "drop oldest messages" strategy breaks the tutor's ability to remember what you were confused about ten minutes ago.

OpenTutor handles this with a two-layer context window guard in `services/agent/compaction.py` (370 lines) and `services/agent/context_trimming.py` (191 lines). Before every agent call, the system estimates total session tokens — system prompt + conversation history + tool schemas + per-message framing overhead — using tiktoken with a character-based fallback for CJK content. At 70% context window fill, it runs an LLM summarization pass over older messages, keeping the most recent 6 turns verbatim and replacing everything older with a structured summary (Goals / Progress / Decisions / Next Steps / Key Facts, capped at 300 words). The summary prompt is designed for incremental updates: if compaction has already run, the new pass integrates new messages into the existing summary rather than regenerating from scratch, so the summary stays coherent rather than accumulating drift. At 90% fill, it falls through to an emergency trim — pure token-count-based truncation, oldest first.

The second part is intent-specific token budgeting. The context builder allocates tokens across three categories — RAG results, conversation memory, and session history — and the allocations shift based on what the student is doing. "learn" mode gets 4000 tokens for RAG (the model needs source material) and 1500 for memory. "review" mode gets 2500 for memory and only 2000 for RAG (you're reviewing what you already know; the source material matters less than your prior errors). "quiz" mode gets 3500 for RAG and only 1000 for history (each question is relatively self-contained). These are fixed allocations tuned by hand; the thresholds for compaction (70%/90%) and the model-specific context window sizes are stored in `MODEL_CONTEXT_WINDOWS` (covers 20+ models from Ollama local models through Gemini 1.5 Pro's 2M token window).

65 test files, 668 test functions. FastAPI + Next.js 16 + SQLite, Docker Compose, MIT. GitHub: https://github.com/zijinz456/OpenTutor

## b) r/LocalLLaMA

**Title:** `I use llama3.2:3b to generate search queries before the main model answers — improves retrieval a lot`

---

Here's a pattern that's been useful in OpenTutor: when a student asks a question, don't just run one retrieval pass. Use your fast local model to generate 3 different phrasings of the question first, run retrieval on all of them in parallel, then fuse the results before sending anything to the main model.

The problem it solves: if a student asks "why does my heart rate go up when I'm scared?", a single vector search will find the closest semantic match. But "autonomic nervous system fight-or-flight response", "sympathetic activation and heart rate", and "epinephrine cardiac effects" all retrieve meaningfully different chunks — and the actual answer is improved by having all three.

The implementation (`services/search/rag_fusion.py`, 143 lines) sends query generation to `get_llm_client("fast")` — which in a local setup maps to llama3.2:3b. The fast model generates the variants in ~0.3–0.5s. Then retrieval runs in parallel for each variant. Reciprocal Rank Fusion (RRF) combines the result lists: `score = 1 / (k + rank)` for each document's position in each ranked list, summed across all lists. Documents that appear consistently across multiple query variants float to the top.

```python
# RRF: score each doc by rank in each result list
# k=60 is the standard constant
def rrf_score(doc_id: str, ranked_lists: list[list[str]], k: int = 60) -> float:
    total = 0.0
    for ranked in ranked_lists:
        if doc_id in ranked:
            rank = ranked.index(doc_id) + 1  # 1-indexed
            total += 1.0 / (k + rank)
    return total
```

In practice: question answering with RAG-fusion retrieves concepts the single-query approach missed ~30% of the time (informal measurement, not a rigorous benchmark). The main model gets more complete context and cites more sources per answer.

The fast-tier query expansion adds about 0.4s total overhead per request. If the fast model fails (circuit open, Ollama not running), it falls back to direct single-query retrieval — no hard dependency on the expansion step.

Setup is `LLM_PROVIDER=ollama` + `LLM_MODEL=llama3.2:3b`, three commands, Docker Compose. MIT. GitHub: https://github.com/zijinz456/OpenTutor

## c) r/Anki

**Title:** `Getting a multiple-choice question right is weak evidence you've learned something — here's the math`

---

This is about one of the problems I ran into building OpenTutor's mastery tracker and why it changed how I think about practice question selection.

Anki's scheduler treats every card review as binary: you either remembered it or you didn't. The rating buttons (Again / Hard / Good / Easy) adjust the interval, but they don't account for the fact that a correct answer on a true/false question tells you much less than a correct answer on a free-response question.

OpenTutor uses BKT (Bayesian Knowledge Tracing) for mastery estimates, and the key difference is question-type-aware guess/slip parameters. The code (`services/loom_mastery.py`, 361 lines):

```python
BKT_PARAMS: dict[str, tuple[float, float]] = {
    "mc": (0.25, 0.10),            # MCQ: 25% guess (1/4 options)
    "tf": (0.50, 0.10),            # True/False: 50% guess
    "short_answer": (0.05, 0.10),  # Short answer: very low guess
    "free_response": (0.05, 0.10), # Free response: very low guess
    "fill_blank": (0.10, 0.10),    # Fill-in-blank: low guess
}

def _bkt_update(prior: float, correct: bool, question_type: str | None) -> float:
    guess, slip = BKT_PARAMS.get(question_type or "", (0.15, 0.10))
    if correct:
        # P(Learned | Correct) = P(L)·(1-slip) / [P(L)·(1-slip) + (1-P(L))·guess]
        posterior = prior * (1 - slip) / (prior * (1 - slip) + (1 - prior) * guess)
    else:
        # P(Learned | Incorrect) = P(L)·slip / [P(L)·slip + (1-P(L))·(1-guess)]
        posterior = prior * slip / (prior * slip + (1 - prior) * (1 - guess))
    return posterior + (1 - posterior) * 0.10  # learning transition
```

What this means practically:

- If your prior mastery is 0.30 and you get an MCQ correct: posterior ≈ 0.55. Not much movement, because there was a 25% chance you were guessing.
- If your prior mastery is 0.30 and you get a free-response correct: posterior ≈ 0.82. Much stronger update, because guessing a free-response right is rare.
- If your prior mastery is 0.80 and you get a true/false wrong: posterior ≈ 0.47. Significant drop — unexpected failure at high mastery is a strong signal.

The practical implication: if you only use MCQ for self-testing, your mastery estimate converges slowly because every correct answer is ambiguous. Free-response and cloze/fill-blank produce much faster mastery signal. FSRS's stability value is then updated per concept, so concepts you've answered in harder question formats get longer review intervals faster.

Anki doesn't currently do this — it doesn't know what question type produced the rating. The scheduler treats a "Good" on a multiple-choice card and a "Good" on a free-recall card the same way.

## d) r/GetStudying / r/medicalschool

**Title:** `Self-testing with the "wrong" question type is probably slowing you down`

---

I spent a long time doing most of my self-testing with multiple-choice questions. They're fast, they feel productive, and most question banks use them. Then I started actually tracking my performance on different question formats and noticed something uncomfortable: I could consistently score 75-80% on MCQ for topics where I would completely blank on short-answer versions of the same concept.

The gap is the problem. MCQ with 4 options gives you a 25% floor — you'll guess correctly a quarter of the time with zero knowledge. That means your 75% score is actually about 67% signal and 33% noise. More importantly, "which of these four is the answer" is a completely different cognitive operation than "explain how X leads to Y." One requires recognition; the other requires reconstruction.

The thing that changed my study approach: I started treating question format as part of the difficulty setting, not just a delivery preference. For any topic I actually need to be able to apply — not just recognize — I started forcing myself to write out the explanation before looking at the options. Even on real MCQ practice banks, cover the options, attempt a free recall, then check if your explanation covers the right answer before unblinding.

The order matters:
1. Write what you know about the topic (free recall)
2. Check against options — did you identify the mechanism correctly?
3. If you didn't surface the mechanism unprompted, that's a gap, even if you could have picked the right option

This is slower. It's also the difference between a 75% MCQ score and actually being able to generate the answer in a viva or applied context.

The tool I've been building (OpenTutor) tracks this explicitly — it weights mastery updates differently based on question type, so a free-response correct moves your knowledge estimate more than an MCQ correct. But the habit — defaulting to free recall before looking at options — is something you can do with any question bank right now.

## e) Dev.to / Hashnode — Technical Article

**Title:** How I built a proactive AI study monitor that chooses to stay silent most of the time

---

When I started building OpenTutor's proactive features, my first instinct was to make the system as active as possible. Overdue flashcards? Notify. Goal stalled for a day? Notify. Session gap of 4 hours? Notify. The result was predictable: users ignored everything. When a notification system fires constantly, it trains users to dismiss it before reading.

The fix required a different design philosophy: the system's default should be silence. Intervention requires justification. This article covers how I built the ambient study monitor in OpenTutor — a background agent that observes learning state every 30 minutes and chooses what to do (including nothing).

### The architecture: deterministic signals + LLM deliberation

The agenda service runs continuously and produces ranked `AgendaSignal` objects — deterministic outputs based on FSRS review schedules, goal deadlines, session gaps, and cognitive load scores. These signals are correct but dumb: they don't know that the user just finished a 2-hour session, or that it's 11pm, or that sending a review notification on top of a goal-stall notification in the same tick would be annoying.

The ambient monitor (`services/agent/ambient_monitor.py`, 363 lines) adds an LLM deliberation layer on top. Every 30 minutes, it:

1. Collects the current learning state (session history, overdue items, stalled goals, current time)
2. Serializes the top 10 agenda signals
3. Sends everything to the fast-tier model with a structured decision prompt
4. Executes whatever the model decides — or nothing

```python
AMBIENT_MONITOR_PROMPT = """\
You are the proactive study agent for a student using OpenTutor.
Your job is to decide what (if anything) to do based on the student's current learning state.

## Rules
- Only intervene when there is a clear benefit to the student.
- Prefer silence over spam. If the student is on track, do nothing.
- Never send more than 1 notification per 6 hours per course.
- Consider time of day: avoid actions during likely sleep hours (11pm-7am).
- For review sessions: only trigger when forgetting cost is high enough.
- For goal pursuit: only trigger when a goal has stalled for 2+ days.

## Available actions
- "silent": Do nothing. The student is on track.
- "notify": Send a motivational or reminder notification.
- "prepare_review": Queue a spaced-repetition review session.
- "trigger_goal_pursuit": Start or resume goal pursuit workflow.
- "generate_report": Generate a daily/weekly learning brief.
- "trigger_guided_session": Start a proactive guided learning session.
- "propose_content_generation": (Tier 2 — requires user approval) Propose generating new content.
```

The prompt lists the rules first, not the capabilities. This matters: when you enumerate capabilities before constraints, models tend toward action. Rules-first nudges toward restraint.

### What state gets sent to the model

```python
async def gather_learning_state(user_id, signals, db) -> dict:
    return {
        "current_hour": now.hour,               # For time-of-day gating
        "hours_since_last_study": ...,          # Session gap
        "overdue_review_items": overdue_count,  # FSRS overdue count
        "active_goals": len(goals),
        "stalled_goals": [                      # Goals not updated in 2+ days
            {"title": g.title, "days_stalled": ...}
        ],
        "agenda_signals": signal_summaries[:10],  # Top-ranked signals
    }
```

The state is intentionally minimal. I don't send the full session history or course content — just the signals the model needs to make a decision. Smaller context means faster inference and less hallucination surface area.

### The decision response

The model returns a structured JSON object:

```json
{
  "action": "prepare_review",
  "reason": "Student has 14 overdue items and hasn't studied in 26 hours. Review cost is high.",
  "message": "",
  "priority": "high",
  "target_course_id": "3f2a..."
}
```

"silent" is the most common response. In a typical run where the student is active and on track, the model returns silent about 70% of the time. The remaining 30% split across notify (~15%), prepare_review (~10%), and the rest rarely.

### The deliberate design choice: prefer the fallback

If the LLM call fails — model unavailable, Ollama OOMed, circuit breaker tripped — the system falls back to the existing deterministic agenda path. This means the deterministic path is the production baseline, and the LLM layer is an optional enhancement that adds richer decisions when available.

```python
async def run_ambient_monitor(user_id, signals, db):
    state = await gather_learning_state(user_id, signals, db)
    decision = await llm_deliberate(state)

    if decision is None:
        # Fallback: use the top deterministic signal directly
        return await execute_deterministic_fallback(signals, db)

    return await execute_ambient_decision(user_id, decision, db)
```

This is a pattern worth adopting in any AI feature where correctness matters more than sophistication: build the dumb version first, make it reliable, then add the smart layer on top without making the whole thing dependent on it.

### What I'd do differently

The 30-minute polling interval is a blunt instrument. A better design would be event-driven: re-evaluate when something changes (new wrong answer, session ends, goal deadline approaches) rather than on a fixed clock. The fixed interval sometimes fires when nothing has changed, burning a fast-tier model call to return "silent."

The action taxonomy is also underdeveloped. "notify" covers too much — a motivational message after a long gap and an urgent review reminder before an exam are meaningfully different and probably need different delivery mechanisms.
