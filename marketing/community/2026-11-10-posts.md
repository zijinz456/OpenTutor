## a) Hacker News — Show HN

**Title:** Show HN: OpenTutor – grading "select all that apply" without ambiguity

**Body:**

The annoying edge case in multiple-choice grading isn't wrong answers — it's "select all that apply." A student selects A, B, C. The correct answer is A, C. Are they half-right? Do you count the unselected D as correct? Does order matter? Does submitting "A,C" differ from "C,A"? Every quiz platform has quietly picked an answer to these questions, and many get it wrong.

We just shipped explicit multi-select support in OpenTutor (open-source local-first AI tutor, MIT, 3-command Docker start). The grader (`apps/api/services/practice/answers.py`, 27 lines) uses set equality: normalize both the submitted answer and the reference to case-folded label sets, reject empty submissions, reject duplicates, reject any label not in the option dict, then compare. Order never matters. Partial credit is not a thing — a "select all" question requires the complete correct set, same as it would on an actual exam. The frontend submits comma-separated option keys on explicit button click rather than on each checkbox toggle, so the submitted answer is a snapshot of intent, not an intermediate state.

The backend routes `select_all` questions through `grade_select_all_answer` in the submit endpoint (`quiz_submission.py`), which also handles 6 other question types: MCQ, short answer, fill-in-blank, true/false, ordering, and coding (the coding path uses an LLM grader). After grading, wrong answers trigger background tasks: auto-derive a diagnostic follow-up question, detect confusion pairs in the LOOM knowledge graph, and check if the failed concept has unmastered prerequisites that might explain the error. All of this runs locally — no cloud, no API keys required. Repo: https://github.com/zijinz456/OpenTutor

## b) r/LocalLLaMA

**Title:** What local models actually work for AI tutoring — tested on OpenTutor with llama3.2:3b and llama3.1:8b

**Post:**

Been running OpenTutor (MIT, self-hosted AI tutor) locally for a few months and figured I'd share what actually works hardware-wise, since most LLM-in-an-app benchmarks are for chat and ours is heavier.

**What OpenTutor does that plain chat doesn't:**

Each user message goes through intent classification first (a fast-model call), then the main response (routed to the right model tier), then optional background tasks: concept mastery updates to the LOOM knowledge graph, confusion pair detection, prerequisite gap checking. The pipeline is async and the background tasks don't block the response, but the intent classifier + main model is two sequential LLM calls for most teaching requests.

**Hardware tested:**

| Setup | Fast model | Standard model | Teaching response |
|---|---|---|---|
| M2 MacBook Air (8GB) | llama3.2:3b | llama3.2:3b (same) | 3–6s |
| M3 Pro (18GB) | llama3.2:3b | llama3.1:8b | 4–9s |
| RTX 3080 (10GB VRAM) | llama3.2:3b | llama3.1:8b | 2–5s |
| CPU-only (16GB RAM) | llama3.2:3b | llama3.2:3b | 12–20s |

The complexity router (`apps/api/services/llm/complexity.py`, 196 lines) classifies each request into fast/standard/frontier based on five signals — message length, intent, complexity markers ("prove", "derive", "step-by-step"), conversation depth, and whether RAG context is attached. A preference change or simple greeting routes to the 3b; a multi-step derivation routes to 8b+.

**What works at 8GB RAM:**

Stick with llama3.2:3b for everything. Set `LLM_MODEL=llama3.2:3b` and `LLM_MODEL_FAST=llama3.2:3b` in `.env`. Teaching quality is acceptable for most subjects; it struggles with proof-heavy math and dense code explanations. FSRS scheduling, knowledge graph updates, and the workspace blocks all run locally regardless of model quality.

**What breaks at <8GB:**

Don't try to run the ingestion pipeline (PDF → notes + flashcards + quiz questions) on a model that needs to be swapped in and out of RAM. The ingestion does parallel LLM calls; on a RAM-constrained machine, serial mode is slower but works: `INGESTION_PARALLEL=false` in `.env`.

**Recommended minimum:** 8GB RAM, llama3.2:3b for everything. The tutor experience with 3b is not great for hard topics but the spaced repetition, knowledge graph, and quiz tracking work fine regardless of which model answers the question.

## c) r/Anki

**Title:** Why we added strict 1–4 rating validation to our FSRS scheduler (and what happens without it)

**Post:**

We're running FSRS-5/6 (21 parameters, upgraded from 4.5's 17) in OpenTutor, and this week we added an explicit guard: ratings outside 1–4 now raise `ValueError` immediately, before any card state is touched.

```python
def review_card(card: FSRSCard, rating: int, ...) -> FSRSCard:
    if rating not in (1, 2, 3, 4):
        raise ValueError(f"FSRS rating must be 1-4, got {rating!r}")
    ...
```

This matters more than it looks. FSRS uses the rating directly as an index into the initial stability parameters (`w[rating - 1]`, where `DEFAULT_W` has 21 entries). It also drives the difficulty update delta (`rating - 3`) and whether hard penalty (`w[15]`) or easy bonus (`w[16]`) applies. A rating of 0 or 5 produces mathematically valid results — no exception, no crash — but the computed stability and difficulty values are wrong in ways that corrupt that card's future schedule permanently.

In Anki's own implementation this is impossible because the UI only presents 4 buttons. In a programmatic API (which is what we expose), it's easy to send the wrong thing. The fix is 2 lines but it matters because FSRS state mutations are designed to be applied sequentially and there's no "undo last review" operation — a bad review poisons the card's history forward.

The other FSRS detail worth knowing if you're implementing this yourself: the 21-parameter upgrade from 4.5 adds `w17–w19` for same-day reviews and `w20` for the forgetting curve decay. Setting `w20 = 1.0` gives you FSRS-4.5-compatible behavior, so the upgrade is a clean migration. The same-day parameter set (`w17–w19`) means two reviews in one session no longer use the same stability formula as a cross-day review — same-day rereps don't inflate stability the way they did in 4.5.

Full implementation is 310 lines in `apps/api/services/spaced_repetition/fsrs.py`. We also have LECTOR on top (experimental): if a card's concept has unmastered prerequisites in the knowledge graph, the queue de-prioritizes it even if FSRS says it's due today. That's a separate layer and can be disabled if you just want vanilla FSRS behavior.

## d) r/GetStudying / r/medicalschool

**Title:** Switched from highlight-and-hope to select-all questions — here's why it's different

**Post:**

I want to share something that changed how I prep for exams, specifically one type of question that I'd been avoiding.

For most of med school I did MCQ practice — one right answer, four options, pick one. I got decent at it. What I was actually getting good at was elimination. If I could rule out three options, the fourth was right, and I didn't need to know *why* it was right in any deep sense.

Then I started doing "select all that apply" questions. These are brutal if you're a recognizer rather than a retriever. You can't eliminate your way through them. You have to independently evaluate each option — is this a cause of condition X? yes or no, without the other options as anchors. And partial credit doesn't exist on most exams. Getting 3 of 4 right means you got the question wrong.

I started using OpenTutor (free, runs locally on your laptop) which just added proper multi-select quiz support this week. When you're reviewing a topic, the AI generates select-all questions from your uploaded material. The grading is strict — you need the complete correct set, not partial matches. At first I was getting maybe 40% on select-all vs. 75%+ on single-choice questions over the same material.

The gap told me something honest: I'd been building recognition memory, not retrieval. I could recognize the correct answer when I saw it. I couldn't generate the complete correct answer from scratch.

Practical things that helped:

**Before selecting anything, state the question in your own words.** Don't go straight to the options. What would your answer be with no options presented? Then check which options match what you just said.

**Wrong-answer tracking is more useful here than in MCQ.** When you miss a select-all, the system logs which options you got wrong. For me, errors clustered around specific concepts I'd nominally covered but couldn't apply independently. That cluster showed me exactly what I needed to review — not "cardiovascular" broadly, but "which conditions increase preload" specifically.

**Don't treat partial correct selections as progress.** A near-miss on a select-all is still wrong on the actual exam. The goal is complete recall, not 80%.

The tool is free and your material stays on your machine — no account, no cloud. Good for anyone grinding through dense content where multiple things are simultaneously true.

## e) Dev.to / Hashnode — Technical Article

**Title:** How I built deterministic grading for select-all quiz questions in my AI tutor

Grading "select all that apply" sounds simple. It's not. When I added multi-select support to OpenTutor, I ran through a list of edge cases that each required an explicit decision:

- Does "A,C" equal "C,A"? (Order independence)
- Does "A,A,C" count? (Duplicate submission)
- Does submitting "A,X,C" where X isn't a real option count? (Unknown labels)
- What if the reference answer uses slashes instead of commas? (Separator normalization)
- What if the options dict is missing? (Missing metadata)
- Is "A,C" a partial pass if the correct answer is "A,B,C"? (Partial credit)

Here's the entire grading function (`apps/api/services/practice/answers.py`, 27 lines):

```python
def grade_select_all_answer(
    answer: str, reference: str, options: dict[str, str] | None,
) -> bool:
    """Compare complete label sets; reject empty, duplicate and unknown labels.

    Clients submit comma-separated option keys. Reference answers may also use
    slash, semicolon or pipe separators, as accepted by question validation.
    """
    if not options:
        return False
    valid = {key.strip().casefold() for key in options}

    def labels(value: str) -> set[str] | None:
        parts = [part.strip().casefold() for part in re.split(r"[,/;|]", value)]
        unique = set(parts)
        if not all(parts) or len(unique) != len(parts) or not unique <= valid:
            return None
        return unique

    expected = labels(reference)
    submitted = labels(answer)
    return expected is not None and submitted is not None and submitted == expected
```

**The design decisions:**

**Set equality, not partial credit.** `submitted == expected` requires a complete match. This is intentional — "select all that apply" on a real exam gives full marks only for the full correct set. Partial grading would reward guessing all options.

**Reject duplicates.** `len(unique) != len(parts)` catches "A,A,C". A submitted answer with duplicate keys is malformed — the client shouldn't send it, but if it does, we don't silently deduplicate it and mark it correct.

**Reject unknown labels.** `not unique <= valid` checks that every submitted key exists in the question's option dictionary. This catches stale client state submitting an option that no longer exists after a question edit.

**Normalize separators.** The reference answer stored at question-creation time might use `/`, `;`, or `|` as separators (all accepted by question validation). The submitted answer always uses commas. `re.split(r"[,/;|]", value)` handles both sides uniformly.

**Fail closed on missing options.** If the options dict is `None` (missing metadata), return `False` rather than attempting to grade. A wrong-but-not-corrupting result is better than a wrong-and-confident one.

### Hooking it into the submit endpoint

The submit endpoint (`apps/api/routers/quiz_submission.py`) handles 7 question types. `select_all` now gets its own branch:

```python
elif problem.question_type == "select_all":
    is_correct = grade_select_all_answer(
        body.user_answer, problem.correct_answer or "",
        normalize_question_options(problem.options),
    )
```

`normalize_question_options` converts the stored options JSON (which can be a list or dict depending on question generation source) into the `dict[str, str]` the grader expects.

After grading, wrong answers trigger three background tasks without blocking the response:

```python
if not is_correct and wa:
    background_tasks.add_task(_auto_derive_diagnostic, wa.id, user.id)
    background_tasks.add_task(_auto_detect_confusion, problem.course_id, user.id)
```

`_auto_derive_diagnostic` generates a targeted follow-up question for the specific wrong-answer pattern. `_auto_detect_confusion` runs LOOM confusion-pair detection: if the student consistently confuses concept A with concept B, the knowledge graph records that pair and de-prioritizes related flashcards until the distinction is mastered.

### The frontend: explicit submit, not on-toggle

The old MCQ behavior fired a submit on each option click (single select = immediate answer). Multi-select needs an explicit submit button. The state management splits into two paths:

```tsx
const [selectedOption, setSelectedOption] = useState<string | null>(null);   // MCQ
const [selectedOptions, setSelectedOptions] = useState<string[]>([]);        // multi-select

// Multi-select submit handler:
onClick={() => void handleOptionClick(
  optionKeys.filter((key) => selectedOptions.includes(key)).join(",")
)}
```

The submitted value is a snapshot at button-click time, not each intermediate checkbox toggle. This avoids race conditions where a quick double-click could submit before the state fully updates, and it makes the user's intent explicit — they're done selecting, now grade it.

### What's downstream

Correct answers on previously-wrong problems trigger an `effective_review` signal that feeds into the block-decision layer (which controls workspace layout suggestions). The LOOM knowledge graph updates concept mastery for each `knowledge_point` tagged on the question. If the student fails and there are unmastered prerequisites in the graph, the response includes a `prerequisite_gaps` list pointing to the concepts that likely need review first.
