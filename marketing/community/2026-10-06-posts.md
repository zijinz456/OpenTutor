## a) Hacker News — Show HN

**Title:** Show HN: Real-time cognitive load detection from 12 behavioral signals in an AI tutor

**Body:**

Most AI tutors send the same kind of response regardless of whether the student is cruising through a concept or quietly drowning. The obvious fix — "detect if the user seems confused" — is slippery when you put it in a prompt, because it relies on the LLM to infer something the data already tells you directly. I went a different route: compute a 0.0–1.0 cognitive load score from behavioral signals on every turn, then inject it as a structured value into the tutor's context.

The implementation is in `apps/api/services/cognitive_load.py` (488 lines across 4 modules: main scorer, calibrator, NLP affect, and a tuning interface, 1,110 lines total). It aggregates 12 signals with explicit weights: text-based fatigue (0.16), session length (0.08), unmastered error count (0.14), message brevity (0.04), help-seeking keyword presence (0.10), quiz accuracy (0.10), answer hesitation time (0.06), NLP affect analysis (0.10), relative-baseline calibration (0.08), wrong-answer streak (0.05), message gap duration (0.05), repeated errors on the same problems (0.04). The weights sum to exactly 1.0. The NLP affect call is expensive (~500ms), so it runs every 3 messages and caches its result in between. The calibrator maintains a per-user rolling baseline so brevity, help-seeking, and message-gap signals are relative to that user's normal behavior rather than a global constant. The score feeds into the Socratic engine (which skips open-ended questioning when load > 0.7) and into the tutor's depth-selection logic.

This is part of OpenTutor — a self-hosted, local-first adaptive learning workspace. The broader system: 12 composable learning blocks, three specialist agents (Tutor, Planner, Layout), FSRS 4.5 spaced repetition, a LOOM knowledge graph, and LECTOR for knowledge-graph-aware review prioritization. Runs on Ollama by default (`llama3.2:3b`), 10+ provider support, 3-command Docker start. Still a public beta — the signal weights are hand-tuned, not learned, and per-user weight optimization is on the roadmap. MIT licensed. Curious whether anyone here has tried similar behavioral signal approaches and what signals they found predictive.

## b) r/LocalLLaMA

**Title:** My local AI tutor makes 2 LLM calls per turn — a small one to classify, a large one to respond. Here's why.

**Body:**

Hey — sharing a pattern from OpenTutor (local-first AI tutor, Ollama by default) that I think generalizes to anyone building multi-step agents on local hardware.

**The pattern: tiered LLM calls**

The Socratic questioning engine (`apps/api/services/agent/socratic_engine.py`, 287 lines) uses two separate LLM calls per turn:

1. **Classification call** — fast/small model, single-word output: `correct`, `partial`, `wrong`, `confused`, or `no_response`. This determines the student's response quality and drives the state machine transition. ~200-400ms on llama3.2:3b.

2. **Generation call** — large model, actual tutor response. This gets a prompt directive based on current state (PROBE/CLARIFY/CONFRONT/SCAFFOLD/CONFIRM) and the cognitive load score.

The LLM router (`apps/api/services/llm/`) supports model-size hints: `"fast"`, `"small"`, `"large"`. The classifier always requests `"fast"`. The tutor and planner agents request `"large"`. The router resolves these to whatever healthy model you've registered under that variant via `.env`. So on a 16GB machine you can run llama3.2:3b as the classifier and llama3.1:8b as the main tutor without changing the application code.

**Why not one call?**

One combined "classify AND respond" call works in demos but drifts in long sessions — the classification logic can get absorbed into the response generation rather than being a reliable gate. A single-word output from a small model is essentially deterministic and fast. The large model's job stays clean: given a specific directive and a load score, produce the appropriate pedagogical response.

**Rough numbers on Apple M2 16GB (llama3.2:3b classifier / llama3.1:8b tutor):**

- Classification call: ~300-500ms
- Tutor response: ~4-8s
- Total per turn: ~5-9s

**Provider setup in .env:**

```
LLM_PROVIDER=ollama
LLM_MODEL=llama3.1:8b
LLM_MODEL_FAST=llama3.2:3b
```

No API keys needed. The circuit breaker still applies to each model variant independently — if the 8b model is slow, the fast classifier still works.

## c) r/Anki

**Title:** My open-source flashcard scheduler reviews related concepts together and checks prerequisites first — here's how it works

**Body:**

I've been building OpenTutor, which uses FSRS 4.5 for flashcard scheduling (same algorithm as current Anki). I want to share the layer I added on top: LECTOR, a knowledge-graph-aware review prioritization system based on this paper: https://arxiv.org/abs/2508.03275

**What FSRS alone doesn't handle**

FSRS is excellent at scheduling individual cards. What it doesn't know: that you probably shouldn't review "Krebs cycle" before "acetyl-CoA" if you have low mastery on the latter. Or that "meiosis" and "mitosis" have high semantic interference and benefit from contrast review. Cards are scheduled individually; the system doesn't know about the concept relationships the cards live in.

**What LECTOR adds**

LECTOR runs after FSRS computes what's due. It re-ranks and groups using 7 priority factors, each with a configurable weight:

1. **Low mastery boost** — concepts below the mastery threshold get higher priority
2. **Never practiced** — newly generated flashcards from uploaded material
3. **Time decay** — FSRS stability check; `days_since / stability_days` captures how far past due a concept is
4. **Prerequisite at risk** — if concept A is a prerequisite for concept B, and A's mastery is below threshold, A's priority is boosted regardless of B's schedule
5. **Confusion pair** — if two concepts are in the `confused_with` edge type (extracted during ingestion), they're reviewed together in a contrast session
6. **FSRS retrievability** — uses the full FSRS-5/6 formula to compute `R = (1 + t/9S)^(-1)` for overdue cards; `(1 - R)` boosts priority
7. **Proactive interference** — edges with `weight > 0.6` in the confusion graph trigger a review even before you've made a mistake, because the system knows the concepts are likely to interfere

**The contrast session**

When two "confused_with" concepts are flagged, instead of reviewing them separately, the UI puts them side by side with the explicit frame: "review these together — they're often confused." This is the part that feels most different from standard Anki use. You're reviewing pairs under contrast rather than each card in isolation.

**What Anki does better**

Anki has a mature optimizer with years of community review data. LECTOR's weights are currently global defaults, not trained per-user. If you have strong opinions about specific prerequisite relationships, you can edit the knowledge graph manually — but it won't auto-tune to your retention patterns the way Anki's optimizer does.

The full LECTOR implementation is `apps/api/services/lector.py` (344 lines), MIT licensed.

**GitHub:** https://github.com/zijinz456/OpenTutor

For Anki power users: do you ever manually reorder your review queue to check a foundational card before a more advanced one? Or do you rely on Anki's scheduling and just trust it?

## d) r/GetStudying / r/cscareerquestions

**Title:** How I used a knowledge graph to stop studying algorithms in the wrong order

**Body:**

Software dev here, grinding for FAANG interviews after a few years of frontend work. My weak spot was the classic graph/tree problems — I could implement BFS but couldn't adapt it to Dijkstra. I'd watch a Dijkstra walkthrough, understand the video, then fail the problem on Leetcode the next day.

The issue wasn't motivation or time — it was that I kept hitting concepts that depended on prerequisites I thought I had but actually didn't. I knew what a priority queue was in theory but had never implemented one under time pressure. So when Dijkstra needed it as a building block, I'd stall.

I started using a tool called OpenTutor for the algorithms section of my prep. You upload study material — I used a few PDF notes from a university algorithms course plus Cracking the Coding Interview chapters — and it builds a knowledge graph of the concepts and their dependencies. The visual was genuinely useful: I could see that I had "medium" mastery on BFS (understood traversal, struggled with variants) but "low" on min-heap operations, and that Dijkstra had edges to both of those.

The review scheduler factors in prerequisites. If you have low mastery on a prerequisite, it bumps that concept's review priority even if the dependent concept is "due." So instead of jumping to Dijkstra drills, it kept pulling me back to priority queue operations until those stabilized. Annoying in the moment, correct in retrospect.

The other thing that helped: the wrong-answer tracker logs every missed problem with the concept it belongs to. After a week I could filter my weak concepts and drill exactly those. I went from around 45% on medium-difficulty tree problems to 73% in about 4 weeks of consistent sessions. Still not where I want to be but the trajectory is different.

Tool is open source and runs locally (no data goes to any cloud). Setup takes maybe 20 minutes if you have Docker; there's also a quickstart script. It's not polished — some features are still experimental — but the core quiz/flashcard/knowledge-graph loop works reliably.

**GitHub:** https://github.com/zijinz456/OpenTutor

Main takeaway beyond the tool: visualizing prerequisite dependencies before you study is worth the time. A list of "topics to cover" treats them as independent. They're not.

## e) Dev.to / Hashnode — Technical Article

**Title:** How I built a 12-signal cognitive load detector to make my AI tutor stop asking questions at students who are already lost

**Body:**

The version of the tutor prompt I'm not proud of looked like this:

```
"If the student seems overwhelmed or confused, adjust your response to be simpler."
```

This works in a demo. In a real session it doesn't: the LLM has no reliable way to detect "confused" from a single message. It would confidently provide a detailed explanation to a student who had just missed their third question in a row. Or ask a probing Socratic question to a student who had typed "i dont get this" after a 3-minute pause.

The fix was to stop asking the LLM to detect cognitive load and just compute it.

### What cognitive load detection actually needs

Cognitive Load Theory (Sweller, 1988) distinguishes between intrinsic load (complexity of the material) and extraneous load (friction from poor instruction). For an adaptive tutor, what matters is extraneous + germane load together — the observable behavioral signal that the student's working memory is saturated. The Nature 2025 paper I based this on ([doi:10.1038/s41598-025-10497-x](https://doi.org/10.1038/s41598-025-10497-x)) identifies several behavioral signals that correlate with high cognitive load: error rate, response hesitation, help-seeking language, and session fatigue. I implemented those plus a few others.

### The 12 signals

The full implementation is `apps/api/services/cognitive_load.py` (488 lines). Here are the signals and their default weights:

| Signal | Weight | What it measures |
|--------|--------|-----------------|
| text-based fatigue | 0.16 | Pre-computed fatigue score from message tone |
| session length | 0.08 | Normalized message count vs. ~45-min window |
| unmastered errors | 0.14 | Count of wrong answers not yet corrected |
| message brevity | 0.04 | Short messages = possible frustration |
| help-seeking | 0.10 | "help", "hint", "don't understand", etc. |
| quiz accuracy | 0.10 | 1 - (correct / total), normalized |
| answer hesitation | 0.06 | Median response time on recent quiz answers |
| NLP affect | 0.10 | LLM-classified frustration + confusion score |
| relative baseline | 0.08 | Deviation from this user's normal behavior |
| wrong streak | 0.05 | Consecutive wrong answers |
| message gap | 0.05 | Pause between messages (30s–300s range) |
| repeated errors | 0.04 | Same problems wrong multiple times |

The weights sum to 1.0. Each signal returns a value between 0.0 and 1.0.

### The weighted aggregation

```python
# apps/api/services/cognitive_load.py (simplified)

async def compute_cognitive_load(
    db: AsyncSession,
    user_id: uuid.UUID,
    course_id: uuid.UUID,
    fatigue_score: float = 0.0,
    session_messages: int = 0,
    user_message: str = "",
) -> dict:
    signals: dict[str, float] = {}
    load = 0.0

    # Signal 1: Text-based fatigue (computed upstream)
    signals["fatigue"] = fatigue_score
    load += fatigue_score * settings.cognitive_load_weight_fatigue  # 0.16

    # Signal 2: Session length fatigue
    # Cognitive performance degrades after ~45 min of focused study
    session_fatigue = min(session_messages / settings.cognitive_load_session_messages_norm, 1.0)
    signals["session_length"] = session_fatigue
    load += session_fatigue * settings.cognitive_load_weight_session_length  # 0.08

    # Signal 5: Help-seeking indicators (pre-compiled regex, no LLM)
    _HELP_PATTERNS = [re.compile(p) for p in [
        r"\bhelp\b", r"\bhint\b", r"\bexplain\b", r"\bdon'?t understand\b",
        r"\bconfused\b", r"\bstuck\b", r"\bhow do i\b",
    ]]
    help_signal = 1.0 if any(p.search(user_message.lower()) for p in _HELP_PATTERNS) else 0.0
    signals["help_seeking"] = help_signal
    load += help_signal * settings.cognitive_load_weight_help_seeking  # 0.10

    # ... (12 signals total)
    return {"score": min(round(load, 3), 1.0), "level": level, "signals": signals}
```

### The per-user baseline calibration

The trickiest signal is relative baseline calibration (weight: 0.08). A student who always sends short messages should not be flagged as struggling just because their messages are short — brevity is their normal. The calibrator (`cognitive_load_calibrator.py`, 273 lines) maintains a rolling per-user baseline of message length and help-seeking frequency. The signal fires when the current turn deviates significantly from that baseline, not when it crosses a global threshold.

```python
# apps/api/services/cognitive_load_calibrator.py (simplified)

def compute_relative_load(
    baseline: UserLoadBaseline,
    current_msg_len: int,
    is_help_seeking: bool,
    current_word_count: int,
) -> dict:
    if not baseline.is_ready:
        return {"calibrated": False, "adjustments": {}}

    adjustments = {}
    # Length drop: significant shortening relative to user's norm
    if baseline.mean_message_length > 0:
        length_ratio = current_msg_len / baseline.mean_message_length
        if length_ratio < 0.4:  # More than 60% shorter than normal
            adjustments["brevity_vs_baseline"] = min(1.0 - length_ratio, 1.0)

    # Help-seeking rate spike
    baseline_help_rate = baseline.help_seeking_rate
    if is_help_seeking and baseline_help_rate < 0.2:
        # Normally doesn't ask for help — this is unusual
        adjustments["help_vs_baseline"] = 1.0 - baseline_help_rate

    return {"calibrated": True, "adjustments": adjustments}
```

### The NLP affect call: expensive, so batched

The NLP affect analysis (`cognitive_load_nlp.py`, 213 lines) makes a lightweight LLM call to classify frustration and confusion on a 0.0–1.0 scale. It costs ~500ms and is the only signal with an LLM dependency. The solution: run it every 3 messages and cache the last result.

```python
# In compute_cognitive_load():

_should_run_nlp = (session_messages <= 1) or (session_messages % 3 == 0)
if _should_run_nlp and user_message:
    affect = await analyze_student_affect(user_message)
    # Cache result, bounded to _MAX_TRACKING_SIZE users
    _last_affect[str(user_id)] = affect
else:
    affect = _last_affect.get(str(user_id), {})

frustration = affect.get("frustration", 0.0)
confusion = affect.get("confusion", 0.0)
nlp_signal = (frustration * 0.6 + confusion * 0.4)
load += nlp_signal * settings.cognitive_load_weight_nlp_affect  # 0.10
```

The cache is an in-process dict bounded to 200 users. For a local single-user deployment this is fine; a multi-user deployment would need Redis or a DB-backed cache here.

### How the score is used downstream

The final `score` (0.0–1.0) flows into two places:

1. **Socratic engine** (`socratic_engine.py`, 287 lines): if `cognitive_load > 0.7`, the initial state is forced to SCAFFOLD instead of PROBE. High cognitive load is not the moment for open-ended questions.

2. **Tutor depth selection**: The score is included in the tutor's system prompt as a structured value: `"Cognitive load: 0.72 (high). Adjust response depth accordingly."` The LLM doesn't compute load; it receives a number and adjusts tone, vocabulary level, and example complexity accordingly.

### What I'd do differently

The signal weights (0.16, 0.14, 0.10...) are hand-tuned, not learned. The calibration logic is validated against a few representative sessions, not an actual dataset. The right thing to do is train a logistic regressor against labeled sessions — "student said they were lost after this turn" as the ground truth — and derive weights from that. The data collection infrastructure is in place (`cognitive_load_tuning.py`, 136 lines); the training loop isn't implemented yet.

The full codebase (~55k lines Python, ~32k lines TypeScript, 65 test files) is at https://github.com/zijinz456/OpenTutor. MIT licensed, contributions welcome. If you've worked on similar behavioral signal pipelines, I'd like to know what signals you found most predictive.
