## b) r/LocalLLaMA

**Title:** Built a local AI tutor with a circuit breaker for multi-provider fallback — here's what actually works

**Post:**

Been building OpenTutor (MIT, local-first AI tutor) for the past several months and wanted to share the LLM routing architecture that makes it usable across different hardware setups — because "it works with llama3.2:3b" is not the same as "it's usable with llama3.2:3b."

**The routing problem:**

An AI tutor does multiple LLM calls per user message. First, intent classification (fast, cheap, picks the right specialist agent). Then the main teaching response (slower, needs reasoning). Then optional background tasks: knowledge graph updates, confusion pair detection, prerequisite gap analysis. The pipeline is async — background tasks don't block your response — but the two sequential main calls make latency add up.

We handle multi-provider fallback with a `ProviderRegistry` + `CircuitBreakerMixin`. The circuit opens after 3 consecutive failures, the provider gets put on a 120-second timeout, and the registry falls through to the next healthy provider automatically. Progressive cooldown steps before the breaker trips: 5s, 10s, 20s, 60s.

**What runs where:**

```bash
# Default local setup (free, no API key)
LLM_PROVIDER=ollama
LLM_MODEL=llama3.2:3b  # intent classification + small tasks

# If you have more RAM
LLM_MODEL=llama3.1:8b  # noticeably better structured output
```

With llama3.2:3b on an M1 Mac (16GB): intent classification is ~1–2s, main teaching response 6–12s depending on answer length. The 8B model bumps quality significantly on quiz generation and structured notes. The JSON parsing issues everyone hits with 3B on structured output are real — we added a retry + prompt-repair path for that.

The circuit breaker is provider-agnostic, so you can configure Ollama as primary + DeepSeek as fallback and it switches automatically if Ollama goes down. Full list of supported providers: Ollama, OpenAI, Anthropic, DeepSeek, Gemini, Groq, vLLM, LM Studio, OpenRouter, any OpenAI-compatible endpoint.

Three commands to try it: `git clone https://github.com/zijinz456/OpenTutor`, `cp .env.example .env`, `docker compose up -d --build`.

## c) r/Anki

**Title:** We implemented FSRS-5/6 from scratch for our open-source tutor — here's what changed from 4.5

**Post:**

We recently upgraded the spaced repetition core of OpenTutor (self-hosted AI tutor, MIT) from FSRS-4.5 to FSRS-5/6, and I figured it's worth explaining the actual differences since the FSRS docs are a bit sparse on the upgrade details.

**What FSRS-5/6 changes from 4.5:**

1. **21 parameters instead of 17.** Four new params (w17–w20) handle same-day reviews and a trainable forgetting curve.

2. **Trainable forgetting curve decay.** FSRS-4.5 had a fixed exponential: `R(t) = e^(-t/S)`. FSRS-5/6 uses `R(t) = (1 + factor·t/S)^(-decay)` where `decay = w[20]` is a trainable parameter. When `decay = 1.0` (the default we ship), it's backward-compatible with FSRS-4.5. The power-law form fits some memory datasets better.

3. **Same-day review handling.** If you review a card multiple times in one day, FSRS-4.5 had no special handling — repeated reviews inflated stability. FSRS-5 adds a separate formula: `S' = S * exp(w17 * (G - 3 + w18)) * S^(-w19)`, which dampens the stability gain from intra-day reviews and prevents the inflation.

4. **Exponential difficulty initialization.** FSRS-4.5 used linear `D0 = w4 - (G - 3) * w5`. FSRS-5/6 uses `D0 = w4 - exp(w5 * (G - 1)) + 1`, which makes difficulty more sensitive to the initial rating.

**How it compares to Anki's SM-2:**

Anki still uses SM-2 by default (unless you've opted into the FSRS experimental mode). SM-2 doesn't model forgetting explicitly — it uses a fixed interval multiplier. FSRS models a continuous forgetting curve and schedules the next review when your predicted recall probability drops below a target threshold (90% by default). The FSRS paper claims 30%+ better retention prediction vs SM-2 on real Anki data. We're not in a position to validate that independently yet, but the per-card stability modeling feels meaningfully more sophisticated.

We also run Bayesian Knowledge Tracing alongside FSRS for quiz questions specifically — it maintains a separate mastery estimate P(L_n) that feeds into how difficulty is selected for new questions.

Repo if you want to look at the FSRS implementation: `apps/api/services/spaced_repetition/fsrs.py` — it's 310 lines, pure Python, no external FSRS library dependency.

## e) Dev.to / Hashnode — Technical Article

**Title:** How I built a multi-provider LLM circuit breaker for an AI tutor

An AI tutor that depends on a single LLM API is fragile in exactly the wrong moment — it goes down during your study session, or latency spikes when you're asking a question before an exam. When we built the LLM layer for OpenTutor (open-source local-first adaptive tutor), we needed something that could fall back gracefully across providers without the user noticing.

Here's what we built, why the naive approach failed, and the specific pattern we landed on.

### The Problem With Naive Fallback

The obvious approach is a try/except chain:

```python
try:
    response = await openai_client.complete(prompt)
except Exception:
    response = await fallback_client.complete(prompt)
```

This breaks badly in practice. If OpenAI is rate-limiting you, it returns a 429, not a network error. If it's intermittently degraded, it returns errors 20% of the time — you either keep hitting it and failing 20% of requests, or you failover on every 429 and exhaust your fallback budget too. And if you don't track failure state, every request re-checks a provider that's been down for 10 minutes.

### Circuit Breaker + Progressive Cooldown

We split the concern into two layers: a `CircuitBreakerMixin` that tracks per-provider health, and a `ProviderRegistry` that maintains the fallback chain.

The circuit breaker implements progressive cooldown before tripping — borrowed from the openakita pattern:

```python
# apps/api/services/llm/circuit_breaker.py

COOLDOWN_STEPS = [5, 10, 20, 60]        # seconds
CIRCUIT_OPEN_THRESHOLD = 3              # failures before opening
CIRCUIT_RESET_TIMEOUT = 120             # seconds before auto-retry

class CircuitBreakerMixin:
    def __init__(self):
        self._healthy = True
        self._cooldown_until: float = 0
        self._consecutive_failures: int = 0
        self._circuit_open: bool = False
        self._circuit_open_time: float = 0

    @property
    def is_healthy(self) -> bool:
        if self._circuit_open:
            if time.time() - self._circuit_open_time >= CIRCUIT_RESET_TIMEOUT:
                self._circuit_open = False
                self._healthy = True
                self._consecutive_failures = 0
            else:
                return False
        if self._cooldown_until > 0 and time.time() >= self._cooldown_until:
            self._healthy = True
            self._cooldown_until = 0
        return self._healthy
```

On each failure, the provider enters a cooldown that doubles with each step (5s → 10s → 20s → 60s), then the circuit opens after 3 consecutive failures. The circuit auto-resets after 120 seconds — we don't want permanent failures baking in without trying again.

### The Registry Fallback Chain

The `ProviderRegistry` queries each provider's `.is_healthy` before dispatching:

```python
# apps/api/services/llm/router.py

class ProviderRegistry:
    def get(self, name: str | None = None) -> LLMClient:
        # Try named provider first
        if name and name in self._providers:
            client = self._providers[name]
            if client.is_healthy:
                return client

        # Fall through the fallback chain
        for provider_name in self._fallback_order:
            client = self._providers[provider_name]
            if client.is_healthy:
                return client

        raise AllProvidersUnhealthyError(
            self._build_diagnostic_message()
        )
```

The fallback order is configured at startup. Our default is `ollama → openai → anthropic`, meaning users get local-first behavior by default and cloud kicks in if Ollama isn't running.

### Model Size Hints

One thing that tripped us up: different tasks in the tutor pipeline want different model sizes. Intent classification wants fast and cheap; the main teaching response wants quality; quiz generation wants reliable structured output. We added variant registration for size hints:

```python
registry.register_variant("fast", small_model_client)
registry.register_variant("large", large_model_client)

# Usage in agents
intent_client = registry.get("fast")    # llama3.2:3b or gpt-4o-mini
teaching_client = registry.get("large") # llama3.1:8b or gpt-4o
```

This decouples "which provider" from "what model size" — if Ollama only has the 3B model loaded, it falls through on the "large" hint and routes to the cloud provider, while still using local for fast calls.

### Error Diagnostics

A common failure mode: "all providers unhealthy" with no actionable message. We store a human-readable last-error on each client and surface it when the whole chain fails:

```python
def _build_diagnostic_message(self) -> str:
    details = [
        f"{name}: {client.last_error_detail or 'no error recorded'}"
        for name, client in self._providers.items()
    ]
    return "All LLM providers are unhealthy:\n" + "\n".join(details)
```

This turns "connection refused" into something like "ollama: connection refused at http://localhost:11434 — is Ollama running?" which is what a user actually needs.

### What This Gives You

The full LLM layer (router, circuit breaker, provider abstractions, error classification, usage tracking) is about 1,700 lines across the `apps/api/services/llm/` directory. The public surface is small: `get_llm_client()` returns a healthy client, throws `AllProvidersUnhealthyError` with diagnostics if none exist.

For a learning app where users might have Ollama running, might not, might have a cloud API key, might not — this architecture has been the right call. We've had no production incidents from provider failures since shipping it, because the app degrades gracefully rather than hard-failing.

The full source is at [github.com/zijinz456/OpenTutor](https://github.com/zijinz456/OpenTutor) — MIT licensed, 3-command Docker start. The LLM layer is standalone enough that you could lift it into any FastAPI project.
