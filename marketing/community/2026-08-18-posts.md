## a) Hacker News — Show HN

**Title:** `Show HN: OpenTutor – knowledge graph that propagates mastery through prerequisites`

---

Most spaced repetition systems treat every card as an island. You review "mitochondria" and "ATP synthesis" independently, on their own schedules, as if the relationship between them doesn't exist. That's fine when you're reviewing isolated vocabulary — it breaks down when concepts have real prerequisite dependencies.

OpenTutor implements FIRe (Fractional Implicit Repetitions) on top of LOOM — a graph-based mastery tracking layer where practicing concept X gives a fractional credit boost to its prerequisites, and an incorrect answer propagates doubt backward through the dependency chain. The implementation is in `services/loom_mastery.py` (361 lines). When a student answers a question correctly, the mastery update runs BKT on the direct concept, then propagates 5% per graph depth level to prerequisites (the FIRe algorithm). Incorrect answers propagate 3% doubt upward using GKT-inspired rules. The propagation runs breadth-first with a depth limit to avoid diffusing credit so far it becomes meaningless.

The second layer (LECTOR, `services/lector.py`, 344 lines) extends FSRS scheduling with this graph context. Instead of scheduling each card individually, it scores review urgency per concept, then clusters related concepts for co-review. Concepts with weak prerequisites get reviewed before dependents — the scheduler enforces prerequisite ordering automatically. Concepts that frequently co-occur in errors are reviewed in contrast (shown side-by-side). The FSRS retrievability function (R(t) = (1 + t/9S)^-1) runs per concept, and decay in one concept triggers a review boost in its graph neighbors.

FSRS itself has been upgraded to FSRS-5/6 (21 parameters, from 4.5's 17): trainable forgetting curve decay, same-day review handling with a separate stability formula, and exponential difficulty initialization. ## b) r/LocalLLaMA

**Title:** `How I handle Ollama going OOM mid-session without crashing the whole app`

---

If you run a local stack for anything beyond casual use, Ollama eventually OOMs. Maybe you loaded a second model, maybe the OS decided to reclaim memory, maybe you're on a 16GB machine running llama3:8b and your browser ate 4GB. Whatever the reason, your app needs to not fall apart.

OpenTutor's LLM layer has a circuit breaker with progressive cooldown that handles this gracefully. The implementation is in `services/llm/circuit_breaker.py`:

```python
COOLDOWN_STEPS = [5, 10, 20, 60]   # seconds, borrowed from openakita
CIRCUIT_OPEN_THRESHOLD = 3         # consecutive failures before circuit trips
CIRCUIT_RESET_TIMEOUT = 120        # seconds before auto-retry

def mark_unhealthy(self, error: str):
    self._consecutive_failures += 1
    if self._consecutive_failures >= CIRCUIT_OPEN_THRESHOLD:
        self._circuit_open = True
        self._circuit_open_time = time.time()
        logger.error(f"Circuit OPEN for {self.provider_name} after {self._consecutive_failures} failures")
        return
    idx = min(self._consecutive_failures - 1, len(COOLDOWN_STEPS) - 1)
    cooldown = COOLDOWN_STEPS[idx]
    self._cooldown_until = time.time() + cooldown
```

On first failure, the provider goes into 5s cooldown. Second failure, 10s. Third failure trips the circuit and the provider is marked unavailable for 120s. After 120s it auto-resets and tries again.

The router layer sits on top and implements a fallback chain. If you have `LLM_PROVIDER=ollama` as primary and a cloud provider configured as secondary, a tripped Ollama circuit automatically routes to the fallback. If Ollama is your only provider, requests that hit the open circuit return a graceful error instead of hanging the request. The router also supports model variants — `get("fast")`, `get("large")`, `get("small")` — so the tutor can route lighter query-expansion calls to the smaller/faster model and only send the main generation to the larger one.

Setup: three commands, `LLM_PROVIDER=ollama`, `LLM_MODEL=llama3.2:3b` to start. Switching to any OpenAI-compatible endpoint is one env var change. MIT. GitHub: https://github.com/zijinz456/OpenTutor

## c) r/Anki

**Title:** `Anki uses FSRS-4.5 (17 params). I upgraded to FSRS-5/6 (21 params) — here's what's different`

---

Anki shipped FSRS-4.5 in 2024 and it's a genuine improvement over SM-2. But FSRS has continued to evolve. OpenTutor's implementation has been upgraded to the FSRS-5/6 parameter set (21 parameters), and the differences are worth understanding if you care about the algorithm.

The three main additions in FSRS-5/6:

**1. Trainable forgetting curve decay.** FSRS-4.5 uses a fixed forgetting curve: R(t) = (1 + t/9S)^-1. In FSRS-5/6, the exponent is a trainable parameter (w20 in the parameter vector) rather than a hardcoded -1. This means the forgetting curve shape can be learned from your actual review data, not assumed to be a power law. The forgetting_forecast service (`services/spaced_repetition/forgetting_forecast.py`) uses this to predict when each card will drop below your retention threshold — defaulting to 90%, which is what Anki uses.

**2. Same-day review handling.** FSRS-4.5 wasn't designed with intra-day reviews in mind. When you review a card twice in the same day, the stability formula doesn't handle it cleanly. FSRS-5/6 adds a separate stability formula for same-day reviews (w17-w19 in the parameter set) that treats short-gap reviews differently from multi-day reviews.

**3. Exponential difficulty initialization.** FSRS-4.5 uses a linear formula for initial difficulty: D0 = w4 - w5·(G-1). FSRS-5/6 changes this to exponential: D0 = w4 - exp(w5·(G-1)) + 1. The practical effect: the difficulty scale compresses at the extremes and is more sensitive in the middle range where most cards land.

The default parameter vector in OpenTutor (`DEFAULT_W`) is initialized to FSRS-5/6 values compatible with FSRS-4.5 performance (w20=1.0 gives the same forgetting curve as 4.5), and personal parameters are tuned per-user from review history.

The LECTOR layer on top (`services/lector.py`, 344 lines) adds something Anki doesn't have: it knows your knowledge graph. If you have weak understanding of a prerequisite concept, it will push that card up your review queue ahead of dependent cards — even if FSRS says the dependent cards are more overdue. For studying anything with concept dependencies (medicine, math, programming) this matters.

OpenTutor is MIT, self-hosted, runs locally. GitHub: https://github.com/zijinz456/OpenTutor

## d) r/GetStudying / r/medicalschool

**Title:** `The most useful thing I track now: which concepts I get wrong consistently, not just which cards`

---

I used to think about review as a cards problem. Review the cards that are due. Simple. The issue is that "which cards are due" doesn't tell you why you keep missing the same concepts.

I started tracking my errors differently: instead of just logging wrong answers, I started mapping which concepts I consistently struggle with and whether my wrong answers cluster around specific prerequisite gaps. The pattern was uncomfortable — I had a lot of cards where I was missing the foundational concept and compensating by memorizing downstream details instead.

A concrete example from pharmacology prep: I was consistently fumbling questions about drug metabolism pathways. I had reviewed cytochrome P450 isoforms and I had reviewed drug-drug interactions, but I kept getting confused because I'd never solidly nailed which enzymes do what. The symptoms showed up in questions two layers above the actual gap.

The diagnostic move that helped: for any topic you keep getting wrong, work backwards through the prerequisite chain. Ask yourself "to answer this correctly, what else would I need to know?" then ask the same question about that. You'll usually find the actual gap is one or two concepts above where you're practicing.

The other thing worth doing: actively distinguish between concepts you recognize versus concepts you can generate. Recognition-level knowledge (picking the right answer from a list) and production-level knowledge (explaining from scratch) feel similar in the moment but perform very differently under exam pressure. If you can't explain a concept unprompted, you don't have production-level mastery of it — even if your card review stats look clean.

I built this into OpenTutor (the tool I'm working on) — it maintains a concept dependency graph and surfaces prerequisite gaps automatically. But the manual version — working backwards through the prerequisite chain when you notice a pattern of errors — works with any study system and is probably more useful to develop as a habit anyway.

## e) Dev.to / Hashnode — Technical Article

**Title:** How I implemented FIRe — propagating mastery credit through a knowledge graph when students practice

---

Every spaced repetition system I'd tried had the same implicit assumption: cards are independent. Review "mitochondria" — update "mitochondria." Review "ATP synthesis" — update "ATP synthesis." But in any subject with real conceptual structure, that assumption is wrong. If you demonstrate mastery of ATP synthesis, you've implicitly also demonstrated something about mitochondria (you can't master the output without understanding the factory). Ignoring that relationship wastes information.

FIRe (Fractional Implicit Repetitions) is a 2024 algorithm for propagating review credit through a knowledge graph. When you correctly answer a question about concept X, its prerequisites get a small fractional credit boost — not a full review, but enough to keep their intervals from compressing unnecessarily. OpenTutor implements FIRe in `services/loom_mastery.py` (361 lines). Here's how the mastery update works end to end.

### Step 1: BKT update on the direct concept

Before any graph propagation, the direct concept gets a Bayesian Knowledge Tracing update with question-type-aware parameters:

```python
BKT_PARAMS: dict[str, tuple[float, float]] = {
    "mc": (0.25, 0.10),            # MCQ: 25% guess probability
    "tf": (0.50, 0.10),            # True/False: 50% guess
    "short_answer": (0.05, 0.10),  # Short answer: very low guess
    "free_response": (0.05, 0.10),
    "fill_blank": (0.10, 0.10),
    "matching": (0.15, 0.10),
    "select_all": (0.10, 0.10),
}

def _bkt_update(prior: float, correct: bool, question_type: str | None = None) -> float:
    guess, slip = BKT_PARAMS.get(question_type or "", (0.15, 0.10))
    prior = max(0.001, min(0.999, prior))

    if correct:
        posterior = prior * (1 - slip) / (prior * (1 - slip) + (1 - prior) * guess)
    else:
        posterior = prior * slip / (prior * slip + (1 - prior) * (1 - guess))

    # Learning transition: even after observation, there's a chance the student learned
    return max(0.0, min(1.0, posterior + (1 - posterior) * 0.10))
```

The question type matters: getting an MCQ right is weak evidence (you could have guessed). Getting a free-response right is strong evidence. This means the BKT prior for the same concept moves faster when you practice harder question formats.

### Step 2: FIRe propagation through prerequisites

Once the direct concept is updated, BFS propagates fractional credit to its prerequisite chain. Correct answers boost prerequisites; incorrect answers propagate doubt:

```python
FIRE_BOOST_PER_DEPTH = 0.05   # 5% mastery boost per propagation level
FIRE_DOUBT_PER_DEPTH = 0.03   # 3% doubt per depth level (GKT-inspired)

async def _propagate_fire(
    db: AsyncSession,
    user_id: uuid.UUID,
    concept_node_id: uuid.UUID,
    course_id: uuid.UUID,
    correct: bool,
    max_depth: int = 3,
) -> None:
    visited = set()
    queue = deque([(concept_node_id, 0)])

    while queue:
        node_id, depth = queue.popleft()
        if depth >= max_depth or node_id in visited:
            continue
        visited.add(node_id)

        # Find prerequisites (inbound edges: prereq -> current)
        result = await db.execute(
            select(KnowledgeEdge).where(
                KnowledgeEdge.target_id == node_id,
                KnowledgeEdge.edge_type == "prerequisite",
            )
        )
        edges = result.scalars().all()

        for edge in edges:
            prereq_id = edge.source_id
            boost = (FIRE_BOOST_PER_DEPTH if correct else -FIRE_DOUBT_PER_DEPTH) * (depth + 1)
            # Apply fractional update to prerequisite mastery
            await _apply_fire_boost(db, user_id, prereq_id, course_id, boost)
            queue.append((prereq_id, depth + 1))
```

The depth limit (3) prevents credit from diffusing so far it becomes meaningless. A concept three prerequisite-hops up gets 15% of a full credit; a concept four hops up gets nothing. This is a tuning decision — too shallow and the graph effect is weak, too deep and unrelated concepts start accumulating phantom mastery.

### What it looks like in practice

For a pharmacology student, the knowledge graph might have: `cytochrome P450 isoforms → drug metabolism pathways → drug-drug interactions`. After a session where they struggle with drug-drug interaction questions, FIRe propagates doubt back to drug metabolism and then to the isoforms. The next LECTOR session surfaces the isoform concept first, even though the student hasn't explicitly flagged it — the graph inferred the gap from downstream errors.

This doesn't always work perfectly. The quality of the graph matters: if the prerequisite edges are wrong or missing, the propagation misfires. OpenTutor generates these edges via LLM extraction at content ingestion time, which means edge quality depends on the extraction prompt and model. Current status: works well for subjects with clear concept hierarchies (medicine, math, CS fundamentals), weaker for humanities where "prerequisite" is fuzzier.
