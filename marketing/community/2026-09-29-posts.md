## b) r/LocalLLaMA

**Title:** Built an adaptive learning workspace that runs on llama3.2:3b — multi-provider router with circuit breaker fallback

**Body:**

Hey all — sharing something I've been building that might be useful for folks who like running LLMs locally for productivity (not just chatting).

**What it is:** OpenTutor is a local-first study workspace. You drop in a PDF/PPTX and within ~30 seconds you get AI-generated notes, flashcards, and quiz questions. Everything runs on your machine.

**The local LLM setup:** Default is `llama3.2:3b` via Ollama, which works fine for content ingestion and basic tutoring. The LLM router implements a circuit breaker with progressive cooldown steps of 5s → 10s → 20s → 60s, then opens the circuit after 3 consecutive failures (resets after 120s). This means if your Ollama instance is slow or restarting, the app degrades gracefully rather than hanging. The registry also supports model-size hints (`large`/`small`/`fast`) so you can point different agents at different model sizes.

**Provider support:** Ollama, OpenAI, Anthropic, DeepSeek, Gemini, Groq, vLLM, LM Studio, OpenRouter, or any OpenAI-compatible endpoint — just swap `LLM_PROVIDER` and `LLM_MODEL` in `.env`.

**Rough performance on llama3.2:3b (Apple M2, 16GB):**
- Content ingestion (10-page PDF → notes + flashcards): ~25-35s
- Tutor chat response: ~3-6s per turn
- Quiz generation (5 questions): ~8-12s

The 3b model is genuinely enough for the spaced repetition and quiz flows. For the knowledge graph reasoning you'll want 7b or larger. No API keys required for the Ollama path.

**GitHub:** https://github.com/zijinz456/OpenTutor

Quick start: `git clone`, `cp .env.example .env`, `docker compose up -d --build` → open `localhost:3001`.

## c) r/Anki

**Title:** I implemented FSRS-5/6 in my open-source study app — here's what I learned vs SM-2 and Anki's current algorithm

**Body:**

I've been deep in spaced repetition implementation for the past few months while building an open-source AI tutor. Thought this community would appreciate a write-up on the FSRS side.

**What I implemented:** FSRS-5/6 with 21 trainable parameters (FSRS-4.5 had 17). The upgrade adds:
- Trainable forgetting curve decay: `R(t) = (1 + factor·t/S)^(-decay)` where `decay` (w20) is learnable rather than fixed at 1.0
- Same-day review handling with a separate stability formula — prevents stability inflation when you review multiple times in one day
- Exponential difficulty initialization for better initial estimates
- Linear damping on difficulty updates

**vs SM-2 (what older Anki used):** SM-2 uses a fixed exponential forgetting curve and adjusts interval multipliers based on rating. It doesn't model individual card difficulty and stability independently, and a single "Again" can dramatically collapse your interval without accounting for how stable the card was before. FSRS models each card's stability and difficulty separately and uses the retrievability formula to decide when to review, not a fixed interval. In practice the FSRS-5/6 variant claims 30%+ accuracy improvement over SM-2 (measured against the open-spaced-repetition benchmark data).

**The forgetting cost estimate I added:** Beyond just scheduling, I track "expected cards forgotten if the user doesn't review now" — sum of `(1 - R(t))` across all overdue cards. If this number hits 2.0+, the app proactively nudges a review session. This is closer to how humans actually experience forgetting than a simple "due count."

**What Anki does better:** Anki has years of real user data and a mature optimizer. My implementation is correct but not yet personalized per-learner — the 21 default parameters are community-tuned, not trained on individual data. That's on the roadmap.

The full implementation is in `apps/api/services/spaced_repetition/fsrs.py` (~304 lines) if you want to read the code. MIT licensed.

**GitHub:** https://github.com/zijinz456/OpenTutor

## e) Dev.to / Hashnode — Technical Article

**Title:** How I built a multi-provider LLM router with circuit breaker fallback for my AI tutor

**Body:**

Building an AI-powered learning app that runs locally means you can't rely on a single always-available API. Users run Ollama on underpowered hardware, switch between providers, or want a cloud fallback when the GPU is tied up. I needed a router that handled provider failures gracefully without crashing the session.

Here's how the LLM router in [OpenTutor](https://github.com/zijinz456/OpenTutor) works.

### The Problem

When a user's local Ollama instance goes down mid-tutoring session, a naive implementation either hangs indefinitely or throws a 500. Neither is acceptable. What I needed:

1. Automatic fallback to a healthy provider
2. Progressive backoff so a struggling provider isn't hammered with retries
3. Circuit breaker to stop attempting a dead provider for a defined window
4. Model-size hints so different agents can target different model sizes

### Circuit Breaker as a Mixin

The health-tracking logic is a mixin so any provider client can inherit it without coupling the circuit breaker logic to any specific provider:

```python
# apps/api/services/llm/circuit_breaker.py

COOLDOWN_STEPS = [5, 10, 20, 60]      # progressive backoff in seconds
CIRCUIT_OPEN_THRESHOLD = 3            # failures before circuit opens
CIRCUIT_RESET_TIMEOUT = 120           # seconds before auto-reset

class CircuitBreakerMixin:
    def __init__(self):
        self._healthy = True
        self._cooldown_until: float = 0
        self._consecutive_failures: int = 0
        self._circuit_open: bool = False
        self._circuit_open_time: float = 0

    @property
    def is_healthy(self) -> bool:
        if self._circuit_open:
            if time.time() - self._circuit_open_time >= CIRCUIT_RESET_TIMEOUT:
                self._circuit_open = False
                self._healthy = True
                self._consecutive_failures = 0
            else:
                return False
        if self._cooldown_until > 0 and time.time() >= self._cooldown_until:
            self._healthy = True
            self._cooldown_until = 0
        return self._healthy

    def mark_unhealthy(self, error: str):
        self._healthy = False
        self._consecutive_failures += 1
        if self._consecutive_failures >= CIRCUIT_OPEN_THRESHOLD:
            self._circuit_open = True
            self._circuit_open_time = time.time()
            return
        idx = min(self._consecutive_failures - 1, len(COOLDOWN_STEPS) - 1)
        self._cooldown_until = time.time() + COOLDOWN_STEPS[idx]
```

The first failure adds a 5-second cooldown. The second: 10 seconds. Third: the circuit opens for 120 seconds and the provider is skipped entirely until it resets. This prevents a single flaky provider from dominating retry loops.

### The Provider Registry

The registry holds all registered providers and handles the fallback chain automatically:

```python
# apps/api/services/llm/router.py (simplified)

class ProviderRegistry:
    def __init__(self):
        self._providers: dict[str, LLMClient] = {}
        self._primary: str | None = None
        self._fallback_order: list[str] = []
        self._model_variants: dict[str, LLMClient] = {}

    def get(self, name: str | None = None) -> LLMClient:
        # Check model-size hints first (large/small/fast)
        if name and name in self._model_variants:
            client = self._model_variants[name]
            if client.is_healthy:
                return client

        # Try the requested provider, then primary, then fallback chain
        if name and name in self._providers:
            client = self._providers[name]
            if client.is_healthy:
                return client

        if self._primary and self._primary in self._providers:
            client = self._providers[self._primary]
            if client.is_healthy:
                return client

        # Walk the fallback order
        for provider_name in self._fallback_order:
            client = self._providers[provider_name]
            if client.is_healthy:
                return client

        raise LLMConfigurationError("No healthy LLM provider available.")
```

Three agents in OpenTutor (Tutor, Planner, Layout) each call `registry.get()` with different hints. The Layout agent uses `"small"` since it only needs to pick a grid config. The Tutor agent uses `"large"` for better reasoning quality. The registry resolves these to whatever healthy provider is registered under that variant.

### FSRS Forgetting Cost: A Smarter Review Nudge

The other interesting piece is how we decide *when* to interrupt a study session for a spaced repetition review. Rather than a simple "cards due" count, we compute expected forgetting cost across all overdue cards:

```python
# apps/api/services/spaced_repetition/fsrs.py

def _retrievability(elapsed_days: float, stability: float, w: list[float] = DEFAULT_W) -> float:
    """R(t) = (1 + factor * t / S)^(-decay)"""
    if stability <= 0:
        return 0.0
    decay = w[20] if len(w) > 20 else 1.0
    factor = 9 * decay
    return pow(1 + elapsed_days / (factor * stability), -decay)

def estimate_forgetting_cost(cards: list[FSRSCard], now=None) -> float:
    """Sum of (1 - R) across all overdue cards.
    
    A value >= 2.0 is treated as urgent: the user is expected to forget
    2+ cards if they don't review now.
    """
    total = 0.0
    for card in cards:
        if card.due is None or card.stability <= 0:
            continue
        due = _as_utc(card.due)
        if due > now:
            continue
        elapsed = max((now - due).total_seconds() / 86400, 0)
        total_elapsed = elapsed + max(card.stability, 1.0)
        total += (1.0 - _retrievability(total_elapsed, card.stability))
    return round(total, 2)
```

The `forgetting_cost >= 2.0` threshold means "you're expected to forget at least 2 cards right now" — it's a more intuitive interrupt signal than a raw due count, which doesn't account for how stable each card was before it went overdue.

### What I Learned

The circuit breaker mixin pattern worked well — it kept health-tracking logic out of the provider implementations and made it trivial to add a new provider. The hardest part was the forgetting cost threshold: 2.0 is still a rough calibration, not something derived from data. The next step is per-user parameter tuning once we have enough review history.
