## a) Hacker News — Show HN

**Title:** `Show HN: OpenTutor – 3-tier LLM routing in a local AI tutor (no LLM call to route)`

---

Most education tools that use LLMs send every request to the same model — usually the largest one available — because choosing a model at runtime feels expensive. We wanted to avoid that without introducing a "router LLM" that doubles the latency and cost of every request. The result is a heuristic complexity scorer that routes each tutor request to one of three model tiers (fast/standard/frontier) without making any LLM call.

The logic is in `services/llm/complexity.py` (196 lines). Each request is scored 0–780 based on four education-domain signals: message length (0–150), classified intent (0–300), active scene (0–100), conversation depth (0–80), and a complexity-marker pass over the message text (patterns like `\bprove\b`, `step-by-step`, `compare`, `\bderive\b`, each worth 25–50 points, capped at 100). A RAG-context bonus adds 50 if retrieval results are injected. Scores < 150 → fast tier; ≥ 500 → frontier. The middle band is standard. `resolve_tier()` then takes the max of the scored tier and a per-agent minimum (planning agents are floored at frontier regardless of score; simple preference agents can use fast).

In practice: greetings, layout changes, and session preferences go to the fast model (llama3.2:3b or equivalent). Explanation, quiz generation, and review go to standard. Study plan generation, code execution, and multi-step curriculum planning go to frontier. The intent classifier already runs for other purposes, so the additional cost of routing is ~200µs of regex matching and arithmetic. The circuit breaker (`circuit_breaker.py`, 83 lines) handles provider failure with progressive cooldown steps (5s, 10s, 20s, 60s) and auto-opens after 3 consecutive failures, auto-resetting after 120s. A background health probe (30s interval) refreshes provider liveness without blocking requests.

63 test files, 996 pytest functions. Docker Compose, MIT. GitHub: https://github.com/zijinz456/OpenTutor

## b) r/LocalLLaMA

**Title:** `How the circuit breaker in my AI tutor prevents Ollama crashes from killing the session`

---

Running local LLMs in a production-ish flow means your model goes down sometimes. Ollama OOMs, the GPU runs hot, the model is still loading. Without handling this explicitly, a single failed request either hard-errors the user session or (worse) hangs indefinitely waiting on a connection that's never coming.

OpenTutor handles this with a circuit breaker + progressive cooldown mixin in `services/llm/circuit_breaker.py` (83 lines). The logic:

- First failure: provider marked unhealthy, cooldown for 5s
- Second: cooldown 10s
- Third: cooldown 20s
- Fourth+: cooldown 60s
- 3 consecutive failures: circuit opens, provider removed from fallback candidates for 120s, then auto-resets

The fallback chain in the provider registry (`router.py`, 399 lines) tries the requested provider first, then primary, then walks the fallback list in order. So if Ollama is circuit-open, the next request automatically goes to whatever's healthy — DeepSeek if you have a key, a mock client if nothing else is configured. The background health probe pings all registered providers every 30 seconds and updates the `_probe_cache` without blocking any request path.

Setup:

```bash
LLM_PROVIDER=ollama
LLM_MODEL=llama3.2:3b          # fast + standard tiers
LLM_FALLBACK_PROVIDER=deepseek
DEEPSEEK_API_KEY=sk-...        # frontier tier + Ollama fallback
```

The 3-tier complexity routing means llama3.2:3b handles greetings, preferences, and simple recall questions automatically. Study plan generation (frontier tier) routes to DeepSeek by default; if DeepSeek's circuit is open, it escalates to whatever's next in the fallback chain.

llama3.2:3b memory at 4-bit quant: ~2.0 GB on M2 Pro. Ingestion classification latency: 0.3–0.8s per chunk warm. A 30-page PDF runs through the full ingestion pipeline in 40–60s. Three commands to start: `git clone`, `cp .env.example .env`, `docker compose up -d --build`.

## c) r/Anki

**Title:** `I added per-item forgetting curve forecasts to my FSRS scheduler — here's the math`

---

Anki tells you what's due today. It doesn't tell you what you're going to forget tomorrow, or which specific cards are decaying fastest right now. This is a real gap: if you're reviewing daily you probably don't need it, but if your review rhythm is irregular or you have an exam in 5 days, knowing the decay curve per topic is more actionable than a card count.

OpenTutor's `forgetting_forecast.py` (137 lines) uses FSRS's retrievability formula to project when each knowledge point will drop below a threshold, and assigns urgency tags per item.

The math is standard FSRS:

```python
def _retrievability(elapsed_days: float, stability: float) -> float:
    """FSRS retrievability: R(t) = (1 + t/(9*S))^-1"""
    if stability <= 0:
        return 0.0
    return pow(1 + elapsed_days / (9 * stability), -1)


def _days_until_retention(stability: float, threshold: float = 0.90) -> float:
    """Days until R drops to threshold. From R(t) = (1 + t/(9*S))^-1, solve for t:
    t = 9 * S * (1/R - 1)
    """
    if stability <= 0 or threshold <= 0 or threshold >= 1:
        return 0.0
    return 9 * stability * (1 / threshold - 1)
```

For each item, the forecast computes `current_retrievability` from elapsed days since last review, then `days_until_threshold` (days remaining before R drops below 0.90). Urgency tiers:

- `overdue`: current R < 0.70 — already likely forgotten
- `urgent`: 0.70 ≤ R < 0.90 — past threshold, degrading
- `warning`: R ≥ 0.90 but ≤ 2 days remaining before it drops
- `ok`: stable

Results are sorted overdue → urgent → warning → ok, then by `days_until_threshold` ascending, so the item decaying fastest surfaces first. The workspace displays this as a proactive review schedule rather than a raw due list — you see "Cardiac Output: 0.8 days until threshold, urgent" rather than "12 cards due."

One thing FSRS gives you that SM-2 doesn't: the stability value S is card-specific and updated after every review. A card you've reviewed 8 times has much higher stability than one you've reviewed twice, even at the same mastery level. The forecast can therefore distinguish "this card is due but stable, it's fine to wait a day" from "this card is due and has low stability, it'll drop fast." Anki's due list doesn't surface that distinction — everything that's past due looks equally urgent.

The full spaced repetition stack (fsrs.py 304 lines + forgetting_forecast.py 137 lines + flashcards.py 149 lines) is 590 lines total. MIT licensed.

## d) r/GetStudying / r/medicalschool

**Title:** `Something clicked when I started studying across courses instead of within them`

---

I had been studying pharmacology and physiology as completely separate things. Different Anki decks, different study sessions, separate notes. They're different courses so it made sense to keep them separate.

The problem showed up on practice exams. I knew drug mechanisms in isolation, and I knew the physiology in isolation, but when a question required connecting them — "given this receptor profile, what happens to cardiac output if you also have this condition" — I'd stall. The information was there but the link wasn't.

The fix wasn't adding more cards. It was stopping to explicitly ask: **what do I actually know from another subject that's relevant to what I'm studying right now?**

For pharmacology, the answer was surprisingly often physiology. Beta-blockers and cardiac output only make full sense if the underlying physiology is solid. ACE inhibitors and renin-angiotensin — same thing. I started keeping a small list during each study session: "concepts from a different subject that this relies on." Usually it was 1–3 items. If I couldn't name them, that was the signal I needed to go back, not forward.

The practical exercise:

1. After finishing any mechanistic topic, write down the subjects it assumes you understand.
2. For each: rate your actual confidence (not "I've seen this" — "I could explain it to someone").
3. For anything below a 7/10: treat it as a prerequisite gap, not background knowledge. Schedule a dedicated review before the current topic again.

The insight is that knowledge transfer is asymmetric. Physiology makes pharmacology easier, but reviewing pharmacology doesn't automatically strengthen physiology. If you only study in one direction, the prerequisite remains weak even as you pile more on top of it.

The tool I've been building (OpenTutor) has a cross-course knowledge graph that tracks these "reinforces" edges between concepts in different courses and surfaces them when it detects a prerequisite gap. But the underlying habit — checking what other subjects your current topic depends on — is something any student can do with a notebook. The tool just makes the map visible.

## e) Dev.to / Hashnode — Technical Article

**Title:** How I built a 3-tier LLM router for an education context — without using an LLM to route

---

One of the first architectural decisions I hit building OpenTutor was: which model do you send each request to? The naive answer is "always the best one" — but that makes every interaction expensive and slow, which kills the experience for simple interactions that don't need it. The smarter-seeming answer is "use a router LLM to classify each request" — but that doubles the latency on every single call, because you're adding a full model inference step before the actual response.

I wanted a third option: a deterministic complexity scorer that routes to one of three model tiers (fast / standard / frontier) in ~200 microseconds, with no LLM call required.

Here's how it works.

### The three tiers

```python
class ModelTier(str, Enum):
    FAST = "fast"         # greetings, preferences, layout changes
    STANDARD = "standard" # teaching, exercises, review — most requests
    FRONTIER = "frontier" # planning, code, multi-step reasoning
```

FAST maps to llama3.2:3b locally (or the cheapest cloud tier). STANDARD covers the bulk of actual education tasks. FRONTIER is reserved for study plan generation and code execution, where reasoning quality visibly matters.

### Scoring a request

The scorer in `services/llm/complexity.py` (196 lines) adds up four signals:

**1. Message length** (0–150 points): Short messages rarely need deep reasoning. Anything over 500 chars is likely a complex question.

**2. Intent** (0–300 points): The intent classifier already runs for other purposes, so I reuse its output here. "learn" intent gets 150 points; "plan" or "code" gets 250.

**3. Active scene** (0–100 points): Exam prep mode gets 80 points; basic study session gets 0.

**4. Complexity markers** (0–100 points, capped): A regex pass over the message. Each matched phrase adds 25–50 points:

```python
_COMPLEXITY_PATTERNS = [
    (re.compile(r"\bcompare\b", re.IGNORECASE), 30),
    (re.compile(r"\bstep[- ]by[- ]step\b", re.IGNORECASE), 40),
    (re.compile(r"\bprove\b", re.IGNORECASE), 50),
    (re.compile(r"\bderive\b", re.IGNORECASE), 40),
    (re.compile(r"\banalyze\b|\banalyse\b", re.IGNORECASE), 30),
    # CJK complexity markers too (the app supports Chinese)
    (re.compile(r"证明|推导"), 50),
    (re.compile(r"比较|对比"), 30),
]
```

A RAG-context bonus (+50) fires if retrieval results are injected, since the model needs to synthesize across multiple source passages.

Total score < 150 → FAST. ≥ 500 → FRONTIER. Between → STANDARD.

### Agent minimums override the score

The scoring gives you a floor based on message content. But some agents should never use a small model regardless of the message — you don't want the planning agent generating a study schedule with llama3.2:3b even if the user typed a short message.

```python
AGENT_MIN_TIERS: dict[str, ModelTier] = {
    "preference": ModelTier.FAST,
    "scene": ModelTier.FAST,
    "teaching": ModelTier.STANDARD,
    "exercise": ModelTier.STANDARD,
    "planning": ModelTier.FRONTIER,
    "code_execution": ModelTier.FRONTIER,
}

def resolve_tier(agent_name: str, message: str = "", intent: str = "general",
                 scene: str = "study_session", history_length: int = 0,
                 has_rag_context: bool = False) -> ModelTier:
    score = score_complexity(message=message, intent=intent, scene=scene,
                              history_length=history_length, has_rag_context=has_rag_context)
    scored_tier = ModelTier.FRONTIER if score >= 500 else \
                  ModelTier.STANDARD if score >= 150 else ModelTier.FAST

    agent_min = AGENT_MIN_TIERS.get(agent_name, ModelTier.STANDARD)
    tier_order = {ModelTier.FAST: 0, ModelTier.STANDARD: 1, ModelTier.FRONTIER: 2}
    return scored_tier if tier_order[scored_tier] >= tier_order[agent_min] else agent_min
```

`resolve_tier()` returns the higher of the scored tier and the agent minimum. If the teaching agent receives a message that scores FAST, it still runs on STANDARD — the agent minimum wins.

### Hooking into the provider registry

The provider registry (`router.py`, 399 lines) supports model-preference hints:

```python
# Registering tier variants
registry.register_variant("fast", ollama_3b_client)
registry.register_variant("standard", ollama_8b_client)
registry.register_variant("frontier", deepseek_client)

# Usage at call site
tier = resolve_tier(agent_name="teaching", message=user_message, intent=intent)
client = registry.get(tier.value)   # "fast" | "standard" | "frontier"
response = await client.chat(messages)
```

The `get()` method checks model variants first, then falls back to primary and the fallback chain if the variant's circuit breaker is open. This means a FRONTIER request that finds DeepSeek circuit-open automatically falls through to whatever's healthy — the tier is a preference, not a hard requirement.

### Does it work?

In practice, ~65% of requests route to STANDARD, ~25% to FAST, and ~10% to FRONTIER. The fast-tier requests (preferences, layout changes, short factual questions) complete in 0.3–0.6s on llama3.2:3b locally. The STANDARD requests average 1.5–3s. FRONTIER requests (mostly study plan generation) take 4–8s on DeepSeek — but those are expected to be slow and are generated once, not interactively.

The complexity scoring is not perfectly calibrated, and I expect to tune the thresholds as I collect more data. The important property is that miscategorization is asymmetric: routing a FRONTIER request to STANDARD produces a mediocre but functional response. Routing a FAST request to FRONTIER is wasteful but correct. The conservative design (agent minimums floor most agents at STANDARD) means misfires in the "too capable" direction are more common than quality failures.
