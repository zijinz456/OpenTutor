## b) r/LocalLLaMA

**Title:** How OpenTutor decides which model to route each call to — task-based size hints in a local-first tutor

**Post:**

An AI tutor makes a lot of LLM calls per user interaction and not all of them need a big model. We've been fine-tuning this in OpenTutor (self-hosted, MIT) and wanted to share what actually works.

**The routing problem:**

Each interaction routes through several calls: intent classification → agent dispatch → main response → optional background tasks (knowledge graph update, confusion pair detection). These are async and don't all block the response, but the front-end two still add up. Using the same model for all of them is wasteful; on 3B you sacrifice quality on the main response, on 8B you pay latency on intent classification that's genuinely a cheap task.

We added variant registration to the `ProviderRegistry`:

```python
# apps/api/services/llm/router.py

registry.register_variant("fast", small_client)   # llama3.2:3b
registry.register_variant("large", large_client)  # llama3.1:8b or llama3.3:70b

# In agents:
intent_client  = registry.get_variant("fast")
teaching_client = registry.get_variant("large")
```

If the "large" variant isn't registered (you only pulled 3B), it falls back to whatever healthy provider is available. This means local-only setups still work, and cloud providers can kick in specifically for the high-quality calls without paying cloud rates for every intent classification.

**Practical numbers on M2 Pro (32GB):**

- llama3.2:3b intent classification: ~0.9–1.4s, adequate quality
- llama3.2:3b teaching response: 7–14s, structural output issues on complex content
- llama3.1:8b teaching response: 10–18s, noticeably better quiz generation and structured notes
- Background tasks (async): knowledge graph update adds 0–2s to wall time since it runs after the stream starts

The JSON parsing failures on 3B for structured output (quiz generation, difficulty metadata extraction) are real. We handle them with a retry + prompt-repair path: truncated arrays get closed, single-quoted keys get replaced, and common LLM formatting mistakes get normalized before the JSON parse attempt. That alone took llama3.2:3b from ~60% parse success on complex quiz prompts to ~90%.

The circuit breaker still protects all of this — 3 consecutive failures trips the breaker, 120-second auto-reset, falls through the fallback chain. So Ollama primary + DeepSeek fallback + OpenAI tertiary is a valid config and switches automatically.

Three commands: `git clone https://github.com/zijinz456/OpenTutor`, `cp .env.example .env`, `docker compose up -d --build`.

## c) r/Anki

**Title:** We track 11 behavioral signals to decide when to surface flashcard reviews — here's why FSRS alone isn't enough

**Post:**

We run FSRS 4.5 (310 lines, pure Python, `apps/api/services/spaced_repetition/fsrs.py`) in OpenTutor as the core flashcard scheduler. The algorithm is solid — but after a few months of real usage, we noticed a gap: FSRS schedules when you're *statistically* at risk of forgetting, but it doesn't know when you're *actually in a good state to study*.

**The problem:**

FSRS's default target retention is 90%. It schedules the next review when predicted recall drops below that threshold. That's the right signal for "you're about to forget this," but not for "right now is a good time to study this." If you've been doing intensive review for 45 minutes and your wrong-answer streak is at 4, surfacing more cards at their FSRS-due moment is probably the wrong call.

**What we added:**

The cognitive load module (`apps/api/services/cognitive_load.py`) computes a 0–1 load score from 11 signals and feeds it into review scheduling:

```python
# apps/api/services/cognitive_load.py

signals["fatigue"]          = fatigue_score
signals["session_length"]   = session_fatigue      # ramps up after 40 min
signals["unmastered_errors"] = error_signal        # unreviewed wrong answers
signals["message_brevity"]  = brevity_signal       # short replies = disengagement
signals["help_seeking"]     = help_signal          # "I don't understand", "hint"
signals["quiz_performance"] = perf_signal          # recent quiz accuracy
signals["answer_hesitation"] = timing_signal       # slow responses
signals["nlp_affect"]       = nlp_signal           # sentiment from LLM affect probe
signals["wrong_streak"]     = streak_signal        # consecutive wrong answers
signals["repeated_errors"]  = repeated_error_sig   # same card wrong multiple times
signals["message_gap"]      = gap_signal           # idle time between messages
```

When load score is high (0.7+), the scheduler deprioritizes new cards, reduces the number of due cards surfaced per session, and the tutor switches to lower-depth explanations. When you're in a low-load state, it pushes harder material.

**How this differs from Anki's Load Balance add-on:**

Anki's load balancing distributes reviews across days to avoid pile-ups. That's a *scheduling density* problem. What we're solving is a *session-state* problem: not how many cards per day, but whether to show the next card *right now* given your current cognitive state.

The LECTOR module also extends FSRS by clustering related concepts (confusion pairs from the knowledge graph) for co-review and ensuring prerequisites are reviewed before dependents. So if you have poor retention on a concept, it checks whether you've actually mastered its prerequisites in the graph before surfacing advanced cards.

If you want to look at the FSRS implementation: `apps/api/services/spaced_repetition/fsrs.py` — 310 lines, 21 parameters (FSRS 4.5 parameters), no external FSRS library dependency. Repo: https://github.com/zijinz456/OpenTutor (MIT).

## e) Dev.to / Hashnode — Technical Article

**Title:** How I built real-time cognitive load detection into an AI tutor (11 behavioral signals, no ML model)

An AI tutor that teaches at a fixed depth and pace isn't really adaptive — it's just an LLM with a nice UI. For OpenTutor, we wanted something that actually notices when a learner is struggling and dials back, or pushes harder when they're breezing through. Here's the architecture we landed on and the specific decisions that shaped it.

### The Core Idea: Load Score as System Prompt Injection

Rather than trying to train a bespoke ML model on student behavior (data we don't have), we composite 11 hand-designed behavioral signals into a 0–1 cognitive load score, then inject a guidance string into the tutor agent's system prompt at every turn.

```python
# apps/api/services/cognitive_load.py

async def compute_cognitive_load(
    db: AsyncSession,
    user_id: uuid.UUID,
    course_id: uuid.UUID,
    fatigue_score: float = 0.0,
    session_messages: int = 0,
    user_message: str = "",
) -> dict:
    """Returns: score (0.0–1.0), signals breakdown, intervention guidance."""
    signals: dict[str, float] = {}

    # 1. Explicit fatigue (passed from fatigue detector)
    signals["fatigue"] = fatigue_score

    # 2. Session length ramp (starts loading after ~40 messages)
    session_fatigue = min(session_messages / 40.0, 1.0) * 0.6
    signals["session_length"] = session_fatigue
    ...
```

The final score is a weighted sum. When the score exceeds 0.7, the guidance string tells the tutor to simplify explanations, reduce question difficulty, and surface fewer due review cards. Below 0.3, it pushes harder material and allows longer, more complex explanations.

### The 11 Signals

Here's the breakdown of signals we track, each normalized to 0–1:

**Message-level signals** (computed per turn):
- `message_brevity` — very short messages correlate with disengagement; threshold at 10 chars
- `help_seeking` — matches patterns like "I don't understand", "hint", "confused"
- `answer_hesitation` — computed from the gap between the tutor's last message and the student's reply
- `message_gap` — idle time between messages (>5 min suggests attention loss)
- `nlp_affect` — LLM-based affect probe: "is this student's message positive, neutral, or frustrated?"

**Session-level signals** (queried from DB):
- `session_length` — ramps from 0 to 0.6 over 40 messages
- `quiz_performance` — recent correct/total ratio from the last N quiz submissions
- `wrong_streak` — consecutive wrong answers in the current session
- `repeated_errors` — the same question missed multiple times across sessions
- `unmastered_errors` — wrong answers that haven't been reviewed/mastered yet
- `fatigue` — explicit signal from the fatigue text detector (looks for fatigue cues in the message)

The NLP affect probe is worth explaining: rather than a lightweight sentiment classifier, we just ask the LLM itself in a low-cost call. The prompt is a few sentences asking for a JSON `{affect: "positive"|"neutral"|"frustrated"|"confused"}`. It's cached per user so it doesn't add latency to every turn.

### Injecting Into the Tutor

At the end of `compute_cognitive_load`, we call `_build_guidance(level, score, signals)` which returns a string like:

> "Student appears to be in a high cognitive load state (score: 0.82). Signals: session_length=0.6, wrong_streak=0.8, unmastered_errors=0.5. Recommendation: Simplify explanations. Use shorter sentences. Avoid introducing new concepts. If the student asks a complex question, acknowledge it and offer to break it down step by step."

This string gets prepended to the tutor's system prompt on every turn. The LLM doesn't need to understand cognitive load theory — it just follows the natural-language instruction.

### What We Learned

The approach works better than we expected for a hand-designed system. The main insight: behavioral signals are noisy individually but robust in combination. `message_brevity` alone fires constantly (users send short messages all the time); combined with `wrong_streak` and `answer_hesitation`, it's a genuinely useful signal.

The NLP affect probe turned out to be valuable despite feeling like overkill. Pure behavioral signals miss the case where a student is writing long messages but expressing frustration in them. The affect probe catches that.

The calibrator is still early-stage — we're collecting data. But the architecture is in place and the signal is there in the per-user weight multipliers.
