## b) r/LocalLLaMA

**Title:** `My local AI tutor's circuit breaker + fallback chain for LLM providers (MIT, runs with llama3.2:3b)`

---

If you run local LLMs as the backend for an app — not just interactive use — you hit a problem: model servers go down, OOM-kill themselves, or just time out under load. You need graceful degradation. Here's how OpenTutor handles it.

The circuit breaker is a `CircuitBreakerMixin` (83 lines, `services/llm/circuit_breaker.py`) that any LLM client subclasses. It tracks two failure modes separately:

**Progressive cooldown** — the first failure puts the provider in a 5-second cooldown. Second failure: 10s. Third: 20s. Fourth and beyond: 60s. This handles transient Ollama hiccups without immediately routing all traffic elsewhere.

**Circuit breaker** — after 3 consecutive failures the circuit opens hard. No more requests until a 120-second timeout passes, then it auto-resets and tries one probe request. If that succeeds, `mark_healthy()` clears all counters.

```python
COOLDOWN_STEPS = [5, 10, 20, 60]       # progressive cooldown
CIRCUIT_OPEN_THRESHOLD = 3             # failures before open
CIRCUIT_RESET_TIMEOUT = 120            # seconds before auto-reset

def mark_unhealthy(self, error: str):
    self._consecutive_failures += 1
    if self._consecutive_failures >= CIRCUIT_OPEN_THRESHOLD:
        self._circuit_open = True
        self._circuit_open_time = time.time()
        return
    idx = min(self._consecutive_failures - 1, len(COOLDOWN_STEPS) - 1)
    self._cooldown_until = time.time() + COOLDOWN_STEPS[idx]
```

On top of that, a `ProviderRegistry` holds an ordered fallback chain. `registry.get()` walks the chain, skipping any provider where `is_healthy` returns False, and returns the first healthy one. If all providers are down, it raises `LLMConfigurationError` instead of silently returning garbage.

The complexity router layered above this routes 40% of typical study-session requests to the fast tier (llama3.2:3b) — greetings, preference changes, short factual lookups. Standard tier (llama3.1:8b) gets teaching and exercise generation. Planning and multi-step reasoning go to frontier, which can fall back to a cloud endpoint if configured. On a 16GB Mac: fast-tier avg ~340ms, standard-tier ~1.2s. Without routing, everything would hit 8b; with it, average latency drops roughly a third for a typical session.

Default config is Ollama + llama3.2:3b, zero API costs. Drop-in support for OpenAI, Anthropic, DeepSeek, Gemini, Groq, vLLM, LM Studio, OpenRouter, any OpenAI-compatible endpoint via `.env`. MIT. https://github.com/zijinz456/OpenTutor

## c) r/Anki

**Title:** `OpenTutor upgraded its FSRS from 4.5 to 5/6 — here's what changed and why it matters for spaced repetition`

---

OpenTutor's FSRS implementation just upgraded from FSRS-4.5 (17 parameters) to FSRS-5/6 (21 parameters). If you use Anki's built-in FSRS, you're already on a version of this algorithm — so here's a concrete breakdown of what the newer variant adds and whether any of it matters in practice.

**Trainable forgetting curve decay.** FSRS-4.5 uses a fixed power-law forgetting curve: `R(t) = (1 + t/9S)^(-1)`. FSRS-5/6 adds a decay parameter `w[20]` that the optimizer can tune: `R(t) = (1 + factor·t/S)^(-decay)` where `factor = 9 * decay`. At the default `decay = 1.0` this is identical to 4.5. When optimized on your own review history it can fit non-power-law forgetting curves — relevant for complex conceptual material versus simple vocabulary, which often have different decay shapes.

**Same-day review handling.** If you review a card twice in the same day (elapsed < 1 day), FSRS-4.5 applies the standard stability update, which inflates stability from multiple intra-day reviews. FSRS-5/6 has a separate formula: `S' = S * exp(w17 * (G - 3 + w18)) * S^(-w19)`. With default params `[w17=0, w18=0, w19=0]` it falls back to standard behavior, but when tuned, same-day reviews increase stability much less than once-per-day reviews. This matters if you do morning + evening reviews on new cards.

**Exponential difficulty initialization.** FSRS-4.5 uses linear: `D0 = w4 - (G-3)*w5`. FSRS-5/6 uses `D0 = w4 - exp(w5*(G-1)) + 1`. The exponential form widens the gap between rating-1 initial difficulty and rating-4 initial difficulty, which better matches empirical data on how much a "Again" first review really signals difficulty versus an "Easy" first review.

In practice, the gains from 4.5 → 5/6 are smaller than the gains from SM-2 → FSRS-4.5 were. The docs quote 30%+ accuracy improvement over SM-2; the 4.5 → 5/6 jump is single digits on most benchmarks, concentrated in users with large review histories who actually benefit from parameter optimization.

OpenTutor adds two layers above FSRS: LOOM tracks prerequisite relationships between concepts, and LECTOR uses the knowledge graph to order reviews — prerequisites before dependents, confusion pairs clustered — which is orthogonal to FSRS scheduling but compounds the accuracy gains. The scheduler is in `services/spaced_repetition/fsrs.py` (304 lines), MIT. Self-hosted, runs locally. https://github.com/zijinz456/OpenTutor

## d) r/GetStudying / r/medicalschool

**Title:** `The review habit that actually prevents the "I knew this last week" problem`

---

There's a pattern I see a lot (and did myself): spend two hours reviewing material, feel confident, then come back three days later and half of it is gone. Not hazy — actually gone.

The reason isn't that you didn't study enough. It's timing. There's a window after you first learn something where reviewing it would cement it at minimal cost. Outside that window, you're essentially re-learning from scratch. The catch is that the window is different for every piece of information and you can't feel where it is from the inside.

What I changed: instead of reviewing on a fixed schedule ("I'll do chapter 3 again on Saturday"), I started tracking which specific *concepts* felt shaky after each session — not which chapters, but which mechanisms or principles I couldn't fully reconstruct on demand. Those got reviewed within 24 hours. The ones I felt solid on didn't — reviewing something you already know cold is low-ROI.

The harder part: distinguishing "I feel like I know this" from "I can actually reproduce this." These feel the same from the inside but they're not the same skill. Recognition (seeing an answer and knowing it's right) develops much faster than recall (generating the answer from nothing). For med school in particular, exam questions test recall, not recognition — you don't get to pick from options, you need to write the mechanism.

The test I use: close everything and explain the concept in one paragraph as if teaching someone who just started the unit. If I can do it fluently, it's genuinely encoded. If I'm reaching for words or finding gaps, I know exactly what to review and why — not just "I need to review cardio" but "I don't have the mechanism for afterload effects on stroke volume locked in."

I built something that does this tracking automatically (OpenTutor — open source, runs locally, no cloud). It tracks a recall probability per concept using FSRS-5/6, schedules proactive reminders when the expected number of forgotten cards crosses a threshold, and surfaces exactly which concepts to review and when. But honestly, the manual version — consciously identifying the specific gap after each session instead of re-reading the whole chapter — is the habit that matters. The tool just means you don't have to hold the tracking in your head.

What study method are you using to distinguish recognition from recall? Especially curious how people handle this for pharm or physiology where the mechanism chains are long.

## e) Dev.to / Hashnode — Technical Article

**Title:** How I built a three-tier LLM router with circuit breakers for my local-first AI tutor

---

When you're building a learning app that calls an LLM for everything — generating explanations, quiz questions, study plans, flashcard reviews — the naive implementation is a single API call for every request. That works fine in development. In production (even "production" meaning someone running this on their laptop for 3 hours of study), it breaks badly: one slow model response blocks the UI, provider failures kill the session, and you're paying the same inference cost for "hi" as for "generate a 4-week curriculum plan."

OpenTutor's solution is a three-layer system: a complexity scorer that decides which model tier to use, a provider registry with automatic fallback, and a circuit breaker mixin that handles provider failures gracefully. Here's how each layer works.

### Layer 1: Complexity scoring without an LLM call

The irony of using an LLM to classify whether you need an LLM is real. OpenTutor's complexity scorer (`services/llm/complexity.py`, 196 lines) scores each incoming request on five heuristics and maps it to `fast`, `standard`, or `frontier`:

```python
def score_complexity(
    message: str,
    intent: str = "general",
    scene: str = "study_session",
    history_length: int = 0,
    has_rag_context: bool = False,
) -> int:
    score = 0
    score += _score_message_length(message)           # 0–150
    score += _score_intent(intent)                    # 0–300
    score += _score_scene(scene)                      # 0–100
    score += _score_conversation_depth(history_length) # 0–80
    score += _score_complexity_markers(message)        # 0–100, capped
    if has_rag_context:
        score += 50   # RAG synthesis benefits from a stronger model
    return score

# score < 150  → fast tier   (llama3.2:3b locally)
# 150–499      → standard    (llama3.1:8b locally)
# 500+         → frontier    (cloud fallback if configured)
```

Intent carries the most weight — a `preference` change scores 30, a `learn` intent scores 150, `plan` scores 250. Complexity markers add up from keyword patterns: `"prove"` and `"derive"` add 50 and 40 respectively; `"compare"` and `"analyze"` add 30 each. CJK markers work the same way (`证明` and `推导` for "prove/derive", etc.).

On top of the scored tier, each agent type has a minimum tier floor:

```python
AGENT_MIN_TIERS: dict[str, ModelTier] = {
    "preference": ModelTier.FAST,
    "scene": ModelTier.FAST,
    "teaching": ModelTier.STANDARD,
    "exercise": ModelTier.STANDARD,
    "planning": ModelTier.FRONTIER,
    "code_execution": ModelTier.FRONTIER,
}
```

The router returns `max(scored_tier, agent_min_tier)`. A 2-word message to a planning agent still goes frontier. A long preference update stays fast. This lets you set hard floors on quality-sensitive paths while still routing cheap requests cheaply.

In practice, about 40% of requests in a typical study session score below 150 — greetings, preference changes, short factual lookups. With routing, average latency on a 16GB Mac drops roughly a third versus sending everything through llama3.1:8b.

### Layer 2: Circuit breaker for provider failures

LLM servers — especially local ones — go down unpredictably: OOM kills, timeout spikes, Ollama restart cycles. A plain HTTP timeout cascades into a stuck UI. The circuit breaker (`services/llm/circuit_breaker.py`, 83 lines) breaks that cascade:

```python
COOLDOWN_STEPS = [5, 10, 20, 60]       # progressive cooldown per failure
CIRCUIT_OPEN_THRESHOLD = 3             # consecutive failures before open
CIRCUIT_RESET_TIMEOUT = 120            # seconds before auto-reset

class CircuitBreakerMixin:
    def mark_unhealthy(self, error: str):
        self._consecutive_failures += 1
        if self._consecutive_failures >= CIRCUIT_OPEN_THRESHOLD:
            self._circuit_open = True
            self._circuit_open_time = time.time()
            logger.error(f"Circuit OPEN for {self.provider_name} after "
                         f"{self._consecutive_failures} failures: {error}")
            return
        idx = min(self._consecutive_failures - 1, len(COOLDOWN_STEPS) - 1)
        self._cooldown_until = time.time() + COOLDOWN_STEPS[idx]

    @property
    def is_healthy(self) -> bool:
        if self._circuit_open:
            if time.time() - self._circuit_open_time >= CIRCUIT_RESET_TIMEOUT:
                self._circuit_open = False
                self._consecutive_failures = 0
            else:
                return False
        if self._cooldown_until > 0 and time.time() >= self._cooldown_until:
            self._healthy = True
            self._cooldown_until = 0
        return self._healthy
```

The two failure modes are separate by design. Progressive cooldown handles the transient case — Ollama hiccupping under memory pressure — without routing all traffic elsewhere. The hard circuit open handles sustained failures and stops hammering a provider that's actually down.

The `ProviderRegistry` (in `router.py`, 399 lines total including re-exports) holds an ordered fallback chain. `registry.get()` walks the chain, skips any provider where `is_healthy` returns False, and returns the first healthy one. If every provider is unhealthy, it raises `LLMConfigurationError` immediately rather than returning a degraded result that would confuse the user.

### Layer 3: FSRS-5/6 scheduling the review queue

The spaced repetition layer is separate from the LLM routing but it feeds into it: when to generate a new flashcard review session is determined by `estimate_forgetting_cost()`, which sums expected forgotten cards across the queue:

```python
def estimate_forgetting_cost(cards: list[FSRSCard], now=None) -> float:
    """Sum (1 - R(t)) across overdue cards. >= 2.0 triggers a proactive reminder."""
    now = _as_utc(now or datetime.now(timezone.utc))
    total_expected_forgotten = 0.0
    for card in cards:
        if card.due is None or card.stability <= 0:
            continue
        due = _as_utc(card.due)
        if due > now:
            continue
        elapsed = max((now - due).total_seconds() / 86400, 0)
        total_elapsed = elapsed + max(card.stability, 1.0)
        recall_prob = _retrievability(total_elapsed, card.stability)
        total_expected_forgotten += (1.0 - recall_prob)
    return round(total_expected_forgotten, 2)
```

The scheduler uses FSRS-5/6 with 21 parameters (up from FSRS-4.5's 17). The key additions are a trainable forgetting curve decay (`w[20]`, default 1.0 for backward compatibility with 4.5), separate same-day review stability handling to prevent intra-day inflation, and exponential difficulty initialization `D0 = w4 - exp(w5*(G-1)) + 1`. The full implementation is `services/spaced_repetition/fsrs.py` (304 lines).

### What the combination gives you

The three layers operate independently but compose well. The complexity scorer decides how much inference to spend per request. The circuit breaker ensures provider failures degrade gracefully instead of hanging. The FSRS scheduler decides when to generate new review sessions, keeping the LLM work front-loaded at the right time rather than on-demand. Together, a study session on a 16GB MacBook with Ollama runs without cloud costs and with predictable latency — fast-tier requests average ~340ms, standard-tier ~1.2s.
