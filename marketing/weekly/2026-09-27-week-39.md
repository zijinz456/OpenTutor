## Reddit Post — r/LocalLLaMA

**Title:** I built a knowledge-graph layer on top of FSRS that orders your review queue by prerequisites — zero extra LLM calls at review time

**Body:**

OpenTutor is an open-source, local-first AI learning tool (FastAPI + Next.js + SQLite, runs against Ollama or any OpenAI-compatible endpoint, MIT license). I've been writing about individual pieces as I go. This week I want to write about the scheduling layer because it's the most technically interesting thing in the codebase and hasn't gotten a dedicated post.

**The problem with flat spaced repetition**

FSRS tells you when to review each card. It does this extremely well — the algorithm is research-backed, the default parameters generalize to most learners, and implementations like Anki's get the mechanics right. But FSRS treats your knowledge as a flat list of independent items. It has no model of the relationships between what you know.

In practice, concepts aren't independent. If you haven't mastered the Chain Rule, reviewing Related Rates problems is mostly wasted effort — you'll fail for the wrong reason, the scheduler will down-weight the card, and you'll see it more often without fixing the actual gap. The problem isn't forgetting; it's that a prerequisite is weak.

**LOOM: knowledge graph with decayed mastery**

LOOM (`apps/api/services/loom_graph.py`, 429 lines) builds a per-student concept graph when a course is ingested. The LLM extracts concept nodes and draws typed edges between them: `prerequisite`, `related`, `confused_with`, `reinforces`. Each node carries a mastery score that's not a raw average of your quiz results — it's that score multiplied by FSRS retrievability:

```
effective_mastery = raw_mastery * fsrs_retrievability(days_elapsed, stability_days)
```

So a concept you peaked at 0.85 mastery six weeks ago but haven't touched decays toward the floor. The graph stays live rather than being a static snapshot.

Learning path generation uses Kahn's algorithm over the prerequisite subgraph, filtered to unmastered concepts (mastery < 0.8), sorted by Bloom taxonomy level within each topological tier. The idea is to surface foundational knowledge before application-level concepts even when both are formally unmastered.

**LECTOR: 7-factor priority scorer**

LECTOR (`apps/api/services/lector.py`, 344 lines, based on arXiv:2508.03275) is the review scheduler that sits on top of LOOM. For each concept, it computes a priority score from 7 factors:

1. Low mastery — how far below threshold
2. Never practiced — first-time boost
3. Time decay — days since practice vs. stability estimate
4. Prerequisite at risk — if a prerequisite is weak, boost this concept's priority and mark review type as `prerequisite_first`
5. Confusion pair — if a confused concept has low mastery, boost and mark as `contrast`
6. FSRS overdue — explicit retrievability calculation from the FSRS schedule
7. Proactive interference — high-weight `confused_with` edges get a priority boost regardless of the confused concept's current mastery, catching potential confusion before the learner makes the mistake

Factor 4 and factor 7 are the departures from plain FSRS. Factor 4 means a concept can jump ahead in the review queue not because it's overdue, but because its prerequisite is weak. Factor 7 surfaces confusion pairs proactively — the "contrast" review type appears before the learner fails the card, not as a correction after.

**No extra LLM calls at review time**

The graph traversal and priority scoring are synchronous arithmetic. The only LLM work happens at ingestion time (concept extraction) and optionally for the interference matrix (embedding-based similarity). At review time, LECTOR is a database read and a sort — fast enough that it runs on every session start.

**Cross-course linking**

`link_cross_course_concepts()` runs at ingestion time and creates bidirectional `reinforces` edges between same-name concepts across different courses. Crude (exact name match), but it means "eigenvalue" in your Linear Algebra course and "eigenvalue" in your Machine Learning course aren't treated as completely separate. Future iteration: semantic similarity with embeddings.

The code is at github.com/zijinz456/opentutor. LOOM is `apps/api/services/loom_graph.py`, LECTOR is `apps/api/services/lector.py`. The LECTOR paper (arXiv:2508.03275) is worth reading if you're interested in the theoretical framing.

For those running local LLM setups: have you found a way to do prerequisite-aware review ordering with Anki add-ons, or is this genuinely a gap in the current ecosystem?

## Reddit Post — r/Anki

**Title:** Anki doesn't know that Chain Rule is a prerequisite for Related Rates. Here's an open-source system that does.

**Body:**

I've been building OpenTutor, an open-source AI tutor that uses FSRS 4.5 for scheduling — same algorithm as Anki's current default. I want to write about a specific problem I hit and how I tried to solve it, because I suspect others have run into the same thing.

**The gap FSRS doesn't fill**

FSRS is excellent at answering "when should I review this card?" It does not answer "should I review this card before that one?" Those are different questions. For isolated facts — vocabulary, capital cities, definitions — the ordering doesn't matter much. For anything with dependencies — math, chemistry, programming concepts — it matters a lot.

I was studying calculus and kept struggling with Related Rates problems even though my FSRS-scheduled reviews showed them regularly. Eventually I realized my Chain Rule mastery had decayed without me noticing. I was reviewing Related Rates on schedule, failing for Chain Rule reasons, getting those cards penalized, and reviewing them even more often — without fixing the underlying gap. The scheduler was working correctly; the problem was that it had no model of the dependency.

**What I built**

The system has two parts:

LOOM builds a knowledge graph when you upload a course. Concept nodes have mastery scores that decay over time using the FSRS retrievability formula — not just "what's your peak score" but "what's your score adjusted for how long ago you last practiced." Edges between nodes are typed: `prerequisite`, `related`, `confused_with`, `reinforces`.

LECTOR is the review scheduler on top of that graph. It scores each concept by urgency with 7 factors. The important one: if a concept's prerequisite is weak (below a threshold), that concept jumps up in the queue with a `prerequisite_first` review type — meaning the system surfaces the prerequisite first, even if the dependent concept is technically more overdue by FSRS rules.

There's also a proactive interference factor. Concepts that students commonly confuse get `confused_with` edges with weights. When that edge weight is high enough, both concepts get bumped into a `contrast` review session together — before either card fails, not as a correction afterward. The weight comes from an embedding-based confusion matrix computed at ingestion time.

**Where it falls short**

The graph is extracted by an LLM and it makes mistakes. Prerequisites that a domain expert would draw aren't always what the LLM infers from the course text. The cross-course linking is exact name matching, not semantic similarity, which misses related concepts with different names. And I haven't done a rigorous comparison to see whether prerequisite-aware ordering actually improves retention rates over plain FSRS — I'm working from the LECTOR paper (arXiv:2508.03275) and intuition.

The code is MIT licensed at github.com/zijinz456/opentutor. LOOM is 429 lines, LECTOR is 344 lines. The FSRS implementation reuses the standard algorithm.

For Anki users: have you found add-ons that handle prerequisite ordering, or do you manage that manually by structuring your decks? I'm trying to understand whether this problem has existing solutions I haven't found.

## IndieHackers Post

**Title:** I've been building a local-first AI tutor for six months. The hardest problem isn't the AI — it's knowing what to review next.

**Body:**

I've been working on OpenTutor since late 2025 — an open-source AI tutoring tool that runs entirely on your own machine. FastAPI backend, Next.js frontend, SQLite, connects to Ollama or any OpenAI-compatible API. No cloud, no subscription, no data leaving your device.

I started because I was frustrated with how I studied. I'd read something, feel like I understood it, take a quiz two weeks later, and fail. Then I'd go back and realize the thing I'd actually forgotten was a foundational concept from two weeks before the one I was reviewing. My study sessions were optimized by the scheduler but not by the structure of the material.

So I tried to build something that could do both.

**What I shipped in April and haven't written about until now**

The scheduling system — LOOM and LECTOR, 773 lines total — has been in the codebase since April. I've written about other things (the dashboard redesign, the LLM complexity router, the circuit breaker) but not about scheduling, even though it's the core differentiator.

LOOM is a knowledge graph: when you upload a course, an LLM extracts the concepts and draws typed edges between them. Prerequisites, related ideas, concepts that get confused together. Each concept node carries a mastery score that decays over time using the FSRS retrievability formula — the same math that Anki uses to estimate how much you've forgotten.

LECTOR sits on top of that graph and decides what to review. The key departure from plain FSRS: if a concept's prerequisite is weak, that concept gets reviewed as `prerequisite_first`, meaning the system surfaces the prerequisite before the dependent concept even if the dependent card is technically more overdue. It also flags concepts that commonly get confused together and surfaces them in the same session for contrast review — proactively, before you fail the card, not as a correction afterward.

**What was hard about it**

The graph extraction is the weakest part. The LLM infers prerequisites from the course text, and it makes mistakes. Edges that a domain expert would draw instantly — "you need limits before derivatives" — sometimes get missed or reversed. I've had to add retry logic for transient LLM failures and accept that the graph won't be perfect on the first pass.

The other hard part was deciding what "mastery" means when it's time-decayed. A student who scored 0.9 on a concept three months ago and hasn't touched it since isn't at 0.9 mastery anymore. Multiplying the raw score by FSRS retrievability gives you a more honest number, but it also means the effective mastery of a well-learned concept degrades continuously — which could be demotivating if the UI just shows declining numbers. I haven't solved the UX of that yet.

**Honest about where things stand**

No new code in the past 15 weeks. I've been writing marketing content and tracking health metrics but not shipping features. The health score on the repo has been declining by 1 point per week because CI hasn't run against any new code. The CHANGELOG is 196 days out of date. The README still has a TODO placeholder where the demo GIF should be, and it's been there for 21 weeks.

I'm writing this partly to hold myself accountable. The system works — I use it to study. The gap is everything around it: documentation, demo, contributor onboarding. Those feel less interesting to work on than the scheduling layer, and that's exactly why they've been neglected for six months.
