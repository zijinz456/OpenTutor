## Reddit Post — r/LocalLLaMA

**Title:** I added LLM-graded coding questions to my local AI tutor — deliberately skipped code execution, here's why

**Body:**

OpenTutor is an open-source, local-first AI learning platform. FastAPI + Next.js + SQLite, runs on Ollama or any OpenAI-compatible endpoint. You upload study material, the system generates practice questions and explanations, tracks performance with FSRS 4.5, and adjusts tutor behavior in real-time based on cognitive load signals.

Last week I shipped a new question type: coding. You upload a programming textbook or course notes, the LLM extracts coding questions from the content (write this function, implement this algorithm), and a student can submit code and get graded.

**The non-obvious choice: no code execution**

The standard approach is to run the code. Sandbox it, execute it, compare output against expected values. I didn't do that.

OpenTutor grades coding submissions purely via LLM. The grading service sends three things to the model: the question text, the reference answer, and the student's code. The model returns a JSON object with `is_correct` (bool) and `feedback` (string, capped at 30 words). That's it.

The grading prompt is intentionally lenient on style and strict on correctness:

```
- Accept any correct implementation, not just the reference solution.
- Minor syntax variations (e.g. single vs double quotes, spacing) are fine.
- The logic must be functionally equivalent to the reference, not identical.
```

**Why not run the code**

Three reasons:

1. **Security surface.** Running untrusted code requires a real sandbox: container isolation, resource limits, network blocking, language-specific runtime management. I don't want to maintain that infrastructure and I don't want to introduce that attack surface in a local-first application that runs on your machine. The LLM grading path has no execution, no network call for code, no file system access.

2. **Language generality.** The LLM can grade Python, JavaScript, Rust, SQL, pseudocode, or any other language it understands. An execution sandbox needs a runtime installed. If someone uploads a Haskell textbook, I don't want to provision a GHC environment.

3. **The quiz system's purpose.** These questions are for learning, not certification. The grader's job is to give fast feedback so the FSRS scheduler knows whether to reinforce this problem sooner or later. It doesn't need to be bulletproof against adversarial submissions. If a student submits a plausible-but-wrong solution that fools the LLM, the FSRS algorithm will notice incorrect recall patterns downstream and schedule more reviews.

**The actual tradeoffs**

LLM grading misses runtime errors that only surface on edge-case inputs. A function that handles the example case in the reference answer but fails on empty input will likely pass. I accept that. The feedback message is capped at 30 words — the grader is a signal, not a tutor. The explanation field on the question itself is where detailed guidance lives.

The fallback is explicit: if the LLM call fails, the submission gets `is_correct: False, feedback: "Grading unavailable."` The student can retry. I'd rather fail closed than silently mark things correct.

**Integration with the annotation system**

Coding questions get `bloom_level: apply` and `skill_focus: implementation` by default in the annotation pipeline. That affects FSRS scheduling: apply-level questions get shorter initial intervals than remember/understand questions. The system treats writing code as harder to retain than recognizing a definition, which matches how I think about it.

The quiz parser now recognizes eight question types: mc, tf, short_answer, fill_blank, matching, select_all, free_response, coding. The extraction prompt tells the LLM to include coding questions specifically for programming/technical content. For non-technical material it ignores the coding type.

**What I'd do differently**

The feedback cap at 30 words is probably too short. I set it to prevent the grader from turning into a mini-tutor, but some coding questions need more explanation when the logic is subtly wrong. I'll probably raise it to 60 words and add a separate "hint" field.

OpenTutor repo: https://github.com/zijinz456/opentutor

Has anyone found LLM grading reliable enough for coding at production scale, or do you always end up needing execution?

## Reddit Post — r/Anki

**Title:** I added coding questions to my FSRS-based tutor — graded by LLM, no code execution, here's how it affects scheduling

**Body:**

I maintain OpenTutor, an open-source AI learning platform built around FSRS 4.5. You upload study material — textbooks, lecture notes, anything — and it generates practice questions, tracks your performance, and schedules reviews using the FSRS algorithm.

I shipped a new question type this month: coding. For programming textbooks or technical courses, the quiz generator now extracts coding problems — "write a function that does X", "implement this algorithm", "complete this method body." You type code in the practice interface, submit, and get graded.

**Why this matters for spaced repetition**

The existing question types (multiple choice, short answer, free response, etc.) test recall and comprehension. Coding questions test something different: procedural implementation. You can recognize the right answer among four options and still not be able to write the code from scratch. These are different memory traces.

FSRS schedules them differently because of the annotation system. Coding questions get `bloom_level: apply` by default, not `bloom_level: remember`. The system treats apply-level questions as harder to consolidate — shorter initial intervals, steeper forgetting curve assumption. In practice that means coding problems get reviewed more aggressively than matching recall to recognition.

This matches what Cognitive Load Theory would predict: writing code is generative, not recognitive. It requires reconstructing the procedure, not pattern-matching to stored examples.

**The grading mechanism**

There's no code execution. OpenTutor grades code submissions by sending your code + the reference answer to the LLM and asking it to judge functional equivalence. The grader accepts stylistic variation (different variable names, whitespace, equivalent constructs) and rejects logical errors.

Limitations: it can miss bugs that only surface on edge inputs, and it doesn't test against a test suite. For the purpose of spaced repetition scheduling, this is acceptable — I need a signal about whether you understood the implementation pattern, not a comprehensive correctness check. If the LLM incorrectly marks something correct, the downstream review sessions will surface the gap.

**Bloom taxonomy in the scheduler**

The annotation system assigns every practice problem a Bloom level, difficulty layer (1-3), skill focus, and potential traps. These feed into card ordering and interval adjustment:

- High cognitive load + low Bloom level → easier cards first, shorter intervals
- Low cognitive load + high Bloom level → challenge cards surfaced, longer intervals allowed
- apply/analyze/evaluate/create → more conservative initial intervals than remember/understand

Coding questions consistently land at `apply`, which is level 3 of 6. They don't get the longest intervals, but they get treated as more retention-resistant than recall questions.

**What's still missing**

The grader gives a brief feedback string (30 words max) but no line-by-line analysis. For wrong submissions it says what's wrong in general terms, not where in the code the error is. I'd need a more expensive grading prompt to get specific feedback, and I haven't decided if that's worth the latency on every submission.

OpenTutor is fully local — Ollama by default, any OpenAI-compatible endpoint. Repo: https://github.com/zijinz456/opentutor

For people using Anki for programming: do you use image occlusion of code, or do you find writing code from scratch (not multiple choice) actually builds better retention?

## IndieHackers Post

**Title:** I added coding questions to my local AI tutor. The grader doesn't run your code. Here's the honest case for why.

**Body:**

OpenTutor is an open-source, local-first AI learning platform I've been building. You upload study material, it generates practice questions and explanations, tracks performance with FSRS 4.5 spaced repetition, and adjusts tutor behavior in real-time. Local by default — Ollama or any OpenAI-compatible endpoint on your own machine.

This week I shipped coding questions. If you're studying from a programming textbook, algorithm course, or any technical material, the quiz generator now extracts coding problems: write a function, implement an algorithm, fill in the missing logic. You type code in the practice interface, submit, and get graded.

The part I want to be honest about: the grading is not what you'd expect.

**The choice I made**

I deliberately did not build a code execution sandbox.

When you submit a coding answer in OpenTutor, your code goes to the LLM with the reference answer and a grading prompt. The model checks if your logic is functionally equivalent to the reference. It returns `{"is_correct": true/false, "feedback": "brief reason"}`. That's the entire grading pipeline: 63 lines in `coding_grader.py`.

The obvious critique is that LLM grading is less reliable than execution. That's true. A solution that handles the example case but fails on edge inputs might pass. If I'm testing "implement binary search," a solution that only works on sorted arrays of unique integers might get marked correct.

I shipped it anyway. Here's why.

**The case against running code**

I'm not building LeetCode. OpenTutor is a learning platform for understanding material — it's not a certification system or a job interview tool. The coding questions serve one purpose: to test whether you've internalized an implementation pattern well enough to reproduce it. They feed the FSRS scheduler with a signal about your retention, not a comprehensive correctness check.

For that purpose, LLM grading is good enough. It catches logical misunderstandings — wrong algorithm, wrong data structure, misunderstood problem — which are the errors that actually indicate a gap in learning. It misses implementation bugs, which are often symptoms of not-quite-right practice rather than wrong understanding. The FSRS algorithm will schedule more reviews if you keep getting things wrong; it doesn't need a perfect grader, just an honest one.

The infrastructure argument matters too. Running untrusted code safely requires real sandboxing: container isolation, resource limits, network blocking, per-language runtime setup. I'm one person maintaining this project in my spare time. I don't want to maintain sandbox infrastructure. I want to keep the system simple enough that I understand all of it.

**What I was worried about**

The failure mode I spent the most time thinking about: a student submits plausible-but-wrong code, the LLM marks it correct, FSRS schedules the problem for a long interval, and the student never discovers the error until they need the skill in practice. That's a real concern.

My partial mitigation: the feedback string is capped at 30 words, but the question's explanation field (generated during quiz extraction) gives a full worked example. A student who passes a problem but reads the explanation and notices a difference has a natural correction path. It's not airtight.

The other mitigation is downstream: FSRS tracks wrong-answer streaks and mastery status across all question types. A student who consistently struggles with apply-level problems will have that reflected in their cognitive load score and their spaced repetition schedule, even if individual grading instances are imperfect.

**The thing that surprised me**

Building the UI took longer than the grader. The quiz view component needed a textarea for code input, a submit button, and a way to display code-specific feedback without conflating it with the explanation panel. That was 42 lines of changes across the existing quiz-view component. The grader itself was 63 lines. Frontend is always where the time goes.

**What I'd change**

The 30-word feedback cap is too aggressive. When a submission is wrong in a subtle way, the grader needs more room to explain it. I'll raise it to 60 words and probably add a separate "hints" field to the question schema so the grader can surface specific guidance without turning into a lecture.

I'd also like to add test case checking as an optional enhancement — the question could include example inputs/outputs, and the grader could report whether the submitted code handles them, even without executing it (the LLM can trace simple cases). Not a priority, but a clean path to better grading without full execution infrastructure.

OpenTutor: https://github.com/zijinz456/opentutor

What's the right threshold for "good enough" in an educational grader? Execution feels like the right answer until you think about the maintenance cost.
