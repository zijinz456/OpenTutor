## Reddit Post (r/LocalLLaMA)

**Title:** OpenTutor week 44: 14 community PRs land at once, all touching the adaptive learning internals

This week was unusual for OpenTutor. I merged 14 contributions in a single session, and almost all of them went deeper into the learning science stack than I expected anyone to go without significant context-building.

**What landed:**

The LOOM knowledge graph now validates that the prerequisite graph is a DAG before use. If a cycle is introduced (say, "calculus requires derivatives" and "derivatives require calculus"), the validator finds the weakest edge by weight and removes it rather than throwing an error. This is a defensive measure — the LLM extraction step is not guaranteed to produce cycle-free output, and previously a bad extraction would silently corrupt the graph. One contributor also made the concept-fusion threshold configurable, which matters when you're working with documents in highly technical domains where concept overlap is normal.

LECTOR (semantic interference detection) had its interference threshold hardcoded. If you reviewed a concept and then OpenTutor wanted to introduce something semantically similar, it would either always intervene or never intervene depending on a constant I had set conservatively. A contributor exposed that as `LECTOR_INTERFERENCE_THRESHOLD` in config.py and added 208 lines of E2E tests covering consolidation on different review outcomes.

The CAT (Computer Adaptive Testing) pretest got configurable stopping criteria. Previously the pretest ran for a fixed number of items. Now you can configure max items, minimum items before early stopping, and the SE threshold that triggers early stop. This matters for local setups where inference is slow — you can trade estimation accuracy for session length.

The cognitive-load tuning fix was the most insidious. The weight tuner reads the current weights, applies a gradient update, and writes back. With async requests, two sessions could both read stale weights simultaneously, compute conflicting updates, and the second write would win. The fix serializes writes with a lock. The contributor also added 123 test lines proving the cache eviction behavior is correct.

**The number that matters:** 2,061 test lines added by contributors across 14 PRs. These are not shallow happy-path tests — the LOOM E2E suite builds a full graph from synthetic documents and asserts on graph structure.

The Windows native support (PR #101) is worth mentioning separately for anyone who has been putting off trying the project because of the Docker requirement. A contributor built a full native launcher with process management, log archiving, and an installer builder that produces a distributable `.exe`. It was tested on Windows 11 23H2.

The project is on GitHub at github.com/zijinz456/opentutor. Using Ollama locally with any model that has decent instruction following works. What local model setups are people running for this kind of adaptive tutoring task?

## Reddit Post (r/Anki)

**Title:** I added DAG validation and configurable stopping criteria to an open-source FSRS-based tutor — here's what broke first

I have been building OpenTutor, a local-first adaptive tutor that uses FSRS 4.5 for scheduling. This week a batch of community contributions landed and I want to share what was actually wrong before they did.

The most useful fix was to the LOOM prerequisite graph. OpenTutor builds a knowledge graph from your uploaded documents — nodes are concepts, edges are prerequisites. When scheduling reviews, it tries to respect the graph order: don't review derivatives before limits if you haven't seen limits yet.

The problem: the LLM-extracted graph was not guaranteed to be acyclic. If two concepts mutually referenced each other as prerequisites (this happens more than you'd expect with definitions in dense textbooks), the graph traversal would loop. There was no validation. A contributor added a proper topological sort with cycle detection, and when a cycle is found, it removes the weakest edge by weight rather than failing. This is the right tradeoff — a slightly imperfect graph is better than a hard failure during a study session.

The Computer Adaptive Testing pretest also got a real stopping rule. CAT pretests estimate your ability level before starting scheduled reviews. The old implementation ran for a fixed number of items regardless of how quickly the ability estimate converged. A contributor made this configurable: you can set a standard error threshold that triggers early stopping once the estimate is confident enough. If you're using a slow local model, cutting the pretest from 20 items to 8-10 when the SE drops below 0.3 makes a real practical difference to onboarding time.

The more subtle fix was to cognitive-load weight tuning. OpenTutor adjusts the weights it uses to detect cognitive overload based on your session history. The tuner was not serialized, so two concurrent requests could both compute updates from the same baseline weights and the second write would silently discard the first. This kind of race condition is especially bad for learning systems because it makes adaptive behavior non-deterministic in ways that are hard to debug from session logs.

FSRS itself was also covered for the first time this week: a contributor added unit tests for grade handling, cross-grade orderings, and interval edge cases. The scheduling logic had no test coverage before this. I knew it. I kept not fixing it.

2,061 lines of tests across 14 contributions in one week. The Anki crowd will appreciate that most of these test files are longer than the code they cover.

If you're using FSRS outside of Anki — standalone implementations, custom schedulers — what edge cases have you had to handle that the original paper doesn't address?

## IndieHackers Post

**Title:** Week 44: Strangers added 2,061 lines of tests to my project's learning science core

I need to be honest about something before I talk about this week.

OpenTutor has had production code running with minimal test coverage. Not no coverage — the main flows had tests — but the learning science modules that are actually the point of the project were mostly untested. FSRS scheduling, LOOM graph traversal, LECTOR interference detection, CAT pretest convergence. The code that differentiates OpenTutor from "just another chatbot wrapper" had gaps I kept deferring.

My reasoning was always that these modules require understanding the underlying research before you can write meaningful tests, and writing that context document kept getting pushed down the priority list.

This week, 14 contributors submitted PRs that did exactly what I had been avoiding. They wrote 2,061 lines of tests across the learning science stack. They caught a race condition in cognitive-load weight tuning that I had missed. They found that the LOOM prerequisite graph had no cycle protection — if the LLM ever produced a circular prerequisite structure, the graph traversal would loop. Nobody had reported this as a bug, which means either nobody had hit it or it was failing silently.

A contributor also submitted Windows native support. No Docker, no WSL — a native installer that bundles Python and Node and manages processes like a real desktop app. That was PR #101. I had been planning to tackle Windows support for months. Someone I had never interacted with built the whole thing.

The uncomfortable part: it took me a full day to review all 14 PRs carefully. I almost merged them faster to clear the queue. I didn't, and I caught a few things — a path normalization issue on Windows, a diagnostic log that was capturing values it shouldn't — but mostly I was just reading work that was better than what I would have written under time pressure.

I don't know what drove 14 contributors to this project in the same week. Maybe the GitHub activity is surfacing the project more. Maybe one person found it and shared it. I don't have good attribution.

What I know is that the test gap is almost closed now, and I didn't close it. That's a strange feeling.

Next week I'm writing the context document I kept deferring — the one that explains the learning science well enough that the next contributor doesn't have to reverse-engineer it from the code. It's overdue.

If you've had a similar experience — contributors fixing things you knew were broken before you did — what was it like to read that PR?
