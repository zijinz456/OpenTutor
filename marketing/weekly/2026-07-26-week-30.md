## Reddit Post — r/LocalLLaMA

**Title:** I added a sliding-window weight dampener to my cognitive load detector — the problem with static signal thresholds in local AI tutors

**Body:**

OpenTutor is an open-source, local-first AI learning platform. FastAPI + Next.js + SQLite, runs on Ollama or any OpenAI-compatible endpoint. The core loop is: you upload study material, the system generates content and practice questions, tracks your performance with FSRS 4.5, and adjusts explanation depth in real-time based on a cognitive load estimate.

The cognitive load detection system computes a score from 12 behavioral signals on every message: text-based fatigue cues, session length, unmastered error count, message brevity, help-seeking patterns, quiz accuracy, answer hesitation timing, NLP-based frustration/confusion, relative baseline calibration, wrong answer streaks, inter-message gaps, and repeated errors on the same problem. These are weighted and summed into a 0.0–1.0 score. High score → shorter explanations, simpler scaffolding, proactive break suggestions.

**The saturation problem**

The system broke for students who are consistently at the difficult end of their material. If your `unmastered_errors` signal is elevated for 20 messages in a row, you might just be working on hard material — not in acute overload. But a static scorer treats a persistent baseline as perpetual crisis, and the tutor starts dumbing down explanations for someone who is actually just challenged, not overwhelmed. The adaptation becomes noise.

**The fix: per-signal sliding window tuner**

New module: `cognitive_load_tuning.py`, 136 lines.

After each `compute_cognitive_load()` call, the tuner records every signal value in a per-user sliding window of size 20. When the window mean for a signal exceeds 0.65, the tuner multiplies that signal's weight by 0.90 (decay). The multiplier has a floor of 0.40 — you never fully suppress a signal. When the mean drops below the threshold, the weight recovers at 1.04x per tick up to 1.0.

The result: a persistently-elevated signal gets dampened, giving the other signals more relative influence. If `unmastered_errors` is always high but `nlp_affect` is low (not frustrated), `message_brevity` is normal (not terse), and `answer_hesitation` is stable — the score lands in medium, not high. The student gets appropriately engaged explanations instead of crisis-mode scaffolding.

**Why not ML**

I looked at Bayesian updating for the weight adjustment (Beta distribution over each signal's "is this elevated?" probability). It would be more principled and would handle non-stationary baselines better. I didn't ship it for three reasons:

1. The observable behavior of the sliding window system is auditable. The constants are in the file header with justification. If something goes wrong, I can trace it.
2. Per-user Bayesian state has serialization implications — the in-memory store is already bounded (200 users, LRU eviction). A proper Bayesian updater needs to persist per-user parameters across restarts.
3. The saturation problem is the dominant failure mode right now. The sliding window fixes that. Phase 2 can add Bayesian updating when I have more data on where the window approach fails.

**The constants**

```python
WINDOW_SIZE = 20
HIGH_SIGNAL_THRESHOLD = 0.65
WEIGHT_DECAY_FACTOR = 0.90
MIN_WEIGHT_RATIO = 0.40
RECOVERY_FACTOR = 1.04
```

These were tuned manually. The window of 20 maps roughly to ~10 minutes of active study (assuming ~30s average per message). 0.65 threshold is "elevated most of the time." 0.90 decay is slow — about 7 ticks to get from 1.0 to the 0.40 floor under sustained elevation. 1.04 recovery is slower still — about 23 ticks to return from floor to ceiling. Asymmetric on purpose: fast to suppress saturation, slow to re-trust a signal.

**Ambient monitor addition**

The same commit also added a Tier 2 action to the ambient monitor: `propose_content_generation`. The ambient monitor runs in the background and decides what (if anything) to do: trigger a review session, send a notification, generate a report. Tier 1 actions happen automatically. Tier 2 requires user approval before execution.

`propose_content_generation` fires when a student has been studying for a while but has no AI-generated notes or practice questions yet. Instead of generating them immediately, it inserts a `pending_approval` task that the student sees and must explicitly approve. The task deduplication check prevents multiple identical proposals from stacking.

This is the trust design problem in AI assistants: when should the system act vs. ask? My current heuristic — everything that generates content is Tier 2, everything that schedules or sends is Tier 1 — is rough but has worked in practice.

**What's next**

Signal calibration across the full user session rather than just the current window. The baseline calibrator already exists for message length and help-seeking; extending it to the full 12-signal set is the logical next step. That gets closer to "this signal is high relative to this student's typical session" rather than "this signal is high relative to an arbitrary threshold."

OpenTutor repo: https://github.com/zijinz456/opentutor

What's your approach when behavioral signals saturate? Do you tune thresholds globally, per-user, or something else?

## Reddit Post — r/Anki

**Title:** My FSRS-based tutor adjusts explanation depth by cognitive load — but static thresholds broke it for consistent high-error students

**Body:**

I maintain OpenTutor, an open-source AI learning platform built around FSRS 4.5. In addition to spaced repetition scheduling, it includes an AI tutor that generates explanations and practice questions from your study material. That tutor adjusts in real-time based on a cognitive load estimate — shorter, simpler explanations when you're struggling, more depth and challenge when you're not.

Last week I'm writing about a fix for a specific failure mode in that detection system. It's relevant if you've thought about why Anki's fixed-difficulty approach sometimes feels tone-deaf.

**The problem with static behavioral thresholds**

The cognitive load detector scores a student's state from 12 signals. One of the most predictive is `unmastered_errors`: the count of wrong answers on problems that haven't been mastered yet. Five or more unmastered errors → maximum signal value, contributing strongly to a high load score.

This works correctly for a student who is usually accurate but is having a rough session. It fails for a student who is consistently working near their limits — who always has 5+ unmastered errors because that's just where they are in the material. For that student, the error signal is always near 1.0. The score saturates. The tutor treats them as permanently overloaded and simplifies every response. That's not adaptive — it's just wrong calibration.

**The Anki parallel**

Anki has a related problem in the other direction: it's calibrated globally, not personally. The default "good" response in FSRS schedules the next review based on a model trained on population-average retention curves. If your forgetting curve is steeper or shallower than average, the schedule is miscalibrated until the algorithm accumulates enough personal data to correct.

FSRS 5 and the optimizer address this by fitting parameters to your own review history. The same principle applies to cognitive load detection: thresholds calibrated on a population don't fit every individual.

**The fix: per-signal sliding window dampener**

New module: `cognitive_load_tuning.py`. After each load computation, the tuner records signal values in a 20-message sliding window per user. If a signal's 20-message mean exceeds 0.65, its weight gets multiplied by 0.90 — reduced, but not zeroed (floor of 0.40). When the mean drops below the threshold, the weight recovers slowly (1.04x per tick).

The effect: a student whose error rate is consistently high gets that signal dampened over time. The tutor stops treating their baseline as a crisis state and starts responding to the *changes* in their pattern — when error rate spikes above even their elevated baseline, the other signals (message brevity, help-seeking, NLP frustration) pick up the slack.

136 lines. No model training. The weights are adjusted in-memory per user, reset on explicit request or long inactivity.

**What this means for learning science**

Cognitive Load Theory talks about intrinsic, extraneous, and germane load. Most software implementations measure a proxy for total load without distinguishing. A student consistently working at the edge of their capacity has high intrinsic load — the difficulty of the material is genuinely challenging for them. A student who is exhausted in session 3 of 5 has elevated extraneous load. These feel similar in behavioral signals but warrant different responses.

The sliding window tuner doesn't solve that distinction — it just prevents the system from treating a consistent baseline as acute crisis. The correct long-term fix would involve session-level baselining (what is this student's normal?) and comparing current signals to that baseline rather than an absolute threshold. That's Phase 2.

**Where FSRS connects**

The FSRS scheduler sees cognitive load scores as an indirect input: when load is high, the ambient monitor may suppress new material and trigger a pure review session instead. The cognitive load score also gates the review card ordering — high load → easier (more stable) cards first. These are post-FSRS-algorithm adjustments; the core FSRS computation runs unmodified.

OpenTutor is fully local — Ollama by default, any OpenAI-compatible endpoint. Repo: https://github.com/zijinz456/opentutor

Has anyone found a clean way to separate intrinsic from extraneous load signals in a behavioral detection system? Every approach I've tried conflates them.

## IndieHackers Post

**Title:** My AI tutor was treating students who struggle a lot as always in crisis. The fix was 136 lines of sliding window math.

**Body:**

OpenTutor is an open-source, local-first AI learning platform I've been building and shipping incrementally. It generates practice questions and explanations from your own study material, tracks performance with FSRS 4.5, and adjusts the tutor's behavior in real-time based on how you're doing.

The "adjusts in real-time" part is the cognitive load detector — 12 behavioral signals combined into a score that tells the tutor whether to explain deeply or briefly, challenge or scaffold, ask or tell. When you're in the zone, it steps back. When you're struggling, it simplifies. It's the part of the project I'm most interested in technically.

And it had a quiet bug that I only noticed because a specific kind of student exposed it.

**The failure mode**

Some students work consistently at the hard edge of their material. They always have multiple unmastered errors. They sometimes send brief messages. They occasionally ask for hints. Not because they're overwhelmed in the moment — that's just how they engage. The system sees elevated signals across the board, computes a high cognitive load score, and starts dumbing down every explanation. The tutor becomes patronizing. The student notices. It's not a subtle problem; it's an obvious one once you observe it.

The underlying issue: my detection thresholds were calibrated for a student who is usually doing fine and occasionally struggling. A student who is always at the hard end breaks the model.

**The temptation I didn't give in to**

The obvious solution, if you have an ML background, is to train a model. Fit the thresholds per user. Use a Bayesian approach. Let the parameters adapt.

I spent an afternoon designing what that would look like. It would work better, eventually. It would also need serialization for per-user state, more complex cold-start behavior, and — most importantly — it would be harder to audit when it goes wrong. A sliding window dampener fails visibly. A Bayesian model fails in ways that are harder to trace without logging the full parameter history.

I built the simpler thing. 136 lines. A 20-message sliding window per signal per user. If a signal's window mean exceeds 0.65, multiply its weight by 0.90. Floor at 0.40. Recover at 1.04x per tick when the signal comes back down. The constants are documented in the file header with their reasoning.

**Whether it actually works**

The saturation problem is fixed. Students who are consistently at the hard end of their material no longer get uniformly simplified explanations. The score still goes high when multiple signals spike together, but a single persistently-elevated signal can't dominate anymore.

What I gave up: responsiveness. The window takes 20 messages to react. A student who was previously fine and suddenly hits a hard chapter will get a slower response to the initial elevation. In practice, the other signals (NLP frustration, help-seeking, message brevity) still react immediately — they just have slightly more room to contribute to the score when `unmastered_errors` is dampened. It's a reasonable tradeoff.

**The ambient monitor side**

The same commit added a new action type to the ambient monitor: proposing content generation. The ambient monitor runs in the background between sessions, deciding whether to trigger a review, generate a report, or send a notification. Before this change, content generation (AI notes, practice questions) happened only when you explicitly requested it.

Now the monitor can notice that you've been studying a course for a while without any AI-generated content and propose generating some. It creates a pending task that you see and must approve. Nothing generates without your sign-off.

This sounds obvious but it took me a while to land on: the right default for an AI assistant that runs in the background is to *propose*, not *act*. Especially for anything that generates content or takes time. The user should always be the one deciding whether generation happens.

**The honest state of the project**

Cognitive load detection is genuinely hard. I have 12 signals, manual thresholds, a sliding window dampener, and a separate baseline calibrator for message length and help-seeking. It works better than a static threshold. It doesn't work as well as I want. The next step is session-level baselining — treating a student's average signal values as their personal baseline and measuring deviation from that, rather than absolute thresholds. I haven't built it because the 12-signal system catches the obvious cases well enough for now.

If you've built behavioral signal systems for any kind of adaptive application, I'd be curious what you found actually moves the needle on calibration accuracy. The theory is clearer than the practice.
