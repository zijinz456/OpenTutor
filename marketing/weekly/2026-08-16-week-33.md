## Reddit Post — r/LocalLLaMA

**Title:** Built a 3-stage validate→repair→dedup pipeline for LLM-generated quiz questions (local-first, open source)

**Body:**

OpenTutor is an open-source, local-first AI learning tool. FastAPI + Next.js + SQLite, runs with Ollama or any OpenAI-compatible endpoint. You drop in a PDF or paste a URL, the system extracts content, generates practice questions, schedules spaced reviews with FSRS 4.5, and adapts explanation depth based on a real-time cognitive load score. No cloud lock-in — everything runs on your machine.

The problem I've been wrestling with: when you ask an LLM to generate structured quiz questions, roughly 15% of what comes back is malformed in some way. Missing explanation fields, multiple-choice questions with 3 options instead of 4, a correct_answer value that doesn't match any option label, or (my personal favorite) the model generating the same question twice with slightly different wording because the source material repeated a concept. None of this crashes anything — the bad data just silently persists and the student gets a subtly broken quiz.

The fix is a pipeline I shipped at the end of March: 379 lines in the quiz parser plus another ~845 spread across 11 other files. Stage 1 is validation: every incoming question goes through field checks (non-empty question text, non-empty correct_answer, non-empty explanation, exactly 4 options for MC questions, valid bloom_level, valid difficulty_layer 1-3). Stage 2 is LLM repair: for each question that fails validation, I construct a repair prompt with the specific validation error, the original malformed question JSON, and the source excerpt that generated it, then ask the LLM to return one fixed JSON object. The repair prompt is strict: "fix only the validation issues called out below, keep the question grounded in the source, never add commentary outside the JSON object." Stage 3 is deduplication: normalized Jaccard similarity on tokenized question text, threshold 0.85 — if two questions share 85% of their meaningful tokens, the second gets dropped.

After all three stages, there's a type balance check: no single question type (MC, true/false, short answer, etc.) can be more than 60% of the batch, with a hard minimum of 2 questions per type. This prevents the model from generating 8 true/false questions when the user asked for a mixed quiz.

The outcome struct tracks validated_count, repaired_count, and discarded_count and returns them from the API endpoint, so the UI can surface "7 questions saved, 1 repaired, 2 discarded" rather than just "done." That transparency feels important — the student should know the system made a call.

One thing I haven't solved well: detecting when the repair itself produces a bad result. Right now I run validation on repaired questions, and if they still fail, I discard them. But I don't have a good signal for "the LLM repaired the format but the question content is now wrong." That's a harder problem and I haven't touched it yet.

Code is at github.com/zijinz456/opentutor. The quiz extraction logic is in `apps/api/services/parser/quiz.py`. What validation layers do you run on LLM-structured output before saving it?

## Reddit Post — r/Anki

**Title:** Automated quiz quality control for AI-generated flashcards — what I built after getting sick of bad questions

**Body:**

If you've experimented with AI-generated flashcards, you've run into this: the LLM generates 8 questions, 6 of them are fine, 1 has a correct answer that doesn't match any of the options, and 1 is basically the same question as another but with different wording. You spot the bad ones if you review before importing, but most of us don't — we just trust the output.

I hit this problem building OpenTutor, a local-first open-source study tool. The system generates practice questions from your notes using FSRS 4.5 for scheduling. The failure rate on raw LLM output was higher than I wanted, and the silent failures (bad data saved without any warning) were worse than the outright errors.

What I built is a three-stage pipeline before anything gets persisted. First, every question is validated against a strict schema: question text must be non-empty, correct_answer must be non-empty, explanation must be non-empty, MC questions must have exactly 4 options and the correct_answer must be one of the option labels. Questions that fail go to stage two — I send them back to the LLM with the specific error and the source material and ask for a repair. Questions that can't be repaired get discarded. Stage three is near-duplicate removal using Jaccard similarity on normalized tokens (threshold 0.85).

The reason I'm posting this in r/Anki rather than a programming sub: the quality problem here isn't really a technical problem, it's a learning science problem. A malformed question is obviously bad and easy to filter. But a valid question that tests the wrong thing — something too surface-level, or a question where the "correct" answer is actually debatable — is much harder to catch automatically. The pipeline I built handles the structural failures well. It doesn't touch semantic quality at all.

The question I'm sitting with: how much validation is worth automating versus leaving to the learner's review step? Anki's model is that you rate cards yourself, so low-quality cards get surfaced and deprioritized. The FSRS model I'm using does the same. But a bad question that never gets answered correctly might just keep getting re-scheduled without the learner realizing the question itself is the problem. Has anyone found good ways to flag low-quality cards based on response patterns rather than manually reviewing before import?

## IndieHackers Post

**Title:** I spent 1,224 lines fixing my AI's output quality — and I'm still not sure it's enough

**Body:**

OpenTutor is a local-first AI learning tool I've been building in public for about a year. The core loop: upload a PDF or paste a URL, the system generates practice questions, schedules them with spaced repetition, and adapts explanation depth based on real-time signals. Everything runs locally — Ollama, SQLite, no cloud.

About six months ago I shipped quiz generation. The first version was naive: send content to LLM, parse the JSON array it returns, save it. It worked well enough that I didn't look too closely. Then a friend tried it and asked why one of his multiple-choice questions had the correct answer listed as "C" but there was no option C in the question. The LLM had generated 3 options, a correct_answer value pointing to a fourth option that didn't exist, and I'd saved it without checking.

That sent me down a rabbit hole. I started logging validation results on a test corpus of 50 documents. About 15% of questions had at least one structural problem: missing fields, wrong option counts, duplicates, type imbalance (sometimes 80% true/false, which isn't a useful study mix). None of these caused errors. They just made the product worse in ways that were hard to notice.

The fix took 1,224 lines across 12 files and three weeks of on-and-off work. The pipeline is: validate every field, attempt LLM repair on failures (send the specific error + source material back to the model and ask it to fix just that one issue), deduplicate using Jaccard similarity on normalized tokens, enforce type balance (no more than 60% any one question type), and return stats to the UI so the user sees "7 saved, 1 repaired, 2 discarded" instead of just "done."

The hard part wasn't writing the code. The hard part was deciding what "good enough" means. The repair step helps a lot for structural issues but it can't fix a question that tests the wrong thing. A quiz question that's syntactically valid but pedagogically useless — too surface-level, tests trivia rather than understanding — will pass all my checks and get scheduled for review. I don't have a good answer for that yet.

What I did learn: transparency matters more than perfection. Showing the user that 2 questions were discarded and 1 was repaired feels better than silently fixing things or silently failing. It sets expectations and lets them decide whether to re-run the generation with different settings.

OpenTutor is at github.com/zijinz456/opentutor. If you're building anything that saves AI-generated structured content, what's your quality floor?
