## Reddit Post — r/LocalLLaMA

**Title:** How I stopped making users repeat themselves: explicit preference capture via agent tool + confidence fast-path (local-first, open source)

**Body:**

OpenTutor is an open-source, local-first AI learning tool — FastAPI + Next.js + SQLite, runs with Ollama or any OpenAI-compatible endpoint. You upload a PDF or URL, it generates practice questions, schedules spaced reviews with FSRS 4.5, and adapts explanation depth and format based on a real-time learner model.

The learner model has a preference system. It tracks things like "this user prefers bullet points", "this user wants concise explanations", "this user learns better from examples than from definitions." Preferences are inferred from behavioral signals: if you repeatedly edit the notes the system generates, that's a `modification` signal. If you consistently ask short questions, that's a `behavior` signal. There's a confidence formula: `base_score × frequency_factor × recency_factor × consistency_factor`. Once confidence crosses 0.4, the signal promotes to a saved preference that gets injected into the tutor's system prompt on every subsequent turn.

The problem: the formula was designed for weak, implicit signals. It requires about 5 signals before frequency_factor maxes out. An explicit signal — the user directly saying "I prefer bullet points" or "can you use more examples?" — went through the same pipeline and got a confidence of ~0.14 on first occurrence. Not enough to promote. The system responded "noted" and waited for more data. I watched a user say "please use examples" three times across a single session before anything changed.

The fix has two parts. First, I added `save_user_preference` as an agent tool available to the tutor. The tool description tells the model when to call it: on explicit preference statements, not on normal study questions. When triggered, it records an "explicit" signal and immediately calls the promotion logic. Second, I added a fast-path in the confidence calculator: if there's at least one explicit signal for a dimension, confidence is forced to `max(confidence, 0.5)` — above the 0.4 threshold. A single explicit statement is now enough to save and apply a preference.

The tricky design question was what to do about conflicts. If the user said "I want concise answers" and the behavioral signals lean toward "detailed," the fast-path means explicit wins. That felt right — explicit overrides implicit. But I also didn't want explicit signals to be permanent if the user's behavior changed. The 90-day exponential decay still applies: `exp(-days/90)`. Six months after an explicit statement with no reinforcement, confidence decays to ~0.13 and the preference can be displaced by fresh behavioral signals.

The code is at `apps/api/services/agent/tools/preference_tools.py` (122 lines) and the fast-path is in `apps/api/services/preference/confidence.py` (19 new lines). Inspired by Letta's core_memory_append, which explicitly separates "things the user told you" from "things you inferred about the user."

One open question: the LLM calling the tool has to correctly identify explicit preference statements. Early testing shows it's occasionally too eager — it calls `save_user_preference` when the user says something like "can you explain this differently?" which is a request, not a preference statement. I haven't solved that yet. Has anyone found good prompt-engineering patterns for getting an LLM to distinguish "preference statements" from "in-session requests"?

## Reddit Post — r/Anki

**Title:** Your AI tutor should believe you when you say "I prefer bullet points" — why I had to build this explicitly

**Body:**

I've been building OpenTutor (open-source, local-first, runs on Ollama), an AI-assisted study tool with FSRS 4.5 scheduling. One of its features is an adaptive learner model — it tries to figure out your preferred explanation style, note format, and detail level by watching how you interact with it.

The original implementation was entirely behavioral. It watched what you did — did you edit the generated notes? Did you ask follow-up questions? Did you consistently use short messages or long ones? — and inferred preferences from those signals. I thought purely behavioral inference was more reliable than asking users to configure things up front. Most people don't know they prefer examples over definitions until they've experienced both. Behavior reveals preferences more honestly than configuration.

That was mostly right. But it broke down for explicit statements. Anki users who've thought carefully about how they learn often know exactly what they want: "I want cards with no context clues so I'm forced to recall," "I want definitions before examples," "I want my notes in plain prose, not bullet points." When OpenTutor users said things like this in the chat, the system would note the statement and then... keep doing what it had been doing, because one explicit statement wasn't statistically strong enough evidence in the behavioral formula.

The fix: the tutor now has a `save_user_preference` agent tool. When it hears you explicitly state a preference, it records it and immediately applies it. A single explicit statement now promotes to a saved preference in one shot.

The learning science angle here is about which layer of your learner model should be authoritative. For Anki, you're the authority — you rate cards yourself, and the algorithm trusts your ratings. There's no system trying to infer whether you actually found a card easy or hard based on your typing patterns. But for a conversational tutor, you're not always explicitly rating things. The system has to infer. The mistake I made was applying behavioral inference logic to explicit statements too — treating a direct user statement with the same skepticism as an inferred signal.

The relevant spaced repetition connection: explicit preferences now get injected into the tutor's system prompt and also influence FSRS card ordering. If you've stated a preference for "concise explanations," that tag biases toward shorter explanation cards when you have a choice of equally-scheduled items. Whether that's actually the right behavior for learning outcomes, I genuinely don't know. Has anyone studied whether learner-stated preferences improve retention versus preferences inferred from behavior?

## IndieHackers Post

**Title:** I made users repeat themselves. Here's the 19 lines that fixed it.

**Body:**

OpenTutor is a local-first AI learning tool I've been building for about a year. The core idea: you upload study material, the system generates practice questions, schedules spaced reviews, and adapts explanation style based on a real-time model of how you learn. Everything runs locally — Ollama, SQLite, no cloud lock-in.

The learner model has a preference system. It watches behavioral signals — do you edit the generated notes? Are your questions short or long? Do you ask for more examples? — and accumulates enough evidence before concluding "this user prefers bullet points" or "this user wants concise answers." I built it this way because I thought behavioral inference was more honest than asking users to configure a learning style quiz up front.

The flaw: when a user explicitly says something like "I prefer examples" or "please use bullet points," that statement went through the exact same pipeline as a behavioral signal. The confidence formula needed about 5 signals to approach the promotion threshold. One explicit statement was worth ~0.14 confidence. Not enough. The system would respond "noted" — and then keep explaining things the old way.

I watched this happen in a recorded session. A user said "can you use more examples?" three times in a single conversation. The third time they said it with a period and no question mark, which I read as mild frustration. The system never changed behavior because it was still waiting for its statistical threshold.

The fix was 765 lines total across a refactor, but the key change was 19 lines in `confidence.py`: a fast-path that forces confidence to 0.5 (above the 0.4 promotion threshold) whenever an explicit signal is present. One explicit statement is now enough to save and apply a preference. I also added `save_user_preference` as a direct agent tool, so the tutor can immediately record the preference inline rather than waiting for a background processing pass.

The honest part: I'm not sure this is fully right yet. The fast-path means the tutor's ability to correctly identify "preference statements" versus "in-session requests" now matters more. A miscall in the old system had low consequence — the signal was just one weak vote among many. Now a miscall immediately promotes. Early testing shows the LLM is occasionally too eager. A user asking "can you explain this differently?" sometimes triggers the tool even though it's a request for a different explanation, not a blanket preference. I'm watching this in logs and haven't patched it yet.

What surprised me most: I thought behavioral inference was the principled approach and explicit capture was a shortcut. It turned out that treating explicit statements with the same skepticism as behavioral signals is its own kind of bad design. When someone tells you something directly, believing them is the right default.

OpenTutor is at github.com/zijinz456/opentutor. What's your model for when to trust what a user says explicitly versus what their behavior implies?
