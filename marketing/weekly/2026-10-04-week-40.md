## Reddit Post — r/LocalLLaMA

**Title:** I replaced "use the Socratic method" in my tutor's system prompt with a 5-state finite-state machine — here's what changed

**Body:**

OpenTutor is an open-source local-first AI tutor (FastAPI + Next.js + SQLite, connects to Ollama or any OpenAI-compatible endpoint, MIT licensed). I want to write about a specific design decision in the teaching layer because I think the pattern generalizes: when a behavioral instruction in a prompt produces inconsistent output, an FSM is often a better solution than a more elaborate prompt.

**The problem with "use the Socratic method" as a prompt instruction**

Early versions of the tutor had this in the system prompt: *"Use the Socratic method. Ask questions instead of giving answers."* This produced a tutor that asked a question in response to almost anything, including cases where asking a question was actively wrong — like when a student had been stuck for 4 turns and needed a worked example, or when the student said "I'm confused" and the tutor responded with another question instead of a hint.

The issue is that "Socratic method" is an umbrella term covering several distinct pedagogical moves: eliciting the student's prior thinking, narrowing a vague answer, presenting a counterexample to a misconception, scaffolding a stuck student, and verifying understanding via transfer. A prompt instruction collapses all of those into a single behavior. It produces the same type of response regardless of what the student actually did.

**The FSM approach**

`apps/api/services/agent/socratic_engine.py` (287 lines) implements a 5-state machine:

- **PROBE**: Student context is good, ask an open-ended question. "What do you think happens when...?"
- **CLARIFY**: Student gave a vague or incomplete answer. Narrow the question. "When you say X, do you mean A or B?"
- **CONFRONT**: Student has a specific misconception. Present a counterexample. "If that were true, what would happen in this case...?" (Note: never say "you're wrong" — let the counterexample create cognitive conflict.)
- **SCAFFOLD**: Student is stuck. Give one small hint, not the answer. Break the problem into smaller steps.
- **CONFIRM**: Student demonstrated understanding. Verify with a transfer question. "Good — now what if we change X to Y?"

Transitions are a 20-entry lookup table: `(current_state, response_quality) → next_state`. Response quality is classified by a lightweight LLM call (using the "fast" client in the router, which routes to the cheapest/fastest available model) that outputs one of: correct, partial, wrong, confused, no_response.

**Initial state selection by context**

The engine doesn't start at PROBE by default. It reads cognitive load and mastery:

```python
def _initial_state(self) -> SocraticState:
    if self.cognitive_load > 0.7:
        return SocraticState.SCAFFOLD
    if self.mastery < 0.3:
        return SocraticState.SCAFFOLD
    if self.mastery > 0.7:
        return SocraticState.PROBE
    if self.error_type == "conceptual":
        return SocraticState.CONFRONT
    if self.error_type in ("procedural", "computational"):
        return SocraticState.SCAFFOLD
    return SocraticState.CLARIFY
```

Cognitive load comes from behavioral signals (error rate, response time, session length). High cognitive load is not the moment to ask open-ended questions — the student doesn't have the working memory for it. A student with 0.85 mastery on a concept gets PROBE. A student seeing it for the first time gets SCAFFOLD.

**The escape hatch**

After 4 consecutive SCAFFOLD turns, the directive changes unconditionally to: "Provide a clear, direct explanation with a worked example. Then ask a simple verification question to check understanding." This matters because the Socratic method is not always the right approach. Some students, at some points, need to be shown how to do something rather than questioned until they figure it out themselves. A pure Socratic chatbot that keeps asking questions at a student who needed a worked example 4 turns ago is doing pedagogical harm, not good.

**State persistence**

State persists per user per course in SQLite via `agent_kv`. A study session that resumes the next day picks up the Socratic state from where it was — if you ended in CONFRONT, the next session starts there. Whether this is the right behavior depends on how much time elapsed, which the current implementation doesn't account for. If a student took 3 days off, restarting at PROBE is probably more correct than resuming at whatever state they were in last time.

The code is at github.com/zijinz456/opentutor, the file is `apps/api/services/agent/socratic_engine.py`. Runs fully local against Ollama — the response quality classifier uses whatever "fast" model you've configured, which can be llama3.2:3b or similar.

For those running local tutoring setups: have you found that prompt-based behavioral instructions hold up as sessions get longer, or do you find the LLM drifts from them?

## Reddit Post — r/Anki

**Title:** I implemented the Socratic method as a finite-state machine in an open-source AI tutor. Here's what the states are and why.

**Body:**

I've been building OpenTutor, an open-source AI tutoring tool that uses FSRS 4.5 for scheduling (same algorithm as Anki). This week I want to write about the teaching layer — specifically, how the AI tutor decides whether to ask you a question, give you a hint, or just explain something.

**Why a finite-state machine instead of a prompt instruction**

The obvious approach is to write "use the Socratic method" in the system prompt. I did this first. The problem is that "Socratic method" covers several pedagogically distinct behaviors, and they're not interchangeable. Asking an open-ended question when a student is stuck and has been stuck for 4 turns isn't Socratic teaching — it's frustrating. Presenting a counterexample to a student who doesn't have a misconception, just a knowledge gap, is the wrong move. The tutor needs to know *which* teaching move to make, not just that it should "use Socratic."

**The 5 states**

The engine has 5 states based on the student's current situation:

**PROBE** — Student knows the material reasonably well. Ask an open-ended question and let them reason. This is the classic Socratic move and it's appropriate when the student has the cognitive resources to engage with it. It's not appropriate when they're overwhelmed.

**CLARIFY** — Student gave a vague or incomplete answer. The problem isn't that they're wrong — they might be right and just imprecise. Ask a more specific question to find out what they actually understand.

**CONFRONT** — Student has a specific misconception. This is the most important state to get right. The instruction to the LLM is explicit: *do not say "you're wrong."* Present a counterexample that creates cognitive conflict. Let the contradiction surface on its own. Research on conceptual change (Chi, 2013) suggests that misconceptions are resistant to direct correction but vulnerable to anomalous data — evidence that doesn't fit the student's current model. The counterexample approach is an attempt to operationalize that.

**SCAFFOLD** — Student is genuinely stuck. Give one small hint, not the answer. Break the problem into a smaller step. This is Vygotsky's zone of proximal development in operational form: move the student forward without removing the productive struggle entirely.

**CONFIRM** — Student demonstrated understanding. Ask a transfer question — the same concept in a slightly different context. This tests for genuine understanding rather than pattern matching on the original problem.

**How the state machine decides what to do**

Initial state is context-driven: cognitive load above 0.7 → SCAFFOLD, mastery below 0.3 → SCAFFOLD, mastery above 0.7 → PROBE. After each student response, a lightweight LLM call classifies the response as correct, partial, wrong, confused, or no_response. That classification drives the transition. CONFRONT + correct → CONFIRM. CONFRONT + wrong → SCAFFOLD (the counterexample didn't help, give a hint). SCAFFOLD + correct → PROBE (they got unstuck, return to open questioning).

The escape hatch: 4 turns in SCAFFOLD with no improvement → direct explanation with a worked example. Some things need to be shown, not elicited.

**What I'm uncertain about**

The classification of "misconception vs. knowledge gap" is the hard part. The system uses the error type from the previous quiz (conceptual error → CONFRONT, procedural error → SCAFFOLD), but that classification is imperfect. An LLM can misclassify a conceptual error as procedural and start scaffolding a student who actually needs confrontation with a counterexample.

I also don't know if 5 states is the right granularity. Bloom's taxonomy has 6 levels; the ICAP framework has 4 engagement modes. I picked 5 somewhat intuitively, guided by what I could implement with a clean transition table. If anyone has studied this specific question — how granular should a pedagogical state machine be — I'd like to know what the research says.

OpenTutor is at github.com/zijinz456/opentutor. The file is `apps/api/services/agent/socratic_engine.py`, 287 lines, MIT licensed.

For Anki users: when you get a card wrong, do you think about *why* you got it wrong — misconception vs. knowledge gap vs. procedural error? Does Anki give you a way to distinguish those, or is it all just "wrong"?

## IndieHackers Post

**Title:** I stopped putting "use the Socratic method" in the system prompt and wrote a 287-line state machine instead.

**Body:**

I've been building OpenTutor for almost a year — an open-source AI tutor that runs on your local machine. FastAPI backend, Next.js frontend, SQLite, connects to Ollama or any OpenAI-compatible endpoint. No cloud, no subscription, no data leaving your device.

I want to write about a specific engineering decision this week, because it taught me something about the difference between describing behavior in a prompt and implementing it in code.

**The original approach**

The first version of the tutor had this in the system prompt: "Use the Socratic method. Ask questions instead of giving answers. Help the student discover the answer themselves."

This worked in demos. In longer sessions it fell apart. The tutor asked questions when students explicitly said they were lost. It asked questions when students had been stuck on the same concept for 4 turns. It asked questions when a student had a misconception that could have been addressed with a counterexample, and instead received another open-ended question about the concept they had wrong. The instruction was consistent; the behavior it produced was not.

**What I replaced it with**

`apps/api/services/agent/socratic_engine.py` is 287 lines. It implements a 5-state finite-state machine:

PROBE → ask open-ended question  
CLARIFY → narrow a vague answer  
CONFRONT → present counterexample to a misconception  
SCAFFOLD → give one hint, not the answer  
CONFIRM → verify understanding with a transfer question  

Transitions are a 20-row lookup table. Response quality — correct, partial, wrong, confused, no_response — comes from a lightweight LLM call after each student message. That quality drives the next state. SCAFFOLD + correct → PROBE. CONFRONT + wrong → SCAFFOLD. PROBE + confused → SCAFFOLD.

Initial state is context-driven. Cognitive load above 0.7 (measured from behavioral signals) → skip PROBE, go to SCAFFOLD. High cognitive load is not the moment for open-ended questions. Mastery above 0.7 → PROBE. Mastery below 0.3 → SCAFFOLD.

The escape hatch: after 4 consecutive SCAFFOLD turns without improvement, the directive changes to "provide a clear, direct explanation with a worked example." The Socratic method fails gracefully into direct instruction. A chatbot that keeps asking questions at a student who needed a worked example 4 turns ago is doing harm.

**What this cost and what it bought**

The cost: 287 lines of code and a second LLM call per turn (the response quality classifier). The fast-path client uses the cheapest/smallest available model for this — it only needs to output one word. On a typical turn the classifier adds about 200-400ms.

What it bought: the behavior is auditable. If a student complains that the tutor never explains anything, I can look at the state history and see whether it was stuck in PROBE. If a student says the tutor keeps asking questions when they're lost, I can look at the cognitive load values and see whether the SCAFFOLD threshold was being hit. A prompt instruction is a black box; a state machine has a transition log.

**The thing I'm still uncertain about**

State persists between sessions in SQLite — if you resume after 2 days, the engine picks up where it left off. I'm not sure this is right. Spaced repetition assumes some forgetting happened; maybe the Socratic state should reset too. I haven't done any measurement on whether resuming state helps or hurts outcomes vs. always starting fresh.

The pattern I keep finding: the interesting parts of the system aren't the AI calls — they're the state machines and graph algorithms that sit around the AI calls and constrain its behavior.
