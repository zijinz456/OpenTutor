## Reddit Post — r/LocalLLaMA

**Title:** I added week-over-week learning deltas to my local-first AI tutor — the "are you improving?" problem snapshots can't answer

**Body:**

OpenTutor is an open-source, local-first AI learning tool — FastAPI + Next.js + SQLite, runs against Ollama or any OpenAI-compatible endpoint. No cloud required. One of the things I've been dissatisfied with for a while is that the dashboard gave you current state only: mastery percentage, completion rate, review queue size. All snapshots. You could look at it every day and see 43%, 44%, 43%, and have no idea if you were on a trajectory or spinning in place.

The commit I'm writing about this week adds weekly comparison stats to the dashboard. The API returns a `WeeklyReport` shape: `this_week`, `last_week`, and `deltas` objects — each carrying `study_minutes`, `accuracy` (quiz score), and `active_days`. The frontend renders a three-column grid with this week's number large, last week's number small, and the delta labeled in green or red. The implementation is straightforward; the interesting question was what to compare. I chose those three because they're independent: you can have high accuracy with low study time (reviewing easy material), high study time with low accuracy (grinding hard material), or high active days with low both (short sessions, low engagement). Looking at all three together is more informative than any one.

I also added a "summary" composable block — OpenTutor has 12 learning blocks that arrange themselves based on learner behavior and unlock progressively. The summary block is the 12th. It surfaces mastery %, total mastered nodes, review queue count, and cumulative study time in a 2×2 card grid. The implementation (118 lines) uses `Promise.all([getCourseProgress(), getReviewSession()])` so both API calls are in-flight at the same time. If getReviewSession fails, the block catches and soft-fails — renders without the review count rather than showing an error for the whole block. The review queue is useful context, not required state.

The third piece is a timeline view in the plan section (241 lines). It calls `listStudyGoals()`, then sorts goals into four urgency buckets by `daysLeft`: overdue (< 0), soon (0–7 days), normal (8–30 days), future (30+ days). Each bucket gets a distinct background color — destructive, warning, brand, muted. Goals with no target date sort to the bottom. This is the first place in OpenTutor where deadlines are rendered visually. The calendar picker has always existed; the timeline is what makes the data actually visible.

I'm running this locally with Ollama (llama3.1:8b). The API routes for weekly stats hit SQLite directly — no cache layer. For a single-user local install that's fine; for a shared instance with multiple active courses it might be slow on the weekly stats query since it spans multiple tables. That's a known issue for later.

OpenTutor is MIT: github.com/zijinz456/opentutor. The weekly report type is in `apps/web/src/lib/api/progress.ts`. The blocks are in `apps/web/src/components/blocks/blocks/`. For local LLM users: have you run into performance issues with FSRS scheduling queries at scale, or does SQLite handle it acceptably for personal use?

## Reddit Post — r/Anki

**Title:** My FSRS-based tutor couldn't answer "am I improving?" — here's what I built to fix it

**Body:**

OpenTutor is an open-source AI-assisted study tool I've been building. It uses FSRS 4.5 for scheduling — same algorithm as Anki's current default — combined with a conversational AI tutor that adapts based on your responses. One thing that bothered me for a long time: it showed current state but not trajectory.

Anki handles this through statistics — the forecast, the review heatmap, the card counts over time. Those are retrospective by design: they show what happened, which helps you understand your review load. What I wanted for OpenTutor was something more forward-looking and comparative: this week vs. last week across three dimensions — study minutes, quiz accuracy, and active days.

The reason I chose those three: they come apart in interesting ways that a single mastery score masks. A week with high accuracy and low study time usually means you reviewed material that was already consolidating. A week with low accuracy and high study time usually means you hit something genuinely hard and kept working through it. A week with many active days and short sessions often means scattered engagement without depth. Seeing all three together tells a different story than mastery alone.

The implementation adds a WeeklyReport API type and a dashboard section that renders the comparison explicitly — this week's number large, last week's small, delta labeled in green/red. No trend lines or graphs at this stage. Just the two periods side by side, because I kept looking at my own mastery number and thinking "is this good?" without having anything to compare against.

I also added a summary block — a new composable block that gives you a within-course digest without having to navigate anywhere. Mastery percentage, completion rate, review queue count, and cumulative study time in a 2×2 grid. The review queue count pulls from the same FSRS-backed review session endpoint that the main review block uses, but soft-fails if the call errors — the digest renders without it rather than blocking. In Anki terms, this is roughly equivalent to having your due count visible on the deck list without opening the deck.

What I still can't answer: whether week-over-week deltas are the right comparison window for spaced repetition progress. FSRS schedules cards on intervals of days to months. A one-week window might capture a lot of review activity one week and almost none the next, not because you studied less, but because that's when the intervals happened to land. Monthly comparisons might be more stable for SRS-heavy workflows. Has anyone figured out the right time window for comparing SRS progress week-to-week vs. month-to-month?

## IndieHackers Post

**Title:** My dashboard answered "where are you?" but not "are you getting better?" — 571 lines to fix that

**Body:**

I've been building OpenTutor for about a year. It's a local-first AI learning tool — runs on your machine with Ollama, no cloud, no subscriptions. The core idea is 12 composable learning blocks that rearrange based on how you're studying: flashcards, practice questions, concept maps, reading, coding problems, all configurable and progressively unlocked.

For the past few months the dashboard showed mastery percentage. That's a snapshot. You could be at 40% today and 40% next week and have no signal about whether anything was working. A student I showed it to said, "how do I know if I'm getting better?" and I didn't have a good answer. That question sat with me for a while.

What I shipped last week (writing this from a backlog, the commit is April 2): week-over-week comparison stats. Three numbers — study minutes, quiz accuracy, active days — each shown alongside last week's value and the delta. The data model is simple: a WeeklyReport type with this_week, last_week, and deltas objects. The frontend is three stat tiles in a row. Nothing fancy. But now when you open the dashboard you immediately have a comparison point.

The tricky design question was where this information should live. OpenTutor has two layers: a dashboard that's course-agnostic (you might be studying multiple courses), and a block layer that's within a single course. I put cross-course mastery on the dashboard, and added a new summary block for within-course state — mastery %, review queue, study time — that lives in the block layer and can be placed wherever the adaptive system puts it in the workspace layout.

Here's the thing about that block: it was the last of the 12 composable blocks I've been building since the start of the project. I didn't plan it that way. I'd been thinking of the workspace as the place where learning happens and the dashboard as navigation infrastructure. The summary block made me realize the digest view was missing from the workspace entirely — students were having to leave their study flow to check their numbers. That felt like a design mistake I'd been carrying for a long time and not naming.

The honest part: I'm not sure week-over-week is the right comparison window for a spaced repetition tool. Review intervals can be weeks long, so one week you might have 50 reviews due and the next week 8, through no behavior change on your part. The weekly stats might just be reflecting the FSRS schedule more than your actual engagement patterns. I don't have enough usage data to know whether users find it meaningful or confusing. I shipped it because I wanted to find out.

OpenTutor is at github.com/zijinz456/opentutor. If you're building something that uses spaced repetition, what do you use to answer the "am I improving?" question — and what time window feels right to you?
