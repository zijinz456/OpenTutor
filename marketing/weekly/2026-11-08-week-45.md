## Reddit Post (r/LocalLLaMA)

**Title:** I found out what happens when you send out-of-range ratings to an FSRS spaced repetition API (it's not pretty)

This week a contributor filed PR #109 against OpenTutor with a subject line I had been quietly dreading: fixing FSRS rating validation.

OpenTutor uses FSRS-5/6, a 21-parameter spaced repetition algorithm. The rating scale is 1–4 (Again, Hard, Good, Easy). The POST `/api/flashcards/review` endpoint accepted any integer without validating it. I knew this was fragile. I didn't know how fragile until someone actually tested the edges.

**What actually happened with invalid inputs:**

Rating 0: Python's negative indexing meant `w[rating - 1]` resolved to `w[-1]`, which is the last element in the parameter array — the forgetting-curve decay constant, not an initial stability value. The algorithm ran without error and produced a card schedule based on the wrong math. That schedule was saved.

Ratings 5–21: The parameter array has indices 0–3 for the initial-rating branch. The code path that handles these ratings falls through to the "review" branch, which treats them like a 3 (Good). No crash, no log entry, just quietly wrong intervals for any client sending unexpected values.

Rating 22+: IndexError. The API returned a 500. But the card's internal state had already been modified before the error propagated, so we were writing partial results to the database on hard failures.

**The fix:**

Two layers. First, a Pydantic field constraint on the request model: `rating: int = Field(..., ge=1, le=4)`. Invalid input now gets rejected with a 422 before `review_card()` is ever called. Second, an explicit guard inside `review_card()` itself that raises ValueError — so the function fails loudly if called directly from Python without going through the API validator.

94 test lines. The tests cover each invalid boundary value, the Python negative-index case specifically, and verify that no card state is written on a rejected request.

**On the quiz side:** the other PR this week added short-answer, fill-blank, and coding question-type support to the quiz UI. These question types already existed in the backend schema but the frontend was rendering them without input controls. Fill-blank now gets a single-line `<input>`, short-answer and coding get a `<textarea>` with a submit button. 162 test lines there.

The FSRS issue is a good reminder that input validation at the algorithm level matters independently of API-layer validation. The two should agree, but they're not the same guard.

## Reddit Post (r/Anki)

**Title:** We shipped a bug where out-of-range FSRS ratings silently corrupted card schedules — here's how it worked

If you've used Anki and wondered what would happen if the review endpoint accepted a rating of 0, or 22, or 7 — I now have empirical data.

OpenTutor uses FSRS-5/6 for spaced repetition. This week we fixed a validation gap that had existed since the spaced repetition backend was first written: the review endpoint didn't reject integers outside the 1–4 scale.

**The 1–4 scale matters for a specific reason:**

FSRS uses a 21-parameter array where the first four elements are the initial stability values for each rating (Again, Hard, Good, Easy). These four starting points are the basis for how the algorithm estimates how long a new card should take to become a "review" card. If you index into that array with 0, you get `w[-1]` in Python — the decay constant, not a stability value. The card's first interval gets computed from the wrong number, and that number gets saved.

For ratings 5–21, the algorithm falls through to a code path meant for review cards (not new cards) and treats the grade as if it were a 3. So a client sending "5" for "correct" would get roughly the same interval as "Good" — but not exactly, because the intermediate computations differ.

For ratings 22+: the array is only 21 elements. IndexError. 500 from the API. Card state partially written.

**What it means for learning:**

Corrupted initial stability means the algorithm can't correctly estimate future review timing. A card that should have its first review in 1 day might get scheduled for 5 days or 0.3 days, depending on what parameter happened to be at the wrong index. The forgetting-curve model breaks down from the first review. Over weeks of reviews, the card's difficulty and stability values compound from that bad starting point.

**The fix:** Pydantic constraint (`ge=1, le=4`) at the API layer, explicit ValueError guard inside `review_card()`, 94 test lines covering the specific bad-index behavior.

The interesting part for me was realizing how much of the algorithm's safety depends on the calling code. FSRS assumes its rating parameter is in range. It doesn't document what happens if it isn't, because that's not supposed to happen. Building a production API around any algorithm means being paranoid about assumptions the algorithm's authors didn't think to state.

Has anyone else run into subtle scheduling corruption issues from bad input data, in Anki or elsewhere?

## IndieHackers Post

**Title:** The bug I knew was there but hadn't measured

I've been building OpenTutor for about eight months — a local-first adaptive learning platform that uses FSRS for spaced repetition and a block-based workspace that rearranges itself based on how you're learning. This week a contributor fixed something I had been quietly flagging as "needs attention" and never getting to.

The review endpoint for flashcards accepted any integer as a rating. FSRS expects 1–4. I knew this. The validation was just never added. My mental model was "the frontend always sends 1–4, so it's fine." That is the mental model of someone who hasn't thought hard about their API surface.

A contributor dug in and documented exactly what happened: rating 0 reads `w[-1]` via Python's negative indexing — a decay constant, not a stability value, so the first interval gets computed from the wrong number. Ratings 5–21 silently grade as Good. Rating 22+ crashes with an IndexError, but only after partially writing the card state to the database.

That last one is the part I found most uncomfortable. We were committing corrupted card data on hard failures. Not "we had a bug that might have caused wrong intervals." We had a bug that could write inconsistent state and then return a 500 with no indication to the client that anything had been saved.

The fix was straightforward: a Pydantic field constraint at the request layer and an explicit guard inside the core function. 94 test lines. It took one afternoon.

The honest thing to say is: I should have written those tests before the endpoint shipped. The gap between "I know this is fragile" and "I've measured exactly how it fails" is where most of the real bugs live. I was aware of the first. A contributor had to do the second.

Also this week: the quiz view now supports short-answer and fill-blank question types. The backend schema had these types from early on, but the frontend was rendering them without any input controls — which meant learners couldn't actually answer them. That's fixed now, with 162 test lines covering the new input behavior.

The number that stuck with me this week was 94 — the test lines it took to describe a bug I could have summarized in a sentence. Tests are documentation for the specific ways things break. I hadn't written that documentation.
