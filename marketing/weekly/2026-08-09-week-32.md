## Reddit Post — r/LocalLLaMA

**Title:** I found a signal saturation bug in my cognitive load detector and fixed it with a sliding window auto-tuner — no ML, 136 lines

**Body:**

OpenTutor is an open-source, local-first AI learning platform. FastAPI + Next.js + SQLite, runs on Ollama or any OpenAI-compatible endpoint. You upload study material, the system generates practice questions and explanations, schedules reviews with FSRS 4.5, and adapts in real-time to a cognitive load score computed from behavioral signals.

That last part is what this post is about.

**The cognitive load detector**

The system computes a composite cognitive load score (0.0–1.0) on every tutor message from five behavioral signals:

- `error_rate` — wrong answers per recent question
- `session_duration` — time in current session
- `help_seeking` — frequency of "help", "hint", "I don't understand" patterns
- `message_length` — shorter messages correlate with exhaustion
- `fatigue_text` — NLP affect analysis flagging fatigue cues

Each signal has a configured weight. The composite score gets injected into the tutor's system prompt to adjust explanation depth, problem difficulty, and pace.

**The bug I found**

Signal saturation. A student with chronically high error rates — not because they're overloaded right now, but because the material is genuinely hard and that's just their baseline — will peg the `error_rate` signal near 1.0 indefinitely. The composite score saturates. The tutor interprets every message as a high-load emergency and keeps softening difficulty, simplifying explanations, offering hints unprompted.

It's not detecting cognitive overload at that point. It's measuring a baseline and mislabeling it as crisis.

I'd built a careful detection system and introduced a systematic bias I hadn't noticed because I was only testing with short sessions where baselines hadn't stabilized.

**The fix: sliding window weight auto-tuning**

`cognitive_load_tuning.py` — 136 lines, no external dependencies.

For each signal, the tuner maintains a `collections.deque` of the last 20 score values per user. After 5+ data points accumulate, it computes the window mean and applies a multiplier:

```python
WINDOW_SIZE = 20
HIGH_SIGNAL_THRESHOLD = 0.65
WEIGHT_DECAY_FACTOR = 0.90   # multiply weight by this when signal is persistently high
MIN_WEIGHT_RATIO = 0.40      # floor — don't suppress entirely
RECOVERY_FACTOR = 1.04       # nudge weight back up when signal drops below threshold
```

If `mean >= 0.65`: the multiplier decays by 10% per computation, down to a floor of 40%. If `mean < 0.65`: the multiplier recovers by 4% per computation, up to 1.0.

The effective weight used by `compute_cognitive_load()` becomes `configured_weight * multiplier`. Signals that are chronically elevated get dampened. Other signals retain their full weight and their relative contributions increase.

**Why not something smarter**

I considered fitting a per-user Bayesian weight distribution. Two reasons I didn't:

1. Complexity cost. I maintain this alone. A sliding mean + decay is easy to reason about, debug, and explain to users. If a student asks "why did the tutor suddenly change behavior?" I can point to a simple rule, not a black box.

2. The dampening goal is narrow. I don't want to learn the "correct" weight — I want to prevent one persistently elevated signal from saturating the composite score. Dampening by 10% per update with a 40% floor accomplishes that without claiming to know what the "true" weight should be.

The bounded in-memory cache handles up to 200 simultaneous users before it evicts the least-active entry. For a local-first single-user deployment this is never hit, but it means the service won't OOM if someone runs it in a small shared deployment.

**The other thing in this commit: Tier-2 ambient actions**

The ambient monitor — which runs a periodic LLM deliberation loop over the student's learning state — got a new action type: `propose_content_generation`. It's explicitly marked Tier 2, meaning it requires user approval before anything happens. If the monitor decides the student has studied long enough that they'd benefit from AI-generated notes or a practice set, it creates a pending block in the workspace UI that the student must approve.

The distinction matters: I don't want the system generating content silently. For notes and quizzes, the student should decide when they want them.

OpenTutor repo: https://github.com/zijinz456/opentutor

Has anyone else run into signal saturation in adaptive systems? I'm curious whether the sliding window approach holds up at scale or whether per-student learned weights are worth the complexity.

## Reddit Post — r/Anki

**Title:** My FSRS-based tutor was quietly misreading cognitive load for struggling students — here's the fix and what it does to scheduling

**Body:**

I maintain OpenTutor, an open-source AI learning platform built around FSRS 4.5. You upload study material, it generates practice questions, tracks performance, and schedules reviews using FSRS. There's also a real-time cognitive load detector that adjusts tutor behavior mid-session.

I found a problem with the cognitive load detector that was affecting scheduling quality for students who struggle.

**What cognitive load detection does in OpenTutor**

The system computes a score (0.0–1.0) from behavioral signals: error rate, session duration, help-seeking frequency, message length, and fatigue text cues. That score does two things:

1. Adjusts the tutor's explanation style in real-time (more scaffolding when load is high, more challenge when load is low)
2. Feeds into card ordering — high-load sessions get easier cards surfaced first, even if FSRS would normally schedule a harder card next

The second part is where the saturation bug mattered most for scheduling.

**The saturation problem**

A student who consistently struggles with a topic will have a chronically high error rate. If error_rate stays near 1.0 for 20 consecutive messages, the system's composite cognitive load score saturates. It interprets every session as high-overload and permanently routes easier cards to the front of the queue — even when the student isn't actually overloaded in a given session, just working through genuinely hard material.

The result: the FSRS scheduler gets a biased difficulty signal. Cards the student is ready to challenge on get repeatedly deferred. Intervals stay shorter than they should be. The system mistakes "this student has a hard baseline" for "this student needs permanent protection from difficult cards."

**The fix: signal dampening with a sliding window**

I added a 136-line auto-tuner that maintains a 20-message sliding window per signal per user. If a signal's mean exceeds 0.65 (persistently elevated), its weight multiplier decays by 10% per reading down to a 40% floor. When the signal drops back below the threshold, it recovers at 4% per update.

This means:
- A student with a genuinely high error-rate baseline: error_rate signal gets dampened, other signals (session duration, help-seeking) retain their full weight, composite score reflects a more balanced read
- A student in a genuinely high-load spike: all signals elevate together in the window, no individual signal dominates, the composite accurately reflects acute overload

The practical scheduling effect: students who were previously having their harder FSRS-scheduled cards indefinitely deferred should now get them surfaced when they're in a normal-load session, even if their historical error rate is high.

**What this doesn't fix**

The auto-tuner is per-session and in-memory. It resets on server restart and doesn't persist across sessions. I haven't decided whether I want per-user learned weights to persist — there's a case that they should (student's baseline is stable across sessions) and a case they shouldn't (a break of several days might mean the baseline changed). Currently they reset, which means the first 5–10 messages of a new session run without dampening.

If you use Anki with any adaptive difficulty layer: have you found that chronically struggling students benefit from permanent difficulty reduction, or does it create a false floor that prevents them from making progress?

## IndieHackers Post

**Title:** I found a quiet bug that was making my AI tutor too easy for the wrong students. 136 lines to fix it.

**Body:**

OpenTutor is an open-source, local-first AI learning platform I've been building. You upload study material — textbooks, lecture notes, anything — it generates practice questions, tracks performance with FSRS 4.5 spaced repetition, and adjusts tutor behavior in real-time based on cognitive load signals. Local by default — Ollama or any OpenAI-compatible endpoint on your own machine.

This week I found a quiet bug in the core adaptive loop. Not a crash, not a data loss, not anything obvious. Just the system silently doing the wrong thing for the users who needed it most.

**The bug**

OpenTutor computes a cognitive load score for each user in real-time. Five behavioral signals feed into a weighted composite: error rate, session duration, help-seeking patterns, message length, fatigue cues. The score adjusts how the tutor explains things — harder explanations when load is low, more scaffolding when load is high — and influences which practice cards get surfaced first.

The problem: a student who consistently struggles has a high error rate by definition. That's not momentary overload. That's their baseline. But the system was treating their chronically high error_rate as if every session were a crisis. The composite score would saturate and stay near the high-overload zone indefinitely.

The practical consequence: the tutor would keep simplifying explanations and deferring harder FSRS cards for students who weren't in the optimal zone but weren't overloaded either. It was giving "protection" to exactly the students who needed challenge.

I hadn't noticed because my test sessions were short. Baselines don't stabilize in ten minutes.

**How I found it**

I ran a simulated long study session — 40 minutes, high error rate throughout — and logged the cognitive load signals. At message 15, error_rate was 0.9. At message 25, still 0.9. At message 35, still 0.9. And the tutor's behavior had locked into permanent-scaffolding mode. No other signals changed. It was entirely driven by one persistently elevated signal drowning out everything else.

**The fix: cognitive_load_tuning.py, 136 lines**

I added a per-user sliding window auto-tuner. It maintains a 20-message deque for each signal. After 5 readings, if the signal mean exceeds 0.65, the signal's weight contribution decays by 10% per reading, down to a floor of 40%. When the mean drops below threshold, the weight recovers at 4% per update.

```python
WINDOW_SIZE = 20
HIGH_SIGNAL_THRESHOLD = 0.65
WEIGHT_DECAY_FACTOR = 0.90
MIN_WEIGHT_RATIO = 0.40
RECOVERY_FACTOR = 1.04
```

No ML, no learned parameters, no new dependencies. The tuner runs synchronously after each `compute_cognitive_load()` call and adds negligible overhead.

I considered making this smarter — a Bayesian model, per-user learned weights that persist across sessions. I chose not to. I'm one person maintaining this. The sliding window is simple enough to understand in two minutes, debug in five, and explain to a user in one sentence. The Bayesian version would have been more principled and more likely to introduce subtle bugs I'd find six months from now.

**What else shipped in the same commit**

The block unlock overlay. OpenTutor has 12 composable learning blocks (quiz, flashcards, knowledge graph, summary, timeline, wrong answers, etc.) that lock and unlock progressively based on session state, learning mode, and prerequisite conditions. Until this commit, a locked block would just... not render. That was confusing — students didn't know if the block was broken or intentionally hidden.

Now locked blocks show a frosted overlay with a Lock icon, the block name, and the specific unlock hint ("Complete your first quiz session to unlock this") and reason. 35 lines of changes to the block-wrapper component. Users now know what they're working toward, not just what they can't access.

The third piece: the ambient monitor got a new Tier-2 action called `propose_content_generation`. The agent can now decide to suggest generating notes or a practice set when conditions are right — but it creates a pending approval card in the workspace instead of generating automatically. The student sees the suggestion and decides whether to accept it.

I debated whether to make content generation automatic. I decided against it. Generating a 30-card quiz set without warning is the kind of thing that frustrates users. The suggest-then-approve pattern costs one extra tap, keeps the user in control, and means generated content appears when the student actually wants it.

**What I'd do differently**

The sliding window doesn't persist across sessions, which means the first 5–10 messages of a new session always run without dampening. For a student with a stable high-error-rate baseline, that means the system briefly overcorrects at the start of each session before the window fills. I haven't decided if I want to persist per-user multipliers to the database — it adds complexity, and a long break between sessions might mean the baseline genuinely changed. Right now, I accept the cold-start imprecision.
